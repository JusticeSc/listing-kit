# SEL-003 选型报告：语义/视觉调用传输层

按 `docs/standards-template/templates/TECH_SELECTION.md` 的字段走一遍（SEL-004 映射：报告不另立
文件，结论落点是项目上下文 §4.1 的 SEL-003 行）。本文件回答：之前 SEL-003 一直「讨论中」，

## 1. 问题
语义（`deepseek-v4.1-flash`）与视觉校验（VLM，模型 ID 待 V2.5.2 定）需要一条稳定的调用传输层：
超时、错误分类、重试边界、结构化输出解析。当前 V2 适配器草案用 `requests` 手写这一层。

## 2. 约束
- 技术栈：Python 3.13；服务端 stdlib `http.server`（SEL-002），不设第二个状态权威（SEL-001）
- 端点：阿里云百炼 OpenAI 兼容模式 `https://dashscope.aliyuncs.com/compatible-mode/v1`
- 依赖纪律：新增依赖必须锁定版本 + 许可证登记，`tools/check_docs.py` 双向比对
- 体积：本机/内网小规模使用，但依赖必须可解释、可移除

## 3. 已有能力盘点（复用阶梯）
- 仓库内：`src/providers/` 已有 requests 实现（V1 基线）
- 现有依赖：`requests==2.34.2`（Apache-2.0），无模型 SDK
- 标准库：`urllib.request`（无连接池、无重试、无类型化响应）

## 4. 候选
- A：`openai` SDK（实测解析到 3.20.0）
- B：`litellm`（实测解析到 1.103.0）
- C：继续 `requests` 手写传输层（对照组）
- （附测）`langchain-core`：用户此前问到的第三选项，一并实测依赖规模

## 6. 推荐与否决
- **推荐 A（openai SDK）**：14 包、Apache-2.0、类型化响应、超时/重试开箱即用；移除成本小（只在适配器 import 处）
- 否决 B（litellm）：59 包，且本项目不需要多供应商路由
- 否决 C（requests 手写）：省包不省维护，违反选型门禁的自造清单
- 否决 `langchain-core`：33 包且与 SEL-001 冲突

## 7. PoC（真实调用，共 4 次最小探针；命令：`uv run --no-project --with openai --python 3.13 python -c <脚本>`）
```
调用1/2: {"model":"deepseek-v4.1-flash","latency_s":1.39,"usage":{"prompt":35,"completion":16,"total":51},"text_len":0}
调用3:   max_tokens=64 → completion=64 全计入、可见文本仍为空；message 暴露 reasoning_content 字段
调用4:   max_tokens=512 → completion=129，reasoning_len=175，可见文本 44 字（中文）→ 通过
```
结论：传输层可用。**`deepseek-v4.1-flash` 是推理型输出**——max_tokens 太小会把预算全花在 reasoning 上、
可见内容为空。适配器必须给 reasoning 预留预算，这条写入 V2.2.2 验收条件。
（探针终端对中文输出有一次编码显示失真；字段与长度正常，属终端显示问题，不影响 SDK 结论。）
