# V2.R6.4 存储与合同测量复访（2026-10-03）

输入：repository 全历史读、代表长历史、跨语言词表/schema（计划 §9 V2.R6.4）。
方法：真实 Chromium headless + 正式测试服务器（tools/v2_test_server.py）+ 产品 storage 代码直调，
独立临时 profile，fake provider，0 次真实模型调用。测量点全部复用 performance.now +
既有 verifier 快照语义（DB_SNAPSHOT / 游标快照 / boot trail 思路），零新依赖。

## 1. 读路径（调用点 → 文件:行 → 触发时机）

- boot：app.js boot() → session.js boot()（openStorage → pointer.get → workspace.open）。
- open：handleOpen（projects.get → pointer.set）→ workspace.open → loadWorkspace（打开唯一全量装载序列）。
- refresh：app.js refresh() = projects.list() 全表 getAll + JS 排序（repository.js:112-119，
  索引 by_updated_at 未被使用）；任何首页显示/项目变更触发。
- save：documents.save（repository.js:244-289）事务内先按 by_project_document getAll
  该文档全链算 currentVersion（:261-263），OCC 期望版本比对（:264-273），再 append（:275-286）。
  读放大 = 该文档链长。任务/槽位/报告等追加写不带 expectedVersion（永不冲突，由领域判新旧）。
- open 主路径 loadWorkspace：14 次 documents 查询，全部落在 by_project_kind /
  by_project_document 索引 getAll，索引键不含 version——每次 listLatest 实际读入该 kind
  全部历史版本再在 JS 里 reduce 出最新版；getLatest/listVersions 读单文档全链。
  参考图每张一次 assets.get（Blob 全量）；ensureReviewReport 可能读 Blob + 写报告；
  deriveAndApplyState 可能写 project.state（revision++）。
- export：transfer.js exportProjectPackage（projects.get → documents.listAll →
  assets.list → 逐资产 blob.arrayBuffer() 全量字节入内存）→ package.js buildProjectPackage；
  manifest.integrity 已记录 document_bytes/asset_bytes（package.js:118-123），导出峰值字节现成判据。
- import：transfer.js importProjectPackage（事务外 parse + 哈希校验 → 单事务
  projects + documents + assets 写入）；失败 abort，无半份项目。

事务语义：projects.revision++（rename/setState）；documents append-only + OCC；
assets 内容寻址去重（同 project_id + sha256 已存在直接返回既有，不重复存）。
指针：localStorage 仅 {project_id, updated_at}（pointer.js，MAX 512B）；损坏即清除返回 null。
单文档上限 MAX_DOCUMENT_BYTES = 1MB（validate.js:9）。

## 2. 实测（本轮新鲜，headless 真实 IDB）

M1 打开类读（种子：suite_plan 单链 120 版 + fact_slot 20 文档×3 版 + 3 资产）：
- listLatest(suite_plan)：1 行，1.6ms；listVersions（链 120）：120 行，1.7ms；
  listAll：180 行，6.8ms；assets.list：3 行，0.5ms。
- saveDocument 在链长 120 时：新 version=121，1.8ms。

W1 现实工作负载（intake 3v + 8 槽×2v + plan 4v + attempts 4×2 + 候选 8 + 报告 8 + 选择 2v，
共 49 文档 0 资产）：7 种 kind 各一次 listLatest 共 31 行 6.6ms；listAll 49 行 0.7ms；
projects.list 1 行 0.2ms；export 2.5ms，zip 19871B，manifest integrity 自洽。

M4 长链压力（suite_plan 单链 2000 版，小 payload）：
- 种子写入 2000 版：22.6s（含每次事务先读全链，写入成本随链长线性增长——写侧已证线性，读侧单次仍毫秒级）。
- listVersions（2000 行）getAll：24.4ms；同范围游标计数：2000 行 41.7ms；
  链长 2000 时再 save 一版：24.9ms（读全链主导）。
- 结论：游标不减少读取条数（getAll 已取全量），只能降峰值内存；2000 版单链下两者同量级，
  游标反而更慢（逐行 continue 开销）。当前规模下无游标/索引改造收益。

M3 导出：181 文档 + 3 资产（document_bytes 42902 + asset_bytes 15021）→ export 13ms，
zip 114718B。manifest.integrity 与包字节一致。

既有最大规模（历史证据，非本轮）：ui-baseline-20261001-chrome.json documents 至 82、
资产至 8、交付 zip 48070B。本轮种子（2000 版单链）已超历史一个量级，仍毫秒级读。

## 3. 判定：无收益，不改

- 打开/保存/导出在现实规模（~50 文档）与压力规模（单链 2000 版）下单次读均为毫秒级；
  瓶颈在种子写入侧的线性全链读（save 先 getAll），但那是 OCC 正确性所必需（算 currentVersion），
  且单次 save 仍 <25ms，无需为其加索引/游标。
- 索引现状：by_project_kind / by_project_document 键不含 version，无法只取最新版而不读历史。
  要降读放大需新增“version 倒序索引或 latest 指针”，即 schema 变更 + 迁移 + 双写一致性——
  当前收益（省几毫秒、几百行内存）远小于成本（迁移风险、双权威风险），明确不做。
- openCursorPromise（db.js:53）全仓无调用者，保持现状（现成落点，不删除、不接线）。
- projects.list 全表 getAll + JS 排序：项目数级规模（个位数）下不改；by_updated_at 索引保持未用。

## 5. 验收对照（V2.R6.4）

- 同版本历史排序/事务/Blob：listAll 稳定排序、事务 abort 无半写、资产去重——读路径与实测覆盖。
- 平台业务不变量仍单一权威：repository 唯一读写入口，未新增第二套 facade。
- 未虚报性能：所有数字为本轮真实 IDB 实测，慢路径（2000 版种子 22.6s）如实保留；
  不把毫秒级单次读夸大为“优化成果”。
- 无向后兼容迁移层新增：零 schema 变更，零迁移。

边界：headless 本机 IDB 延迟，不代表用户机器满载/配额紧张形态；2000 版单链为合成压力，
非真实任务形态。长历史若进入万级版本/百 MB 资产，需重测 M1/M2/M4 再议。
