Observed correction
===================
The initial design treated the CI runner as the image-transfer owner. That repeatedly moves the base image and did
not match the requested remote-server Docker operating model. The accepted design sends a minimal, explicit build
context; the remote Docker daemon builds a SHA-tagged image, reuses its layer cache, replaces only the named
amz-listing-kit container, and restores the previous named container if health does not become healthy.

What this proves
================
- A clean GitHub runner can validate the tracked repository and build/start the Product V2 image.
- The configured SSH credentials can reach the target server and use its Docker daemon.
- The target server built and started the named SHA image on host port 8780, and Docker reported healthy.
- The workflow has an executable previous-container rollback path for failed health transitions.

What this does not prove
========================
- It does not prove public or tunnel reachability from an end-user network; no public URL was observed.
- It does not prove the rollback branch by deliberately deploying a bad image.
- It does not prove future semantic/image/VLM providers, which are outside current Product V2 runtime behavior.
- It does not prove the complete product goal; V2.2.2 and later product slices remain pending.
