## 4. 结论：漂移的真实构成

| 漂移项 | 事实 | 是否本轮 Phase 0 造成的 |
|---|---|---|
| 源码树身份 | 两个时点都是 78 个文件、同一个集合，**只差 1 个**：`evals/probes/project_state.py` | **否**。Phase 0 的代码全在 `demo/`，不在基线身份范围内 |
| `out/B0FULLSET01_…/run.jsonl` | 301,530 → 320,671 字节 | 否。是 09-24 18:54 那次**复用现有 out/** 的回归重写了它 |
| `evals/last_regress.txt` | sha16 `8c3b5b70ab3ed24a`（21 通过 · 0 环境拦下 · 0 未通过）→ `cdd3b48ae1f01313`（20 通过 · 0 环境拦下 · 1 未通过） | 否 |

**一处计划与实现不一致（需产品决策，本轮只登记不改）**：计划 §4.3 明文写「v2 基线身份只覆盖后者」（`config/ src/ tools/ web/ run.py requirements*`），而`tools/snapshot_v2_baseline.py` 的 `source_files()` **额外**把整个 `evals/**/*.py`也算进身份。后果恰好是计划想避免的那件事：**修一个控制面探针，基线就报「代码树身份已变化」**。而这次唯一的源码变化正是那个探针 —— 按计划口径，「v2 legacy 未被改动」其实仍然成立。

**基线刷新不能单独做**：`snapshot_v2_baseline.py` 不校验回归报告是否属于当前代码，只把 `last_regress.txt` 的哈希与结论行抄进 manifest。此刻刷新 = 把「已修代码树」和「修复前的失败结论」绑在一起（伪造，不是刷新）。顺序只能是：**先有一次干净的当前代码回归 → 再快照**。
