# D4.8 逐图生成、异常与恢复界面证据

> EVIDENCE-SNAPSHOT: current · NOT-AUTHORITY

## 结论

D4.8 已完成。生成态现在呈现两个真实阶段（准备/提交、逐图生成），正常生成由界面**自动轮询**逐图更新，不再要求用户手动点“核对”：只有 `UNKNOWN` 的尝试才显示“核对当前生成状态”，且核对只按原 provider task id 查询、不重新提交。局部失败保留成功图并只提供“重新生成这张”；欠费、限流、凭据缺失等错误显示可执行的修复指引。刷新与服务重启后状态从工作空间恢复，付费提交次数不变。

## 实现结果

- 新增正式端点 `POST /api/attempts/{action_id}/reconcile`（body `{directory}`），复用应用层 `reconcile_generation`，只查询已持久化的原任务；批量 `POST /api/generation/reconcile` 保留为兼容别名。
- 前端自动轮询（4 秒）只覆盖 `SUBMITTED`/`RUNNING` 且带原 provider task id 的尝试；`UNKNOWN` 保持人工核对（按钮只在这些状态下出现）；编辑中（资料/方案未保存或提示词抽屉打开）暂停渲染，避免自动刷新覆盖用户输入。
- 阶段反馈：生成中标题为“逐图生成中 · x/n 张已有候选”，状态行为“逐图生成中：x/n 张已有候选，自动更新。”；全部终态后为“整套生成已结束：x/n 张有候选。”
- 失败指引（`error.title` 保留原始错误）：`UPSTREAM_ACCOUNT_ARREARS` → “百炼账户欠费：充值后再点『重新生成这张』；系统不会自动重复提交。”；`UPSTREAM_RATE_LIMITED` → “上游限流：稍等片刻后再点『重新生成这张』。”；`PROVIDER_API_KEY_MISSING` → “图片模型凭据缺失：配置 API Key 后再生成。”
- 局部失败重试沿用 `/api/generation/rework`，只对目标 Shot 新建 Attempt；其他 Shot 的 Attempt 与候选保持不变。

## 本次发现并记录的真实边界

- 候选记录的主键是图片内容摘要（`candidate_id = sha256(bytes)`），因此**两个不同 Shot 若生成完全相同的字节**，第二个会被“保护候选来源”判定为重复候选并记为 `FAILED`（提示“这张图片与已有候选完全相同”）。真实模型下概率低，但这是当前设计的真实边界：浏览器验收第一次因此失败（两个假任务用了同一张固定字节 PNG），夹具改为每任务不同颜色后才通过。是否按 Shot 命名空间化候选主键，留待 D4.12/D4.14 审计评估，本轮不擅自扩大改动面。
- “自动轮询”只做查询：任何路径都不会在 `UNKNOWN`、无 task id 或预算/凭据拒绝时自动重提。

## 关键浏览器观测值

- 混合轨迹渲染：`['生成中', '生成失败', '结果待核对']`；失败图 1 个“重新生成这张”；存在 Unknown 时“核对当前生成状态”可见。
- 自动轮询：不点任何按钮，浏览器自行发出 `POST /api/attempts/act_…/reconcile`；`resolve` 完成后 RUNNING 自动变“已完成”，候选图自动出现；提交次数保持 3。
- Unknown 核对：手动核对后状态变“已完成”，提交次数仍为 3（只查不重提）。
- 欠费：`.generation-error` 显示“百炼账户欠费：充值后再点『重新生成这张』…”；再次重试成功后提交次数 5，前/后无关 Shot 的 Attempt 数与候选摘要完全一致。
- 刷新与服务重启：三张图全部“已完成”，提交次数保持 5，无新的 reconcile 重放。
