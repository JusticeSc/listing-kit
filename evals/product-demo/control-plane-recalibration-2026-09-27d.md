## 1. 触发与审计结论

产品发起人对 FE-08 的实际走查反馈是：当前界面仍在刻意证明 Mock 能跑，而不是把一个真实业务
工具在“后端暂由 Mock 代替”的情况下呈现出来。该反馈推翻的是 v1.20 的前端产品形态，不是
Mock service、状态机、提示词版本、候选保留、单图返工和异常轨迹这些工程能力。

回看计划与页面后，最早断点位于**交互合同**：旧合同要求固定 Aster 输入、永久三栏、常驻状态/
责任信息、用户逐项处理 F1–F8，并把重置与场景切换放进业务页面。实现忠实投影了这个合同，所以
页面自然成为工程测试台。继续润色 CSS 或补按钮只会强化错误模型，不能修复产品形态。

## 2. 裁定

1. v1.20 的 `D2.R1b` 与 `D2.R1c` 状态改为 `superseded`。产物仍是有效历史证据，但不再是
   后续走查和 Phase 3 的产品规格。
2. Aster 01 继续作为 Phase 2 的确定性验收 fixture；界面能力不再被描述为“只能打开内置杯子”。
   生产形态资料入口允许添加、替换和排序商品图。Phase 2 对非 Aster 资料不伪造生成结果，而是
   明确“资料可接入，但当前离线候选只有示例商品”。
3. 单页改为 `INTAKE → PLAN → REVIEW → DELIVERY` 的渐进任务工作区。当前阶段占主区，已完成
   阶段折叠为摘要，未来阶段不提前摆空控件；这仍是同页单人自签，不是多页向导。
4. F1–F8 是系统检查与验收依据，不是普通用户必须逐项打表的日常流程。正常候选只显示简短
   “未发现阻塞”；发现风险才显示具体事实、证据和处理动作。完整证据与提示词都放高级区。
5. Mock 边界改为任务头低干扰徽标、候选来源和导出清单标识。重置、制造失败、Unknown 场景
   切换移出业务界面，只从启动参数、测试 API 或独立测试入口注入。
6. 新主链为 `D2.R1 → D2.R1d → D2.R1e → D2.R1f → D2.R2 → D2.R3`：先确认生产形态
   视觉稿，再改正式入口，再由产品发起人复验，最后才找未参与者走查。
