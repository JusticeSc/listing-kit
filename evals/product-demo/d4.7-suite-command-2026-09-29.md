# D4.7 一键整套编排证据

> EVIDENCE-SNAPSHOT: current · NOT-AUTHORITY

## 结论

D4.7 已完成。正式入口现在有两条清晰路径：S1「生成整套图片」用**一个**带 `action_id`/`expected_etag` 的写命令完成“保存当前资料 → 编译缺失或过期的 Brief/Plan/Prompt → 创建唯一 GenerationBatch”；S2「先看方案」只编译并停在方案页，不创建批次、不调用图片模型。前端不再把多个写请求串成“一键”，旧的分步按钮（分析商品、生成方案、开始生成）已退出正式导航。

## 实现结果

- 新增应用命令 `prepare_suite` 与 `generate_suite`。`generate_suite(directory, expected_etag, action_id, intake=None)` 在持有有效 Intake 时自动编译并持久化 Brief/Plan/Prompt，然后创建批次；`action_id` 同时作为批次标识来源与图片提交的幂等键。
- 新增 `generation_batch` 契约（`contracts/product-v1.schema.json` + `src/product_v1_contracts.py`），记录 `schema/id/workspace_id/action_id/created_at/plan/shots`，每个 Shot 指向本批次的 `attempt_action_id`；批次状态由投影派生，不落冗余字段。
- HTTP 层新增 `POST /api/plan/compile`、`POST /api/generations`、`GET /api/generations/{id}`；两个 POST 同时接受 multipart（S1 内联保存表单）与 JSON（S2 携带 `expected_etag`）。
- 重复 `action_id` 返回同一批次并带 `replayed: true`，不重复提交图片；`prepare_suite` 对已就绪的套图零图片调用、零批次、不进入 `GENERATING`。
- 前端：S1 页脚为「先看方案」（次）+「生成整套图片」（主）；S2 页脚为「保存方案调整」+「按此方案生成」；`action_id` 按工作空间目录保存在 localStorage，失败重试复用同一 id，提交成功后清除。

## 本次发现并修复的真实缺陷

1. **批次文件写入与读取不一致**：`src/workspace_store.py` 读取 `generations/batch-*.json`，写入却是 `batch_<sha>.json`（下划线），导致 `202` 成功后投影看不到批次、磁盘列表为空。改为 `batch_*.json` 后恢复。
2. **Plan 版本号冲突**：`_generate_product_plan` 按 plan id 局部取版本，而存储层按全 kind 全局递增；Brief 重编译产生新 plan id 时触发 `WorkspaceCorrupt: workspace.current.plan does not match the record`。改为对 `list_records("plan")` 全局取 max + 1。
3. **验收脚本自身的导航竞态（非产品缺陷）**：`tools/verify_product_v1_usability_accessibility.py` 的 `open_workspace` 在第一次 boot 尚未读完 sessionStorage 时就覆盖并 reload，boot#1 会先读到新目录、失败后按产品逻辑清掉 key，reload 后的页面于是停在首页无提示。改为先等 `networkidle` 再写 key 后 reload；同一场景单独复现时产品提示一直正常（“此文件夹中没有可打开的商品工作空间。”）。
