# D2.5 传输接线缺陷与真实提交探针 - 证据

- 日期：2026-09-28
- 范围：`src/providers/dashscope_image.py` 的默认传输接线、离线回归、单次真实提交探针
- 结论：正式图像 Provider 的真实网络提交路径此前无法建立任何 HTTP 调用；已修复并有新鲜真实证据

## 1. 缺陷与表现

- 现象：2026-09-28 21:09 的第一次真实整套运行为每张图留下一条 `UNKNOWN` attempt，且都没有 provider task id；按合同不自动重提，工作空间因此停住。
- 根因：`DashScopeImageProvider.__init__` 默认装配模块级函数 `_requests_transport`，但调用点按对象协议执行 `self._transport.request(...)`；函数没有 `.request` 属性，真实提交在发请求之前就抛 `AttributeError`。
- 为什么此前没被发现：离线校验一直注入带 `.request(...)` 的 `FakeTransport`，从未覆盖“不传 transport 的默认路径”；服务层把该异常按通用异常记成 UNKNOWN（`提交结果暂时无法确认`），外观像网络未知。
- 影响：正式入口“一键真实出图”此前一次网络请求都没有发出；21:09 的 5 条 UNKNOWN 不是网络丢包，也没有产生计费。

## 2. 修复

- `src/providers/dashscope_image.py`：新增 `_CallableTransport` 适配器与 `_coerce_transport()`；`None` 走默认适配器，对象协议直接使用，可调用对象自动适配，两者都不是则拒绝；`__init__` 改为 `self._transport = _coerce_transport(transport)`。
- `tools/verify_dashscope_image_provider.py`：新增回归 `test_default_and_callable_transports_are_both_wired`（默认 transport 必须暴露 `.request`；函数式 transport 必须能完成一次 submit，且请求体真的携带参考图 data URI）。

## 4. 边界

- 探针只证明“提交 + 按原 id 核对”通道恢复，不代表整套生成完成；整套证据见 `d2.5-real-generation-*.md`。
- 21:09 的 5 条假 UNKNOWN 保留在 `real-run-01` 作为历史轨迹，不再用于交付；真实交付走 `real-run-02`。
