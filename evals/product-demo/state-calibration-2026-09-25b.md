**一处计划与实现不一致（需产品决策，本轮只登记不改）**：计划 §4.3 明文写「v2 基线身份只覆盖后者」（`config/ src/ tools/ web/ run.py requirements*`），而`tools/snapshot_v2_baseline.py` 的 `source_files()` **额外**把整个 `evals/**/*.py`也算进身份。后果恰好是计划想避免的那件事：**修一个控制面探针，基线就报「代码树身份已变化」**。而这次唯一的源码变化正是那个探针 —— 按计划口径，「v2 legacy 未被改动」其实仍然成立。

## 9. 复核 G-1 的一条判据：Goal objective ≡ 计划 §2

G-1 判据原文含「其 objective 与 §2 逐字相等」。这条**离线守卫守不住**：
`tools/check_project_state.py` 只能校验 goal_id 绑定，读不到 Goal 的文本。
所以本轮用会话记录里的原始 JSON 复核了一次。

| 项 | 值 |
|---|---|
| 来源 | `C:\Users\31368\.codex\sessions\…\rollout-2026-09-23T16-30-37-…_.jsonl` |
| 该 Goal id 在文件里出现的次数 | 11 次，其中 **2 种** objective |
| 旧 objective（Product V1 版） | 2026-09-23T09:08:22Z · sha16 `171f018c479ba3ad` |
| **当前 objective（演示产品版）** | **2026-09-24T03:47:35Z（= 11:47:35 +08:00）· sha16 `0bcf762f3e9dd7fb`** |
| 计划 §2 引用块 | 4 段；去掉排版后与 objective **逐段逐字相等** |
| 结论 | **该判据成立**，且 Goal 文本自 2026-09-24T11:47:35+08:00 起未再变 |

**取法上的教训（本轮踩到）**：同一个会话文件里既有旧目标又有新目标，
所以「按文件 mtime 取最新」和「取第一条命中」都会拿到**旧的** objective ——
第一次比对就是这样得出「不相等」的假警报。正确取法是**同一文件里最后一次出现**。
这条与 §2 同型：**「哪一条才是当前」不能靠时间戳或出现顺序猜，要有明确的取法。**

**另一处差异不是漂移**：objective 原文段间是单个换行，计划 §2 用空引用行分段。
逐字层面无差异，差的只是段间分隔的表示法。已把 §2 引言写准，
免得下次有人按字节去比而误判成漂移。

复核脚本在 `_stage-amz-control/verify_goal_text_matches_plan.py`（**项目外**：
它要读 Codex 的会话存储，装进 `tools/` 会让项目依赖本机会话目录）。
因此这条判据仍然**只能人工/外挂复核**，不能在离线回归里守 —— 这是它的已知边界。
