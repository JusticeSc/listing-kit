## 1. 制定计划时的实现基线

### 1.1 已有能力

当前项目已经具备可复用的工程基础：

- Windows 本地浏览器审核台，入口为 `web/server.py` 与 `web/index.html`；
- 商品包读取、齐套检查、计划预览、后台执行和进度查询；
- 当前七坑位渲染、确定性检查、候选版本展示、采纳、三层重做和导出；
- `plan.json`、`run.jsonl`、原始文件和导出清单组成的可追踪文件链；
- 商品事实、数据策略、人工审核合同及相应验证工具；
- 文档权威、执行状态、回归和反向探针组成的项目控制面。

这些能力是迁移资产，不等于新 Goal 已经完成。

### 1.2 最早的能力断点

当前 `src/imagegen.py` 只向百炼发送文本，正式渲染路线是“模型生成背景 + 本地贴入商品主体”。它不能证明：

- 模型真实读取商品参考图；
- 模型直接生成的完整场景图保持商品外观；
- 系统能以可版本化的完整提示词驱动参考图生成；
- 陌生使用者能够从商品资料独立完成整组候选的计划、生成、返工与导出。

因此，第一条实施切片必须先验证参考图生成，而不是先扩展完整界面。

### 1.3 2026-09-26 设计重新基线

首轮真实 I2I 已证明参考图真实进入模型且四张候选均有人工保留价值，但也暴露出原设计把
“商品事实必须保持”过早收敛成“`cylinder-v1` 必须自动判完 F1–F8”。进一步复核确认：

- 旧 v2 的 BiRefNet/rembg 抠图没有接入新场景候选检查；当前 `product_check.py` 实际使用的是颜色阈值掩膜；
- Bex 02 第二商品由规格确定性绘制，再由同一横向色带协议量测，只证明协议内可配置，不证明跨品类或真实场景通用；
- 已知负样本中的文字和扁平杯盖仍会机器放行，故 P2 只能证明部分能力与已登记缺口；
- “同意继续交付”不能替代对“无文字/水印”这一具体事实的显式人工签字；
- “四张至少两张机器通过”与五步界面、完整事件存储均是设计假设，不是用户原始需求。

因此 v1.4 保留真实 I2I、预算/幂等/Unknown、候选不可覆盖、提示词版本和人工最终选择，
撤销“单一确定性事实门就是通用方案”的假设。后续先比较模型分割、参考图条件视觉判断和
混合验证路线，再用离线候选走通用户垂直切片；只有观察到真实状态需求后才固化最小持久化架构。

### 1.4 2026-09-26 生命周期与处理设计校准

当前不是“需求尚不清楚”，也不是“已经进入完整产品施工”。已经足以冻结的，是演示对象、
目标用户、核心任务、真实 I2I 路线、成本红线和完成边界；仍需验证的，是各处理环节能否在其
适用前提内稳定地产生可判定结果。因此当前生命周期定位为：

> **方案可行性验证与设计收敛阶段** —— 用冻结样本和离线垂直切片，证明关键机制并冻结处理合同；
> 完成后才进入最小产品核心实现。

进入产品实现前必须同时满足：

- 每个关键环节都有明确的输入权威、处理机制、成功输出、拒绝/失败/Unknown 和人工接管；
- 真实 I2I 与事实验证责任链分别有证据，不能用“图片好看”替代事实，也不能用分割结果代表商品身份；
- 离线 tracer 证明陌生人能理解默认方案、提示词、候选、返工、选择和导出；
- 领域对象、页面和持久化边界来自上述证据，不从一张静态流水线图反推。

这次校准不改变 §2 Goal objective；它改变的是达成路径和证据顺序。

## 3. 产品完成合同

### 3.1 目标使用者与任务

目标使用者是了解自己商品、但不会写专业生图提示词、也不熟悉模型和 API 的首次使用者。

代理任务：

> 为虚构 `Aster 01` 保温杯准备一组 Amazon US Listing 图片候选。采用系统默认建议开始生成；检查候选，保留可用图片；选一张不满意的图片说明原因并单独重做；逐图作出最终选择并导出交付包。

允许产品内提供平台与业务判断说明，不允许开发者在旁指挥点击顺序、解释内部术语、代改文件或代恢复状态。

### 3.2 必须、可以、禁止

**必须：**

- 给出完整默认计划、视觉方向、每张图片的目的、参考图、提示词和理由；
- 图片数量由计划和已知事实决定，不由固定七张决定；
- 至少包含一张可检查的白底主图候选、一张模型直接参考商品图生成的场景图候选，以及一张表达可见结构或事实的补充图；
- 每次生成绑定商品事实版本、参考包版本、计划版本、提示词版本、模型参数和候选文件哈希；
- 事实底线先于审美选择；事实硬失败候选不能被选入最终交付；
- 旧候选不可覆盖；单图返工只影响对应 Shot；
- 超时或外部结果不确定时记录 `UNKNOWN`，核对原任务后才能决定是否重试；
- 导出只复制已选且允许导出的候选，并产生可读说明与机器清单。
- 同一名操作者在一个任务工作台内完成资料确认、方案确认、整套生成、逐图审核/返工和导出；
- 主路径是一键生成计划中的整套图片，单图操作只用于查看、调整、选择和定向返工；
- 输入区说明商品图、卖点、参考链接和平台如何进入任务；系统默认增强并编译方案与提示词，用户可手动调整。

**可以：**

- 用户直接接受默认方案；
- 用户用业务语言调整场景、构图、视觉方向和允许改变项；
- 高级用户查看、编辑、比较或恢复完整提示词版本；
- 系统对视觉方向、场景和返工原因提出模型建议，但建议不自动成为事实或选择。

**禁止：**

- 将纯文生图背景、本地贴图或 mock 输出标成参考图生成；
- 生成成功后自动选中候选；
- 让提示词编辑绕过商品事实、平台硬规则、模型调用预算或人工最终选择；
- 把模型自评、接口成功或局部测试通过当成图片可用与产品完成；
- 使用未经参考板支持的容量、材质、性能、认证或绝对化卖点；
- 为得到偶然好图无限增加调用次数。

## 4. 目标架构

采用 Windows 本地模块化单体，不引入微服务或多 Agent。浏览器只呈现状态，Python 后端掌握规则与写入权。
系统不是单向流水线，而是“提出方案 → 验证 → 人工决策 → 定向修订”的受控闭环：

```text
浏览器任务工作台（最终步骤数由 Phase 2 走查决定）
  → 素材与 ProductFacts（来源、未知、人工确认）
  → Plan / ShotSpec / StyleSpec 方案提议
  → 规则校验 + 用户确认 PlanVersion
  → Prompt 编译 / 可见编辑 / PromptVersion
  → Permission / Budget / Duplicate Gate
  → Qwen I2I Adapter → Attempt Observation / Reconcile
  → Candidate Store
  → 文件与平台检查
  → 逐事实验证路由
       ├─ 确定性规则
       ├─ 参考图条件视觉判断
       ├─ 可选分割/检测/局部匹配证据
       └─ 显式人工事实确认
  → 人工审美判断 keep / redo / reject
       ├─ redo → 按原因只修改对应 Shot/Prompt/参考图/确定性处理
       └─ keep → 人工 Selection
  → 确定性文案与版式合成（需要精确文字时）
  → 对最终文件重跑技术/平台检查
  → Immutable OutputVersion

SQLite 状态库 + 内容寻址文件库
```

### 4.1 权威对象

```text
DemoProduct
  └─ FactsVersion
      └─ ReferencePackVersion

Task
  └─ PlanVersion
      └─ ShotSpec + StyleSpec
          └─ PromptVersion
              └─ GenerationAttempt
                  └─ Candidate
                      ├─ VerificationResult
                      ├─ VisualReview
                      └─ Selection

Selection set
  └─ CompositionVersion
      └─ OutputVersion
```

| 对象 | 稳定身份 | 责任 |
|---|---|---|
| DemoProduct | `product_id` | 虚构演示商品与免责声明 |
| FactsVersion | 内容哈希 | 可见事实、来源和未知字段 |
| ReferencePackVersion | manifest 哈希 | 模型参考图、角色、顺序和文件哈希 |
| Task | `task_id` | 一次完整图片交付任务 |
| PlanVersion | 内容哈希 | 动态图片计划、共享视觉锁和依赖 |
| ShotSpec | `task_id + plan_version + shot_id` | 单张图的业务目的、允许变化、必须保持、参考图角色、构图与验收要求 |
| StyleSpec | 内容哈希 | 多张图共享的视觉方向；是可编辑约束，不是事实来源 |
| PromptVersion | 内容哈希 | 实际发送的完整提示词及父版本 |
| GenerationAttempt | `action_id` | 一次可能收费的外部调用及最终或未知状态 |
| Candidate | `candidate_id + file_hash` | 不可覆盖的模型或确定性候选 |
| VerificationResult | `verification_id` | 逐事实记录责任者、前提、证据及 pass/fail/unknown，不包含审美结论 |
| VisualReview | `review_id` | 人工 `keep / redo / reject` 及具体视觉理由，不改写事实判断 |
| Selection | 事件身份 | 人工采用关系，不修改 Candidate |
| CompositionVersion | 内容哈希 | 已选视觉底图与精确文案/版式资源的确定性合成结果；无文案时也记录恒等合成 |
| OutputVersion | manifest 哈希 | 通过最终文件复检的一组不可变交付包 |

本节定义的是语义身份和追溯边界，不等于首版必须一对象一张表。物理持久化按 §6.12.0 收缩：
只有具备独立写入、版本、恢复或外部动作身份的对象单独保存，其余先作为不可变快照嵌入。

### 4.2 状态边界

**Task：** `DRAFT → READY → RUNNING → REVIEW → COMPLETE`，另有 `BLOCKED / FAILED`。

**Attempt：** `PREPARED → SUBMITTING → SUBMITTED → RUNNING → SUCCEEDED / FAILED / UNKNOWN`。

**Candidate：** `CREATED → CHECKED → KEEP / REDO / REJECT`；`KEEP` 仍不等于已选。

**Shot：** `PLANNED → GENERATING → REVIEWABLE → SELECTED`；依赖变化后转 `STALE`，不删除历史。

`UNKNOWN` 不是失败。原调用身份没有核对前，不得创建相同请求的新 Attempt。

### 4.3 存储与兼容

- SQLite 使用本地磁盘、WAL 与单写者约束，先保存当前权威状态、付费动作、候选、选择和必要审计事件；不预设全量事件溯源；
- 原始参考图、请求快照、候选和导出物以不可覆盖文件和哈希登记保存；只有重复存储成本被真实观察后才引入通用内容寻址层；
- 当前 `plan.json` / `run.jsonl` 保留为历史证据；legacy reader 不在新产品关键路径，是否实现由发布阶段的实际演示需要决定；
- 新产品不提供旧“背景生成 + 本地贴图”正式运行入口；旧代码保留仅用于历史回归或安全恢复，不能进入完成证据；
- 项目没有 Git 版本安全网，改动既有关键文件前继续使用项目外备份，并记录恢复入口。
- 新演示产品的代码根为 `demo/`，与冻结的 v2（`config/`、`src/`、`tools/`、`web/`、`run.py`、`requirements*`）分开；
- v2 基线身份还纳入 `evals/**/*.py` 中的既有判据源码，但不纳入生成报告和图片。原因是 v2 的回归结论依赖这些判据；改判据也必须使基线身份变化。新增 `demo/` 代码与 `evals/product-demo/` 产物不进入该身份；旧 v2 入口不进入新产品正式路径。

### 4.4 全链路处理合同

以下合同规定“每一环怎样处理”，不是 UI 步骤数。模型只负责提出候选或证据，任何模型输出都不能未经验证直接写成权威事实、最终选择或已交付结果。

| 环节 | 输入及权威 | 处理机制 | 成功输出 | 拒绝 / 失败 / Unknown 与人工接管 | 验收证据 |
|---|---|---|---|---|---|
| PC-01 素材接入 | 用户选择的商品包；manifest 和文件哈希是资产身份权威 | 校验存在性、格式、尺寸、哈希、角色和外发政策；只读解析，不改原图 | `ReferencePackVersion` + 齐套报告 | 缺失/漂移为业务拒绝；读图异常为技术失败；角色不明为 Unknown，要求用户确认 | 正反夹具、哈希报告、无写入证明 |
| PC-02 ProductFacts | 用户/规格文件是非视觉事实权威；参考图只证明可见事实 | 抽取候选事实并逐项标注 `source/evidence/confidence/confirmed_by`；材质、容量、功能不得仅看图定论 | `FactsVersion`，每项为 confirmed / unknown | 来源冲突则阻断相关 Shot；不可证实保持 Unknown；用户逐项确认关键事实 | schema、冲突样例、事实来源链 |
| PC-03 图片计划 | FactsVersion、平台规则和用户目标为硬输入；范例仅供提案 | 模型或规则提出 ShotSpec；确定性校验必需图、无依据卖点、参考图需求和预算；用户确认 | 不可变 `PlanVersion` + 每张图的目的和理由 | 不支持的声明拒绝；信息不足返回补料/删 Shot；不得用固定七张补空位 | 同输入稳定性、无依据声明反例、用户确认记录 |
| PC-04 视觉方向 | 已确认事实和用户偏好；参考范例是风格证据而非商品事实 | 形成共享 StyleSpec，区分可变审美和不可变 FactLocks；用户可接受或调整 | `StyleSpec` + 适用 Shot 集合 | 风格与商品事实/平台规则冲突则拒绝；偏好不明可用默认并明确可改 | 风格差异、冲突反例、版本哈希 |
| PC-05 提示词 | ShotSpec、StyleSpec、FactLocks、provider capability | 确定性编译固定事实块与可变镜头块；展示的完整文本就是实际发送文本；编辑产生新版本 | `PromptVersion` + 编译输入哈希 + diff | 删除硬事实锁时阻断或显式确认；编译错误不回退空提示词；文字措辞不被当作保真保证 | 黄金编译测试、编辑/撤销、发送体比对 |
| PC-06 生成提交 | PromptVersion、有序参考图、模型配置、预算与外发许可 | 请求前校验 I2I 端点、图像字段/顺序/哈希、action id、重复与预算；只由正式 adapter 提交 | `GenerationAttempt(SUBMITTED/RUNNING)` + 原始请求证据 | 无 key/越预算/非 I2I 为拒绝；网络/协议为失败；提交结果不明为 UNKNOWN，不自动重发 | 请求哈希、provider task id、账本、守卫反例 |
| PC-07 结果核对 | Attempt 身份和 provider task id | 轮询原任务；验证响应归属、下载文件、哈希与可解码性；先落原始响应再晋级 | 不可覆盖 `Candidate` + `SUCCEEDED` Attempt | provider 明确失败记 FAILED；无法确定终态记 UNKNOWN；下载失败保留 task id 后恢复 | 超时/响应丢失/重启轨迹，同 action 不重复 submit |
| PC-08 技术检查 | Candidate 原文件与平台配置 | 确定性检查解码、尺寸、格式、色彩、文件大小及适用的平台形态 | `VerificationResult` 的确定性项目 | 规则命中可 fail；规则不适用必须 Unknown，不得借审美覆盖 | 边界值和反向样例、可重复结果 |
| PC-09 商品事实验证 | Candidate、参考图、FactsVersion、逐事实 capability contract | 为每项事实选择规则、参考图条件视觉判断、可选分割/检测/局部匹配或人工；分割只定位，不证明同一 SKU | 逐事实 pass/fail/unknown + 证据与责任者 | 未校准模型默认 risk/needs-human；前提不成立为 Unknown；关键 Unknown 必须人工确认或阻止选择 | 冻结正负样本对照、误报漏报与 Unknown、人工签字 |
| PC-10 审美审核 | 通过或已明确处理事实风险的 Candidate；ShotSpec/StyleSpec | 人比较候选，从构图、层级、光线融合、材质感、背景干扰和商业完成度选择理由 | `VisualReview(keep/redo/reject)` | 不伪造总分；审美 keep 不能覆盖事实 fail/unknown | 多候选对照与理由记录 |
| PC-11 返工路由 | VerificationResult、VisualReview、原 ShotSpec/Prompt/参考图和旧候选 | 先分类原因，再只改对应变量：技术形态→确定性修复；场景/构图/光线→ShotSpec/Prompt；身份结构→参考图/模型/编辑路线；精确文字→版式层；未知→人工 | 新 ShotSpec/Prompt/Attempt 或确定性修复版本；旧候选保留 | 原因无法归类不自动重跑；超过预算阻断；不得用堆否定词处理身份失真 | 单变量 diff、未受影响 Shot 哈希与 submit=0 |
| PC-12 选择与精确合成 | 人工 Selection、已确认文案、版式规格、已选 Candidate | 用户显式选择；精确文案/标注由确定性排版合成，不交给生图模型拼字；生成 CompositionVersion | 不可变 `Selection` + `CompositionVersion` | 事实硬失败/关键 Unknown 不可选；排版溢出/字体缺失为失败；不自动换候选 | 选择事件、像素/资源哈希、长文与溢出反例 |
| PC-13 最终复检与导出 | CompositionVersion、PlanVersion、平台与导出规则 | 对最终文件而非中间候选重跑技术/平台检查；校验计划覆盖、选择唯一性、manifest 与免责声明 | `OutputVersion` + 人读说明 + 机器清单 | 任一最终文件失败则不发布该 OutputVersion；重导创建新版本，不覆盖旧包 | 换目录 verify、篡改反向测试、完整清单 |

### 4.5 跨环节不变量

- 候选不等于结果；模型建议不等于事实；`keep` 不等于已选择；选择不等于已导出。
- 用户/规格是非视觉事实权威；视觉模型只能提出可见事实证据，不能凭图确立材质、容量、功能或认证。
- 分割回答“提示对象大致在哪里”，不回答“它是否为同一 SKU”；位置、中心和类别形状只能作为弱证据。
- 未完成样本校准的模型判断不得直接 hard pass/hard fail；允许拒绝回答并输出 Unknown。
- 精确文字、尺寸标注和版式由确定性合成负责；生图模型只生成适合的视觉底图。
- 返工必须保留旧候选、说明原因、只改变必要变量；不存在无界自动重试。
- 导出检查必须针对最终合成文件重跑，不能沿用中间 Candidate 的绿灯。
- **不许自证**：为满足某个判据的前提而人为制造出来的输入，不得反过来充当该前提成立的证据。
  适用性必须在真实输入（原图、原候选、原请求）上判；在制造出来的中间产物上重探前提，
  只能作工程卫生检查，且必须显式标注它不是证据。

### 4.6 目标模块布局与「换商品」的边界

目标形态。标记「已有」的今天就存在，其余是后续任务的落点：

| 层 | 路径 | 职责 | 换商品时是否改动 |
|---|---|---|---|
| 合同身份 | `demo/contract/`（已有） | §4.2/§4.4/§9.1.1 的机器镜像与守卫；只核对身份，不复制正文 | 不改 |
| 处理链 | `demo/core/`（前半链已有） | PC-01–PC-13 的实现：素材、事实、计划、风格、提示词、提交、核对与后半链 | 不改 |
| 商品数据包 | `demo/fixture/<sku>/`（已有；名字来自 Phase 0） | 事实卡、阈值推导、提示词 profile、事实验证路由计划、人工裁决记录 | **换商品只加这一层** |
| 可替换验证器 | `demo/verify/`（D1.R3 起） | 每个验证器声明：适用前提、能判哪些事实类型、结论域、证据形态 | 不改（新增验证器 = 新增插件 + 数据声明） |
| 执行适配器 | `demo/provider/`（已有） | 百炼 I2I 的提交、轮询、下载、能力契约与 doctor；上层只经 PC-06/PC-07 调用 | 不改；换模型 = 换 adapter + 改能力声明 |
| 夹具工具 | `demo/fixture/*.py`（已有） | 事实卡校验、量测、冻结、负样本与商品包工具；不是产品运行路径 | 可加新工具；不进入正式运行链 |
| 冻结参考包 | `evals/product-demo/fixture-design/pack/`（已有） | 有序参考图与 manifest，只读资产 | 加新包，不改旧包 |
| 本地产品 | `app/`（Phase 2 先做技术 tracer 与单页 mock，Phase 3 起接权威状态） | 本地 store、本地 server、浏览器界面；只渲染权威状态 | 不改 |
| 证据 | `evals/` | 时点产物与报告 | 不改 |

三条由此产生的硬规矩：

1. **商品身份与逐商品资产位置只能来自商品数据包**，不得由 `demo/core/`、`demo/verify/`、`app/`、
   `demo/provider/` 的代码自行认定。入口接受商品 id 或包路径，模块常量只能作**调用时**的默认值。
   三种可证伪形态，少写一种就会有一种缺陷在守卫全绿时改掉结论（§1.9 是实测反例）：
   - **商品名字面量**：`rg -n 'aster-01|bex-02' demo/core demo/verify app demo/provider --glob '*.py'` 必须零命中；
   - **导入时焊死默认包**：产品层不得出现顶格的 `X = <包模块>.default(...)`；默认值只能在函数体里解析；
   - **旧位置形态**：产品层不得按收拢前的老路径（`demo/core/` 下带 SKU 后缀的逐商品文件）读数据 ——
     数据搬了家而代码没跟着搬，会把「阈值缺失」读成「前提不成立」，静默改掉验证结论。
   三者由 `demo/verify/swap_probe.py` 按层判死（产品层 violation；夹具与证据层只记清单）。
   另外，位置一变还要**重跑依赖它的离线验证工具并逐条核对读数**，不能只看守卫是否变绿。
2. **逐商品数据只住 `demo/fixture/<sku>/`，文件名不带 SKU**：目录承载身份，文件承载用途。
   约定文件为 `product.json`、`threshold-derivation.json`、`prompt_profile.json`、`verifier_plan.json`、
   `human_fact_review.json`、`human_visual_review.json`、`fact_capability.json`。
   现状：前两个已就位；其余四份现居 `demo/core/` 且带 `.aster-01.json` 后缀，属**待收拢漂移**，
   由 D1.P4 步骤 0 处理；D1.R1 起的新数据直接写进商品包。
3. **换商品的可证伪判据是「不改 `.py`」**：用第二个商品数据包（现有 `bex-02`）跑同一条链，
   运行前后对 `demo/**.py` 的哈希清单必须逐条不变，新增文件只能是数据与证据。
   本项目不是 git 仓库，回滚依赖工作区外的备份，所以用哈希清单而不是 `git diff`。
   它证明的是「流程与配置解耦」，**不**证明跨品类或真实商品的泛化——后者仍按 §5.1 P4 后置。

硬规矩 1 的检查范围包含 `demo/verify/` 里的离线对照脚本：边界样本与商品路径必须从商品包目录
派生，不能写死 SKU。`demo/fixture/` 的夹具工具可以绑定具体商品（它们本来就是那个商品的夹具），
产品层与验证层不行 —— D1.R2 的对照脚本第一版正是在 `demo/verify/` 里写死了商品名。

### 4.7 用户眼中的业务模型与单页交互契约

内部处理合同有十三环，但用户不是来逐环执行流水线的。用户面对的主对象只有一个：
**商品套图任务**。它把商品输入、整套方案、各图状态和最终交付组织在同一上下文中。

| 用户对象 | 用户需要看到 | 用户可以做 | 后端权威对象 |
|---|---|---|---|
| 商品资料 | 商品图、卖点、参考链接、平台、缺料/冲突 | 补充或修正输入 | DemoProduct、FactsVersion、ReferencePackVersion |
| 套图方案 | 计划图片数、每张用途、视觉方向、预计调用 | 接受默认方案或调整单张方向 | Task、PlanVersion、ShotSpec、StyleSpec |
| 整套生成 | 总体进度、逐图状态、失败/Unknown | 一键生成整套；只重试明确允许的目标图 | GenerationAttempt、Candidate |
| 单图工作区 | 当前图的方案、实际提示词、候选、事实/审美结论、历史 | 改提示词、比较、选定、按原因返工 | PromptVersion、VerificationResult、VisualReview、Selection |
| 交付包 | 哪些图已选、哪些仍阻塞、最终复检与文件清单 | 条件满足后导出 | CompositionVersion、OutputVersion |

单页只保留五个有业务职责的区域，不按内部对象另建页面：

```text
任务头：商品 + 平台 + 当前阶段 + 主动作
├─ 输入区：商品图 / 卖点 / 参考链接 / 缺料与冲突
├─ 套图计划区：所有 Shot 卡片、用途、状态、整套进度
├─ 单图检查器：当前 Shot 的方案 / 提示词 / 候选 / 检查 / 返工 / 选择
└─ 交付栏：阻塞项 / 已选数量 / 导出
```

必要主按钮只有：`生成推荐方案`、`一键生成套图`、`保存提示词新版本`、`选定此图`、
`重做此图`、`导出套图`。添加素材使用输入控件自己的动作，不另造流程按钮。按钮是否出现和是否可用
必须由 Task/Shot 状态、前置条件和权限推导；页面不得靠本地布尔值猜成功。

Mock 前端也必须遵守真实状态转换：输入不齐不能出可执行方案；方案未确认不能生成；生成中输入与方案
不可改；生成成功不自动选择；返工只让目标 Shot 产生新候选并保留旧候选；计划必需图未全部选定或
最终复检未通过时不能导出。Mock 只替代后端执行，不得删减业务对象、状态、失败与反馈。

## 5. 实施阶段

任一时刻最多一个 Phase 为 `active`。只有 Gate 获得当前证据，才能进入下一阶段。

### Phase 1：跑通真实参考图生成能力

**结果：** 最小付费切片验证真实 I2I 的生成价值；先冻结全链路处理合同，再建立不依赖单一手工量测器的事实验证责任链。

**Gate G1：** 请求证据证明参考图真实进入模型、非 mock、身份/参数/原图/用量可追溯；至少一张候选的 F1–F8 均由已声明责任者解析为 pass（可由高置信规则、经对照验证的模型判断或显式人工事实确认组成），没有 Unknown 或硬失败，且独立视觉结论为 `keep`。模型判断不得伪装成确定性规则，人工结论不得从一般性同意推断。首轮四张与累计八张仍是成本上限，不再把“2/4 机器通过”作为业务事实。若现有四张不能形成可信证据链，再决定单变量复验或停止；不得先扩展完整产品。

### Phase 2：先跑离线产品垂直切片

**结果：** 先由产品发起人确认「商品套图任务」的业务模型和单页交互投影，再用不联网不付费的 mock 后端让陌生人完整走通输入、默认方案、一键生成套图、逐图审核、定向返工、选择和导出；观察结果决定最终术语与状态边界。

**Gate G2：** 产品发起人已确认 UI 交互契约与业务模型一致；随后一名未参与开发的人仅凭界面和任务说明完成完整 mock 轨迹。记录其疑问、误操作和需要的培训；据此冻结最小区域、术语、领域对象和状态需求。AI 代理可预演但不能替代真人；mock 后端不得被表述为真实 provider 或完整产品。

### Phase 3：建立最小可恢复产品核心

**结果：** 从已冻结前端合同反推最小服务与数据；Task、Shot、PromptVersion、Attempt、Candidate、Selection 和 Export 可恢复，其余概念先作为不可变快照保存；默认计划与提示词控制可恢复。

**Gate G3：** 把前端从 mock service 切到本地 API 后，页面结构、按钮和状态语义不变；SQLite 与不可覆盖文件保存 §6.12.0 的最小对象；fake provider 覆盖正常、拒绝、失败、UNKNOWN、重复提交和重启恢复；内置商品能得到可解释方案与实际 PromptVersion；编辑创建新版本并只标记目标 Shot 需重生成；不建设通用事件溯源或工作流引擎。

### Phase 4：完成候选、审核与单图返工闭环

**结果：** 真实模型调用进入正式状态机，候选经过事实验证路由和独立视觉判断；返工保留历史且只影响目标图片。

**Gate G4：** 至少一个完整 Task 使用真实 provider 跑至 REVIEW；每项事实展示验证器、证据与 pass/fail/unknown，未解决硬事实不可选择；模型建议无最终接受权；返工前后旧候选存在、未受影响 Shot 的候选哈希和 provider 调用数不变；UNKNOWN 不自动重试。

### Phase 5：完成陌生人可用的产品体验与导出

**结果：** 经 Phase 2 走查确定的任务工作台从导入到导出自解释、可刷新恢复、无技术操作负担；精确文案由确定性合成完成，最终文件重新受检；不预设必须五步。

**Gate G5：** 从全新本地状态打开产品，可完成“选择演示商品 → 齐套检查 → 默认计划 → 生成 → 审核/返工 → 选择 → 导出”；刷新和服务重启不丢任务；导出包换目录后可独立核验；错误页给出业务语言下一步。

### Phase 6：真实首次使用者验收与质量收敛

**结果：** 最终版本首次接触者独立完成代理任务，暴露的摩擦被修复后仍有新鲜验收证据。

**Gate G6：** 一名没有参与开发、此前未使用最终版本的真实使用者，在不接受开发者口头技术指导的情况下完成默认生成、一次定向返工和导出；开发者介入为 0；所有疑惑、误操作和失败均有记录。AI 代理只可用于预演。若验收后修改关键流程，必须由新的首次使用者重验。

### Phase 7：发布候选与完成审计

**结果：** 形成可恢复、可启动、证据匹配声明范围的本地发布候选。

**Gate G7：** C1–C11 全部为 `proven`；当前完整回归、恢复演练、干净启动、导出核验和控制面检查通过；所有必要资产与代码有恢复方式；不支持范围和未证明结论写入产品及交付说明。只有此时才可把 Goal 标记完成。

#### 6.10.1 D1.P3 用冻结样本验证后半链合同

**处理**：把 PC-08–PC-13 实现成一条真能跑、也能被跑红的链：

| 环节 | 输入 | 处理 | 输出 | 允许的结论 |
|---|---|---|---|---|
| PC-08 技术检查 | 候选原文件、平台形态规则 | 解码、尺寸/比例/格式/色彩/大小；只判文件与平台形态，不判商品 | 逐条技术类 `VerificationResult` | pass / fail / not_applicable |
| PC-09 事实验证路由 | 候选、参考图、FactsVersion、验证器能力注册表 | **先判适用性，再选责任者，最后合并**（三步不许并成一步） | 逐事实 `ReviewItem`（责任者 + 证据指针 + 结论） | pass / fail / risk / unknown / needs_human |

| PC-12 选择与精确合成 | 人工 Selection、已确认文案、版式规格 | 精确文字与版式由确定性排版完成；无文案时记录恒等合成 | 不可变 `Selection` + `CompositionVersion` | accepted / business_reject / technical_fail |
| PC-13 最终复检与导出 | CompositionVersion、PlanVersion、导出规则 | 对**最终文件**重跑技术与平台检查，校验计划覆盖、选择唯一性与清单 | `OutputVersion` + 人读说明 + 机器清单 | accepted / fail（该版本不发布） |

#### 6.10.4 D1.R2 离线比较三种验证路线

**输入（全部只读）**：四张场景候选、三张对照视图、七个既有负样本、第二商品的边界样本、
事实卡、`cylinder-v1` 量测器、verifier plan 里的 `applies_when` 声明。

三条路线在同一批输入上对照，机制各自独立：

| 路线 | 机制 | 为什么要有它 |
|---|---|---|
| A 分割后量测 | 先用分割模型把主体从场景里切出来、贴回中性底衬，再复用既有阈值量测 | 给颜色、比例、轮廓这类事实一条可复算的几何读数；换商品要新 profile（代码级配置） |
| B 参考图条件视觉判断 | 把参考图与候选一起交给视觉模型，逐事实问「是否保持」，只输出 `same/different/uncertain` | 给部件、结构、关系这类语义事实一条责任者；换商品只改事实卡与提示词模板（数据级） |
| C 混合 | A 出几何、B 出语义、判不了交人工；不需要新调用 | 两条路线的失效条件不同，合并是唯一不新增成本仍能提高覆盖的做法 |

**处理**：先修掉两处已证缺陷，再在同一批输入上对照三条路线。步骤不可跳、不可并：

| 步骤 | 输入 | 处理 | 输出 | 验收 / 失败路径 |
|---|---|---|---|---|
| R2.0 修量测器的尺寸前提 | `measure_cylinder.py` 的 4×4 降采样 | 让网格掩膜与裁剪区域形状恒等；只对齐形状、不改语义 | 量测器 + 它自己的 `self-test`（形状契约 / 语义不变 / 端到端 / 变异可抓） | 修复前后对全部冻结图逐值相同（含整体结论）；把修复换回旧实现必须让 `self-test` 变红 |
| R2.1 修路线 A 的判据错位 | 原图、分割输出、制造出来的底衬 | 适用性只在**原图**上判；画布读数改标 `self_referential` 且不作证据；画布四周留出真背景，使边框估色有效 | 对照脚本的路线 A | 场景候选必须判 `not_applicable`，既不是 pass 也不是 hard fail；画布探针不得再参与适用性 |
| R2.2 路线 A 全量 | 上述输入 | 分割 → 贴回底衬 → 复用既有量测；结论是否作数由原图前提决定 | 逐图检出 / 漏报 / 误报 / Unknown | 受控底衬图上能拦住已知负样本；场景候选上机器覆盖为 0，一律记 Unknown |
| R2.3 路线 B 全量 | 参考图、候选、逐事实问句 | `qwen-vl-max` 同时看参考图与候选，逐事实答 `same/different/uncertain`，映射成 `keep/risk/unknown` | 逐图事实结论 + 调用账本 | 只报 risk，不默认 hard 判；每次调用记 action id、请求哈希、用量与终态；没有开关就不发请求 |
| R2.4 路线 C 合并 | A 的几何、B 的语义、人工兜底 | 合并规则，不新增调用 | 逐图合并结论 | 判不了的事实必须落到人工，不能被 A 或 B 顶上 |
| R2.5 报告 | 上述全部 | 逐图写下「哪条路线在哪类事实上不可用」以及原因（前提不成立 / 覆盖不到 / 判不了） | 对照报告 + 本计划与 state 的必要修订 | 同一批输入、同一份事实定义；结论指向具体图与具体事实，不写「哪个模型更好」这类感受 |

**成本口径**：见 §10，本节不重复数值；R2.3 是唯一付费步骤。

**验收**：结论必须写明「哪条路线在哪类事实上不可用」，并给出各自的原因；不得把「不适用」
写成通过，也不得把「没有信号」写成失败。三种原因必须分开陈述：前提不成立、判据覆盖不到、
模型判不了。

**失败路径**：模型不可用时保留未验证，不以手工规则顶替；任一路线不能可靠承担某类事实时，
D1.R3 的责任链把它降为人工，不降低事实标准。

|---|---|---|---|---|---|

**失败路径**：任一路线不能可靠承担某类事实时，降为人工，不降低事实标准。

1. 初始输入不齐；
2. 输入齐全、可生成推荐方案；

4. 整套生成中，逐图显示进度；
5. 部分图片失败或结果 Unknown，其余结果仍保留；
6. 全部候选就绪、等待逐图选择；

9. 全部必需图已选、可导出，以及导出完成。

| 按钮 | 所属对象 | 出现/可用条件 | 业务结果 |
|---|---|---|---|
| 生成推荐方案 | 商品资料 | 最低输入齐全 | 把原始资料变成可检查的整套方案和默认提示词 |

| 重做这张 | 当前 Shot | 已选返工原因、预算允许且没有同 Shot 运行任务 | 只为当前 Shot 产生新 Attempt，保留旧候选 |

前端技术形状固定为 `app/server.py` 继续充当本地入口，新增 `app/static/`：`index.html`、

#### 6.11.5 验收命令与失败路径

| 项 | 内容 |
|---|---|
| 验收命令 | `python app/server.py --offline-fixture demo/fixture/aster-01 --check`：进程起得来、零网络、正式状态零写盘；单页五个区域都能取得数据；完整 mock 轨迹可复位；退出码 0（`1` 自检不通过 / `2` 缺料装不起来 / `3` 端口用不了） |

| 与 Phase 3 的接缝 | 把 mock store 换成 SQLite 与正式 adapter，§4.7 的业务对象、页面区域和动作语义不动；这条接缝就是 D3.R1 的验收对象 |

**外部依赖（唯一需要用户投入、且不可由 AI 替代的一项）**：D2.R2 与 D6.3 都需要一名
**真实且未参与开发**的使用者。它有两个前置条件：提前约定人选；被选者不接受开发者口头的
技术指导。state 已把它登记为 unknown。若到 Phase 2 仍未安排，Phase 2 只能完成预演部分，
Gate 保持未过——这不是可以靠加班补上的工作。

#### 6.11.6 D2.R2 走查包：拆成两段，只有第二段需要真人

D2.R2 的产物不是「通过 / 不通过」的结论（结论属于 D2.R3），而是**一份观察记录**。它此前
只有一行意向，走查者因此拿不到「任务说明」这个东西。拆成两段，是因为第一段不需要等人。

| 段 | 谁能做 | 输入 | 处理 | 输出 | 验收 |
|---|---|---|---|---|---|
| R2.a 准备 | AI 可独立完成 | §6.11.2 的数据来源 + §6.11.3 的单页区域与可见边界 | ①写一页任务说明：只写「打开什么、要得到什么、拿不准怎么办」，不出现命令行、JSON、字段名、对象名 ②写观察记录表，列固定为：时刻 / 当前任务状态 / 他做了什么 / 他说了什么 / 停在哪 / 他问的问题 / 他要找的东西在不在页面上 ③按任务说明预演完整闭环，只记「说明里写的东西页面上找不到」这类缺口 | 任务说明、观察记录表、预演缺口清单 | 任务说明里每一句操作都能在单页找到落点；预演发现的缺口先修，再找人；任务说明不含开发者术语 |
| R2.b 真人 | **不可替代**：未参与开发、此前未用过本项目的人 | 只有 R2.a 的任务说明 | 在单页独立完成输入确认、默认方案、一键整套、一次单图返工、逐图选择和导出；开发者只观察、被问才记录、不口授技术步骤 | 按状态转换的观察记录 | 记录里至少有：他实际做了什么、哪些词他不懂、哪些东西他找了但页面上没有、哪里需要培训；**中途必须靠开发者指路这件事本身就是结论**，如实记下，不重跑充数 |

**找不到人怎么办**：G2 保持未过，按 §7.1 处理。R2.a 可以做完并保留，它是可复用的输入，
但它不是 R2.b 的替代物，也不给 G2 记账。

**一条必须登记的偏差风险**：任务说明由写产品的人写，容易把开发者词汇带进去，而被测的人
正是要检验这些词看不看得懂。缓解办法是 R2.a 的第三项（照说明自己预演一遍，凡说明里出现
而页面上没有落点的词就算缺口），并把这条限制写进 D2.R3 的依据里，不假装说明是中立的。

#### 6.12.0 前端反推后端与最小流水线原则

Phase 3 不再从 §4.1 的概念对象直接生成一表一对象。先冻结 FE-02/FE-07，再为每个界面动作定义
一个最小服务合同；没有页面消费者、恢复用途或验收证据的字段和表不进入首版。

```text
输入快照
→ 计划/提示词编译
→ 按 Shot 顺序提交生成
→ 保存候选并执行适用检查
→ 人工选择或定向返工
→ 最终复检与导出
```

首版持久化对象收缩为：

| 对象 | 为什么必须独立保存 | 最小内容 |
|---|---|---|
| Task | 刷新/重启后恢复同一套图任务 | 输入快照、当前计划快照、总体阶段、更新时间 |
| Shot | 整套进度、单图隔离与导出覆盖都以它为单位 | 用途、顺序、当前状态、当前 prompt/selection 指针 |
| PromptVersion | 用户可编辑、恢复推荐且必须与候选绑定 | 完整文本、父版本、来源、哈希 |
| Attempt | 唯一可能重复扣费或进入 Unknown 的外部动作 | action id、请求哈希、provider task id、状态、错误 |
| Candidate | 旧图不能覆盖，审核与选择都指向它 | 文件、哈希、来源 Attempt、检查快照、人工结论 |
| Selection | `keep` 不等于选中，导出只读人工决定 | Shot、Candidate、操作者、时间 |
| Export | 交付包必须不可变且可复核 | 目录、manifest 哈希、文件清单、复检结果 |

Facts、ReferencePack、Plan、Style、Verification 与 Composition 在首版作为上述对象中的不可变 JSON
快照保存；出现独立编辑、共享、并发或迁移需求时再拆表。这样保留追溯能力，但不把演示产品提前做成
通用工作流引擎。

后端不另造第二套状态词，直接使用 §4.2：Task 只投影 `DRAFT / READY / RUNNING / REVIEW /
COMPLETE` 与异常状态；是否可导出由「所有必需 Shot 已选且最终复检通过」实时推导，不增加
`EXPORTABLE` 状态。Shot 使用 `PLANNED / GENERATING / REVIEWABLE / SELECTED / STALE`；Attempt
保留 `PREPARED / SUBMITTING / SUBMITTED / RUNNING / SUCCEEDED / FAILED / UNKNOWN`。只有真实外部
调用允许 Unknown，普通页面加载或表单错误不用它包装。

界面动作与最小服务合同一一对应：

| 界面动作 | 服务合同 | 成功输出 | 失败/恢复 |
|---|---|---|---|
| 打开任务 | `get_task(task_id)` | 页面所需完整投影 | 读不到显示任务级错误，不构造默认成功 |
| 保存输入 | `update_inputs(task_id, patch)` | 新输入快照 + 校验结果 | 冲突/缺料贴近字段；不改原文件 |
| 生成推荐方案 | `create_plan(task_id)` | 计划与每 Shot 默认提示词 | 缺事实返回可操作问题，不返回空计划 |
| 一键生成套图 | `generate_set(task_id)` | 逐 Shot action id 与进度 | 已成功 Shot 不重跑；重复点击复用同 action |
| 保存提示词 | `save_prompt(shot_id, text)` | 新 PromptVersion + 影响标记 | 事实锁被删则拒绝并指出具体内容 |
| 重做这张 | `rework_shot(shot_id, reason)` | 新 Attempt，旧候选保留 | 原因不明/越预算不提交 |
| 选为成品 | `select_candidate(shot_id, candidate_id)` | Selection | 硬事实未处理或并发冲突则拒绝 |
| 导出套图 | `export_task(task_id)` | Export + 文件清单 | 任一必需 Shot 未选或复检失败则不创建 Export |

Mock service 与真实 service 必须实现同一合同。Phase 3 的验收不是「建了数据库」，而是把
`mock-service.js` 切换为本地 API 后，FE-07 的页面和操作语义不变，刷新/重启仍能恢复同一状态。

#### 6.12.1 本地产品运行时与存储（D3.R1、D3.R2）

**拟定形状**：单进程 Python 后端 + 本机浏览器界面；不引入前端构建链、微服务或多进程写库。

| 环节 | 输入 | 处理 | 输出 | 验收 |
|---|---|---|---|---|
| 入口 | 工作区路径、本地端口 | `app/server.py` 只绑定 `127.0.0.1`；启动即建库建目录；缺 key 或权限时给业务语言提示，不抛堆栈 | 可访问的本地地址 + 健康读数 | 全新工作区能启动；端口占用有明确提示 |
| 数据目录 | 工作区路径 | 拟定 `<工作区>/_local/amz-listing-kit/`：`state.db`（SQLite + WAL）、`files/<sha256>`（不可覆盖原文件）、`exports/`、`logs/` | 可整体搬移的本地目录 | 搬移后任务、候选与导出仍可读 |
| 状态库 | §6.12.0 的七个首版对象 | SQLite 单写者；快照 JSON 保存尚无独立生命周期的概念；界面从不直接写库 | schema + migration | 只建前端合同消费的字段；不做全量事件溯源或通用工作流表 |
| 重启恢复 | 进程重启、刷新、双击 | 未完成 Attempt 先按 §4.2 核对再决定是否重试，不自动重发 | 恢复后的权威状态 | 覆盖正常/拒绝/失败/UNKNOWN/重复提交/响应丢失六条轨迹 |

#### 6.12.2 默认计划与提示词编译（D3.R3、D3.R4）

| 环节 | 输入 | 处理 | 输出 | 验收 |
|---|---|---|---|---|
| 计划编译 | 商品包（事实卡 + 参考包版本）、用户业务选择 | 每 Shot 编译目的、理由、允许变化、事实锁、参考图角色、检查要求与预计调用 | `PlanVersion` + `ShotSpec` + `StyleSpec` | 默认用户不写提示词即可开始；同输入稳定；无事实支持的图型不进计划 |
| 提示词编译 | ShotSpec/StyleSpec + 商品包 `prompt_profile.json` + provider 能力 | 确定性拼装固定事实块与可变镜头块 | `PromptVersion` + 编译输入哈希 + diff | 界面展示文本 == 实际发送文本；编译错误不回落空提示词 |
| 编辑与派生 | 当前 PromptVersion、用户编辑 | 编辑产生新版本；删除硬事实锁则阻断或显式确认；只让真实依赖该 Shot 的下游转 `STALE` | 新 `PromptVersion` + 影响预览 | 历史版本永不覆盖；影响范围与依赖一致 |

| 环节 | 输入 | 处理 | 输出 | 验收 |
|---|---|---|---|---|
| 界面绑定 | 后端权威状态 | 界面只渲染，不本地推断成功；读不到时显示未知 | 页面 + 状态绑定 | 刷新、离开、重启后状态一致 |

### 6.13 Phase 6–7 环节级实现规格（D6.1–D7.4）

§6.12 的写法延续到这里。这两个阶段不产生新架构，它们产生**证据**：陌生人能不能独立完成、
C1–C11 的声明有没有被证明。因此每一行的「输出」都是可核对的东西，不是状态更新。

| 环节 | 输入 | 处理 | 输出 | 验收 |
|---|---|---|---|---|
| 开发者代理轨迹（D6.1） | 可运行的本地产品、内置商品包 | 开发者按任务说明走完整轨迹：默认生成 → 一次定向返工 → 一次故障恢复 → 导出；发现阻塞先修再重走 | 轨迹记录 + 错误清单 + 导出包 | 正常路径、返工、恢复三条都通过；不把代理验收当调试现场 |
| 可用性与可访问性检查（D6.2） | 稳定下来的页面 | 键盘可达、焦点顺序、错误与字段相邻、窄屏与主要浏览器的检查与修复 | 检查报告与修复项 | 关键操作不需要鼠标精确定位；加载与错误状态可理解 |
| 真实首次使用者验收（D6.3） | 最终版本与任务说明（不含开发者口授） | 一名真实、未参与开发且首次接触的人独立完成任务；开发者只观察、只在被问时记录 | 逐步记录或录像 + 观察笔记 + 完成物 | 开发者介入次数为 0；阻塞即失败；关键路径改过之后换新使用者重验 |
| 问题收敛（D6.4） | D6.3 的观察 | 逐项归类到正确的层（文案 / 交互 / 后端状态 / 提示词 / 商品资料），改在那一层 | 问题→原因→改动→回归记录 | 不把业务不熟悉误判成技术故障；没有新鲜最终验收证据时 Gate 不通过 |
| 完整工程验证（D7.1） | 冻结候选 | 全回归、状态与文档守卫、恢复探针、E2E 一起跑 | 验证报告 | 每项都是本次运行；环境阻塞与产品失败分开列 |
| 安装与回退演练（D7.2） | 干净工作区 | 安装、启动、备份、恢复、卸载；不使用开发机隐含路径 | 演练报告 | 恢复后任务与候选可读；回退只恢复程序与状态备份 |
| 完成声明审计（D7.3） | C1–C11 与各自证据 | 每项标 proven / contradicted / missing / indirect，并指向具体对象与时间 | completion audit | 任一项非 proven 时 Goal 保持未完成；不得用局部测试或代理预演顶替 C1 与 C11 |
| 冻结发布候选（D7.4） | 通过审计的版本 | 写版本 manifest、变更摘要、已知限制与演示包 | 发布候选 | 冻结后任何代码或资产改动都使候选失效并重验 |

**与 §8 的关系**：同上。本节只固定输入、处理、输出与验收口径；要改某一行时先改本节再改代码，
并把变更记入下一次校准证据。

## 7. 任务依赖主链

```text
D-1.1 → D-1.2 → D-1.3 → D-1.4
  → D0.1 → D0.2 → D0.3 → D0.4 → D0.5 → D0.6 → D0.7 → D0.8
  → D1.1 → D1.2 → D1.3 → D1.4 → D1.5 → D1.C1
  → D1.P1 → D1.P2 → D1.P3 → D1.R1 → D1.R2 → D1.R3 → D1.R4
                      └→ D1.P4（换商品探针；与 D1.R1–D1.R4 无逻辑依赖，可并行，
                            但两条支线都完成才进 Phase 2）
  （D1.C2 与环境解耦，见 §7.1；它只卡「引用 v2 基线作证明」的声明，不卡设计与验证）
  → D2.R1 → D2.R1b → D2.R1c → D2.R2 → D2.R3
  → D3.R1 → D3.R2 → D3.R3 → D3.R4 → D3.R5
  → D4.1 → D4.2 → D4.3 → D4.4 → D4.5
  → D5.1 → D5.2 → D5.3 → D5.C1 → D5.4 → D5.5
  → D6.1 → D6.2 → D6.3 → D6.4
  → D7.1 → D7.2 → D7.3 → D7.4
```

可并行准备但不能并行提交权威状态的工作：D1.R2 的各验证路线可以使用同一冻结样本并行实验；D6.2 的静态可访问性检查可在 D5 页面稳定后提前执行。其余按主链推进，避免验证路线、用户流程和状态模型同时变化而无法归因。

### 7.1 环境阻塞任务与并行规则

有的任务卡在环境上，而不是卡在设计上。`D1.C2` 就是：完整旧链回归要求在可用提交内存 9 GB 以上起跑（单次抠图实测约 6 GB 物理 / 9 GB 提交），而本机可用提交内存长期在 8.0–8.4 GB 之间；已核对本机没有残留的抠图进程，缺口来自浏览器与桌面应用。`--force` 会把抠图降级成环境项，仍然得不到「全过」，也就仍然不能重建基线，所以不放行。

由此定下两条对称规则：

- **环境阻塞的卫生任务，不阻塞与它没有逻辑依赖的设计与验证工作。** `D1.P1`–`D1.P3` 既不读、也不引用 v2 基线身份，因此依赖改为 `D1.C1`；否则一个与产品无关的内存门槛会让整个目标停摆。
- **反过来同样成立：任何引用 v2 基线或旧链回归结论作为证据的声明，必须在 `D1.C2` 之后才能提出。** 解耦的是调度，不是证据强度。

环境阻塞不得被写成产品失败，也不得用 `--force`、手改哈希或先刷新基线绕过。同一环境阻塞连续多轮无法解除时，按 Goal 的阻塞审计处理，而不是把结论静默降级成「已通过」。

**真人资源是另一类不可替代输入，处理方式相反（不许并行）。** `D2.R2` 与 `D6.3` 各需要一名
**未参与开发、此前未用过本项目**的人。它与内存门槛不同：内存可以等、可以重启整机，人的时间
不由本机调度。但办法不是让 Phase 3 先跑起来 —— 本项目任一时刻只允许一个 Phase 处于 `active`，
且后一阶段的 Gate 依赖前一阶段（§5、§7 主链与状态守卫一致），提前开工等于把 G2 的结论预先
假定成立。所以：

- **先做不需要等人的那一段**：§6.11.6 的 R2.a（任务说明、观察记录表、AI 预演）。它有独立
  验收（说明里的每一句操作都能在页面上找到落点），做完留着复用，但不给 G2 记账。
- **R2.b 没有替代物**：没人时 G2 保持未过，按 Goal 的阻塞审计处理；不得用作者自测、AI 预演
  或「已经做了别的准备工作」顶替，也不得为了让主链动起来而降低 G2 的判据。
- 同一条规则覆盖 `D6.3`：最终版本的关键流程改过之后，必须换一名新的首次使用者重验。

### 7.2 旧任务标识的处置

v1.3 的任务标识不得在改变语义后继续使用。历史证据保留原 ID，但不再调度：

| 历史标识 | v1.5 处置 |
|---|---|
| D1.6、D1.7 | 由 D1.R1–D1.R4 取代；先重建验证责任与证据链，不直接假定“修量测层” |
| D2.1–D2.5 | 由 D2.R1–D2.R3 取代；先用离线垂直切片观察产品需要，完整事件存储与 legacy reader 退出关键路径 |
| D3.1–D3.5 | 由 D3.R1–D3.R5 取代；只实现走查支持的最小可恢复核心 |

旧 ID 只用于解释历史计划，不得出现在 `next_action_task`，也不得以“已完成”映射到新任务。

## 9. 模型与质量控制

### 9.1 首个能力实验

已生成的四张候选是冻结的真实能力证据，不是必须继续消耗到八张的配额。完成 D1.R1–D1.R3 前不再发起付费生成；D1.R4 只有在证据链仍无法裁决、且一个生成变量确实可能改变结论时，才允许单变量复验。累计八张仍是上限，不是目标。改用新的付费视觉模型属于外部动作，必须另行授权。

### 9.1.1 量测适用性（F1–F8 之前的隐含前置）

每项事实必须先回答“谁有能力判断、依据是什么、能力边界是什么”，再给结论。`cylinder-v1` 的阈值掩膜只在其前提成立时可用；2026-09-26 的场景候选中，纯背景列有 16%–42% 像素被当成主体，因此这些 hard fail 不能代表商品失败。它证明的是该量测器不适用，不证明“只能修分割”，也不证明候选事实已经通过。

| 事实类型 | 首选责任者 | 允许的结论边界 |
|---|---|---|
| 文件、格式、哈希、尺寸和平台规则 | 确定性程序 | 可复现输入上可直接 pass/fail |
| 文字、标识和水印 | OCR/参考图条件视觉模型 + 人工复核 | 未经对照验证的模型只报风险或转人工 |
| 颜色、比例和轮廓 | 适用时用分割后量测；否则参考图条件视觉判断或人工 | 位置、中心和类别形状只能作弱先验，不能定义商品身份 |
| 部件、结构和相互关系 | 参考图条件视觉模型 + 显式人工事实确认 | 不能用单一阈值掩膜替代语义判断 |
| 构图、光线、材质感和商业完成度 | 人工视觉审核 | 只输出 `keep / redo / reject` 及理由，不伪造客观总分 |

分割只是可替换的验证器之一，不是所有事实的必经步骤。只有高精度、可复现的规则或显式确认的商品事实可以直接 hard fail；模型判断在完成对照校准前默认是 `risk/needs-human`。任何验证器前提不成立时返回 Unknown，并路由到别的责任者，不能放宽阈值求绿。

量测器自己也有前提。`cylinder-v1` 用 4×4 降采样块找最大连通域，所以它隐含一条尺寸前提；
不成立时旧实现把掩膜裁小，再与裁剪区域做广播而中断 —— 这不是「某张图坏了」，是适配器
少声明了一条前提，而棚拍夹具恰好全是 1344×1344，把它遮住了整整两轮。修法只对齐形状、
不改语义（修复前后对全部冻结样本逐值相同），并把它写成量测器自己的 `self-test`：
判据必须有回归，否则换一张尺寸不同的图就等于换了一个程序。

### 9.2 图片审核顺序

```text
请求真实性
→ 文件与平台技术形态
→ 逐项事实验证路由
→ 未解决事实的显式人工确认
→ 画面物理一致性
→ 人工商业视觉判断
→ 人工选择
```

前一层的已确认失败，后一层评价不能把它改成通过；前一验证器“不适用”必须变成 Unknown 并换路由，不能当失败，也不能被视觉偏好偷偷覆盖。通用性来自稳定的工作流、逐事实责任合同和可替换验证器，而不是所有商品共用中心位置、圆柱形状或同一个分割阈值。

### 9.3 审美判断

不建立伪客观总分。人工使用 `keep / redo / reject`，并必须从构图、主体层级、光线融合、材质真实感、背景干扰和商业完成度中选择具体理由。模型可以提供风险建议，没有最终接受权限。

## 10. 外部动作与成本控制

- 商品参考图进入百炼是已确认的产品固定前提，界面负责告知，不提供每次调用的外发选择开关；
- 项目级数据政策明确允许 `product_reference → aliyun_dashscope/qwen-image-3.0 → reference_image_generation`，并保存版本；
- 每次付费调用必须有稳定 action id、请求哈希、最大候选数、seed、预计/实际用量和最终状态；
- 首个实验最大八张是硬预算；后续每个 Shot 的默认候选数与最大返工轮次在 Phase 3 固化；
- 双击、刷新、超时和进程重启不能重复 submit；
- 没有价格或用量信息时允许在演示中记录 Unknown，但不得显示虚构费用；
- 扩大模型调用数量、改用其他付费模型或购买额外服务需要新的用户授权。
- 事实验证若使用视觉模型，只允许使用项目已在用的 `qwen-vl-max`（`evals/probes/vlm_stability/`、
  `evals/probes/prompt_enhance/vision/` 有 token 记录），逐次记账并设阶段调用上限（≤ 40 次）；
  换用其他付费视觉模型或提高上限仍需新的用户授权。预算数值只在本节维护。

## 11. 回归与完成审计

最低验证层次：

1. 纯规则与 schema 单元检查；
2. SQLite、对象存储、provider adapter 和 API 集成检查；
3. fake provider 正常/失败/Unknown/中断轨迹；
4. `qwen-image-3.0` 受控真实探针；
5. 浏览器完整任务 E2E；
6. 真实、未参与开发的首次使用者验收（AI 代理只作预演）；
7. 干净状态安装、备份和恢复；
8. C1–C11 完成证据审计。

测试通过只证明它覆盖的行为；真实探针不证明其他商品；代理验收不证明真实运营提效；演示图片不证明 Amazon 实际审核通过。
