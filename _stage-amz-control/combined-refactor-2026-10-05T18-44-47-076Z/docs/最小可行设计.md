## 0 一句话

**一次命令，一个商品，七张图，一次云模型调用，实测约 2.5 分钟。**

```bash
python run.py --product examples/product_demo.json --model qwen-image-3.0
# → out/B0DEMO1234_<时间戳>/  七张 JPG + plan.json + subject.png + run.jsonl
```

关键：**把两张扩到七张，模型调用次数不变，仍是 1 次。**
多出来的六张全是确定性合成（秒级、零成本）。所以"七张全出"几乎不额外花钱。

## 1 输入契约（一次运行的输入 = 一个商品包）

| 字段 | 必填 | 用途 | 缺了怎样 |
|---|---|---|---|
| `upc` | ✅ | 过审硬要求 + 文件命名 | 拒绝运行 |
| `images[]` | ✅ | 实物照片，主体唯一事实来源 | 拒绝运行 |
| `title` | ✅ | 用于指代商品主体 | 降级为"商品" |
| `bullets[]` | 副图必填 | 卖家写的卖点（**断言，工具不代写**） | 副图无字，主图照常 |
| `specs{}` | 规格图必填 | 尺寸/容量/材质 | 跳过位置 3 并报缺料 |
| `assets{}` | 按坑位 | **按坑位拆分的原片**（特写 / 内容物 / 竞品）+ 字体与图标资产 | 缺则该坑位**跳过**，禁止拿别的图充数（见 §4.2） |

**入口体检（E0）**，任何一条不过就拒收，不进入后续环节：

- `upc` 非空；`images` 至少 1 张且**最长边 ≥1000px**
- 原图**无文字/水印/道具**（工具修不了不合规的输入）
- `bullets` 过品牌禁用词表（示例里"全网最低价，绝对是最好的杯子"会被剔除并在日志里列出）

## 2 云 API 到底能控什么

你列的 14 个参数，**在 qwen-image-3.0 上只有 5 个真实存在**：

| 你列的 | 是否存在 | 说明 |
|---|---|---|
| 正向提示词 | ✅ | `input.messages[].content[].text`，**≤800 字符** |
| 负向提示词 | ✅ | `parameters.negative_prompt`，**≤500 字符** |
| 模型 | ✅ | `model` |
| 尺寸 / 分辨率 | ✅ | `parameters.size`，格式 `"1600*1600"`（用 `*` 不是 `x`） |
| 随机种子 | ⚠️ **弱保证** | `parameters.seed` 存在，但**同 seed 不保证出同一张图** |
| 数量 n | ❌ | max/plus 系列**固定为 1**，设其他值直接报错 |
| 参考图 | ❌ | 文生图不接受参考图（那是 qwen-image-**edit** 的能力）【待实测】 |
| 强度 / 步数 / 采样器 / CFG | ❌ | 云 API 不暴露 |
| VAE | ❌ | 同上 |

**另有三个由厂商控制、但必须显式设置的开关：**

| 参数 | 设成 | 为什么 |
|---|---|---|
| `prompt_extend` | **false** | 默认 true 会**改写你的提示词** → plan 记的和实际执行的不是一回事 |
| `watermark` | false | 默认已是 false，显式写死防上游改默认值 |
| `n` | 不传 | 固定 1，传了报错 |

### ⚠️ 两处我必须纠正自己（上一轮写错了）

1. **上轮我写"关掉 prompt_extend + 显式传 seed = 同输入可复现"——错。**
   官方与第三方口径一致：**同 seed 不保证每次结果完全相同**。
   正确表述：这两个开关只**降低**不可复现性，**不消除**。
   所以 `plan.json` 是「**可重放**」（重放得到近似结果），不是「**可复现**」（不是同一张图）。
   重做位置 4 = 重放第 4 条 plan，观感接近但不逐像素相同。这条要写进界面文案。

2. **上轮我写"qwen-image-3.0 单边支持到 2048"——未经验证。**
   官方文档对 plus/max 系列写的 1:1 上限是 **1328**；2.0 系列才支持 2048×2048。
   **3.0 的实际上限我没有实测过**，属【待实测】。
   代码里已有防御：按 `1600 → 1024 → auto` 逐级降级，把**实际拿到的尺寸写进日志**。
   所以：这一轮**不会崩**，但可能拿到 1328 后放大到 1600（1.2×，尚可，不是长边不足）。

## 3 一轮怎么跑（六环节）

| 环节 | 输入 | 处理 | 输出 | 模型调用 |
|---|---|---|---|---|
| **E0 收件** | 商品包 | 体检 + 禁用词过滤 | `facts` | 0 |
| **E1 抠图** | 原图 | 本地 BiRefNet（**本地优先，找不到就降级 floodfill，绝不联网下载**） | `subject.png` + bbox + alpha 覆盖率 + `subject_hash` | 0 |
| **E2 规划** | `facts` + `slots.yaml` | 查表：每个坑位分配文案条目 + 排版参数 + **仅位置 4** 生成背景提示词 | `plan.json` | 0 |
| **E3 渲染 ×7** | plan 单条 + `subject.png` | 七路互不依赖，可串可并 | 七张 1600×1600 JPG | **1**（仅位置 4） |
| **E4 校验** | 成品图 + 坑位校验强度 | 只能验尺寸/白底/占比/文件名 | 校验记录写 `run.jsonl` | 0 |
| **E5 交付** | 七张 + plan + subject + 日志 | 按 `{UPC}_{序号}_{用途}.jpg` 命名 | `out/<UPC>_<时间戳>/` | 0 |

**唯一顺序依赖**：E1 → E3（七路都要读 `subject.png`）。其余环节互不等待。

## 3.1 使用逻辑（和运行逻辑是两条时间轴）

上面那张表是**系统怎么跑**。这一节是**人怎么用** —— 两者长度差得很远。

| | 使用逻辑 | 运行逻辑 |
|---|---|---|
| 谁在动 | 人的手 | 系统的代码 |
| 长度 | 准备以小时/天计，审核以分钟计 | **一轮约 2.5 分钟**（实测 154 s） |
| 对应文档 | §7 的 5 个干预点 | §3 的 6 个环节 |

**人点一次"提交"，系统在背后跑完 E0→E5。中间这两分半，人零介入。**

### 两种形态，同一条链路

| 形态 | 入口 | 人介入 | 适用 |
|---|---|---|---|
| **CLI** | `python run.py --product …` | **零介入**，一条命令出全套 | 首次全量、批量 |
| **界面** | 五步页（`web/design-v2.html`） | 分段：齐套先看 → 生成 → 审核 → 重做 | 单商品精修 |

**它们不是两个系统，是同一条 E0–E5 链路的两种停法。** CLI 是不停的那条；界面是在 E3 之后**停下来给人看**的那条。
→ **重做能力（重放 `plan.json` 第 k 条）是界面形态成立的技术前提。** 没有重放，停下来看也只是"看得见、改不了"。

### 一次完整使用序列（动作级）

| # | 谁 | 动作 | 系统产出 |
|---|---|---|---|
| 1 | 人 | 拍齐原片（正面 / 特写 / 内容物 / 竞品）+ 写卖点与规格 + **选类目站点** ← §7 干预点 1–3 | 商品包 |
| 2 | 人 | 提交（一条命令，或界面投递） | — |
| 3 | 系统 | E0 体检 → E1 抠图 → E2 规划 | `facts` / `subject.png` / `plan.json` |
| 4 | 系统 | **E3 渲染 ×7**（仅位置 4 调模型） | 七张 1600×1600 |
| 5 | 系统 | E4 校验 → E5 交付 | `out/<UPC>_<时间戳>/` |
| 6 | 人 | 一屏并排审核，逐张采纳 ← §7 干预点 4 | 采纳记录 |
| 7 | 人 | 对不满意的张：选"**哪一层**错" → 重做 | 只重放该条 plan |
| 8 | 人 | 复核（白底 / 占比 / 命名）→ 取件上传 ← §7 干预点 5 | — |

**一轮的边界（事务单位）**：一个商品包进 → 一个 `out/` 目录出。
失败粒度是**单个坑位**，不是整个商品 —— **只有 E1 失败才是全局失败**（没主体就没有任何一张图）。

### 四个还没定的接口

使用逻辑要完整，这四条必须定下来，现在都是空的：

| # | 缺口 | 影响 |
|---|---|---|
| 1 | **等待期可见性** —— 那两分半界面显示什么 | CLI 下是终端日志；界面下必须有分路进度 |
| 2 | **交付落点** —— 人"去 `out/` 拿"还是界面给"导出" | 决定它是**内部工具**还是**对外服务** |
| 3 | **重做版本** —— 覆盖原图，还是**新增版本** | 覆盖 = "改前长什么样"不可回溯 |
| 4 | **结束判定** —— 七张都采纳算结束？还是人主动关 | 决定有没有"未完成"这个状态 |

**建议（待拍板）**：
1. 显示**分路进度**，橙色那条单独走（其余瞬完）；
2. 最小可行先"给目录"—— 导出按钮是外壳，不进 P0；
3. **新增版本，不覆盖**（覆盖会把归因数据一起抹掉）；
4. **人主动结束** —— 系统只记状态，不自动判定。

## 4 七坑位映射（"只有 1 次调用"是怎么来的）

| # | 用途 | 怎么出 | 调用 | 为什么这样选 |
|---|---|---|---|---|
| 1 | 主图 | 抠图 → 居中 85% → **纯白画布** | 0 | 平台强制项，容错为零，不接受概率工具 |
| 2 | 卖点 | **纯色底** + 叠字 | 0※ | 底=环境，**本可生成**；当前选纯色底是产品决策，不是判据结论（见 §4.1） |
| 3 | 规格 | 纯色底 + 叠字 + 标注线 | 0※ | 同上；规格数字来自 `specs`（卖家给的断言，不涉画面） |
| 4 | 场景 | ★ **生成空背景** → 贴主体 → 叠字 | **1** | 全链路唯一"无人担责"的部分：环境是设计，不是事实 |
| 5 | 细节 | **特写原片**裁切 + 叠字 | 0 | 细节必须是真的；**一张正面全身图裁不出螺纹**，缺特写就跳过 |
| 6 | 内容物 | 有**内容物原片**则白底合成，无则**跳过报缺** | 0 | 正面图里没有包装盒和配件，缺就只能缺，不许让模型画 |
| 7 | 对比 | 并排合成 + 叠字 | 0 | 不得贬低竞品、不得出现竞品品牌 |

**位置 4 是唯一的"生成 → 贴入"两段式**：

```
qwen-image-3.0 只画一张空背景（提示词里无条件排除产品本体）
        ↓ 下载
确定性把 subject.png 贴进留白区（占位 60%、底部对齐、可选接触阴影）
        ↓
叠字层画文字
```

代价诚实说：**主体绝对保真，但接缝/光影不融**。这是唯一没有确定性控制的地方，
最小可行版本**接受它**（背景优先选简单环境：桌面、墙面、单色渐变），
不引入超分、不引入重绘、不引入 ControlNet。

### 4.1 为什么是 1 路，而不是 3 路（判据与边界）

**合法可生成的选项有 3 个：位置 2 / 3 / 4。上限是 3，不是 1。**

判据只有一条：这一路画面里，哪些内容**没有任何人持有事实**？

| 坑位 | 画面内容 | 事实持有者 | 可否生成 |
|---|---|---|---|
| 1 主图 | 纯白底 + 实物 | 平台强制禁修饰 | ❌ |
| 2 卖点 | 底（环境）+ 文字 | 底：无人 / 字：卖家 | ✅ 底可生成 |
| 3 规格 | 底（环境）+ 标注 | 底：无人 / 数：卖家 | ✅ 底可生成 |
| 4 场景 | 环境 | 无人 | ✅ |
| 5 细节 | 材质纹理 | **原片** | ❌ 生成 = 编造材质 |
| 6 内容物 | 盒里有什么 | **原片** | ❌ 生成 = 编造配置 |
| 7 对比 | 自家 + 竞品 | **原片 / 竞品** | ❌ 生成 = 编造对方 |

**⚠️ 本文选 1 路（只做位置 4），是选了下限，不是推出了下限。** 理由要按真实权重排：

1. 最小可行优先跑通（先证明链路，再扩范围）
2. 少一个失败面
3. 省一次调用

**"卖点图要可读性、背景越干净越好"不构成理由** —— 生成背景同样能在提示词里要求留白。
把它写成理由是**倒果为因**：先定了"少调模型"，再回头补一个设计说法。已改。

**1 路与 3 路真正的差别（不是钱）：**

| | 1 路 | 3 路 |
|---|---|---|
| 有环境的图 | 1 张 | 3 张 |
| 成套观感 | **割裂**：一张有氛围，六张纯平 | 更成套 |
| 额外代价 | 无 | 3 倍调用、3 倍失败面、3 路都要约束留白 |

**批次一致性不靠多调模型**：位置 4 那一次生成，可以从图上**提取主色**，
让其余六张纯色底共用这一色系 —— 一次调用的产物被六路复用。
所以"只有 1 路"与"成套统一"并不冲突：前者是调用次数，后者是控制面共享。

**另有一条上轮漏掉的路径**：`qwen-image-edit`（保主体、换背景）。
它以原图为主输入，接缝比"生成空背景再贴主体"自然得多；代价是主体经重绘、保真度下降。
对位置 2/3 这类"主体小、背景占比大"的图，可能比位置 4 更合适。【待实测】

### 4.2 不调模型那六张，像素从哪来

**先纠一个我没说清的说法：「不调模型」不等于「不需要素材」。**

那六张不是"生成"出来的，是**拼装**出来的 —— 把**已经存在的像素**重新排列。
所以每一张都有一笔**硬依赖**：画面里必须出现的那块像素，**手上得先有**。
没有，不是"做得差一点"，是**根本做不出来**；而且模型也**没资格**替它编。

| # | 坑位 | 不调模型时，像素从哪来 | 这块必需的原片，在一张产品图里吗 |
|---|---|---|---|
| 1 | 主图 | `subject.png`（抠自原片） | ✅ |
| 2 | 卖点 | `subject.png` + 纯色填充 + 图标 + 字体 | 主体 ✅ ／ 图标与字体需另行备 |
| 3 | 规格 | `subject.png` + 矢量标注线 + 字体 | ✅ |
| 4 | 场景 | **生成的空背景** + `subject.png` | 背景 ❌ **唯一能由模型合法补的像素** |
| 5 | 细节 | **特写原片**裁切 | **❌ 正面全身图里没有螺纹、接缝** |
| 6 | 内容物 | **内容物原片**抠图 | **❌ 正面图里没有包装盒、配件** |
| 7 | 对比 | 自家 `subject.png` + **竞品图** | **❌ 竞品图不在手上** |

**读出来的两条结论：**

1. **七格里只有一格（位置 4 的背景）的缺失像素，可以由模型合法补上。**
   其余缺口 —— 细节的特写、内容物的包装、对比的竞品 —— 全是**事实**，
   模型没有资格给。**缺了就是缺了，只能补拍或跳过。**

2. **「不调模型」不是免费的，它把成本从「生成能力」挪到了「素材完备性 + 拍摄」。**
   §5 那句"七张和两张花一样的钱"，说的是**模型调用费**，不是总成本。
   总成本里真实存在的一项是**把角度拍齐**。省下的调用费，一部分转手花在摄影上。

**于是输入契约必须补 `assets{}`（已加进 §1）** —— 原来只有平铺的 `images[]`，
没和坑位对上，这是一个真缺口：**少一张特写，系统不会知道**，
只会把正面图放大当成"细节图"，产出**看似合规、实则零信息**的废图。

**E0 按坑位做齐套校验，缺了就跳过该坑位（不是硬失败）：**

| 坑位 | 需要的素材 | 缺失时 |
|---|---|---|
| 1 / 2 / 3 | 任意一张清晰原片 | 无 → **全局拒绝**（没有主体就没有任何图） |
| 5 细节 | `closeup[]` | 跳过；**禁止用全身图放大充数** |
| 6 内容物 | `contents[]` | 跳过（现有行为已是"跳过报缺"） |
| 7 对比 | `competitor[]` | 跳过（**不得让模型画一个"竞品"**） |
| 4 场景 | 无（背景由模型生成） | — |

**为什么是"跳过"而不是"降级凑一张"**：凑出来的图没有信息增量，
但它**占掉一个坑位**，还让买家以为看到了细节。**假图像比缺图更贵 —— 它花的是信任。**

**第三类极易被漏掉的素材：字体与图标，且带授权。**
文字用字体文件画（这是确定性的一环），但**商用字体是要授权的**。
用一款没授权的字体画出来的图，**合规上不可用** —— 和"原片自带水印"是同一类问题，
都应该在**入口拦**，不该等出口报错。所以字体 / 图标也进 `assets` 清单，记录来源与授权，E0 一并校验。

## 5 时间与成本

| 环节 | 实测耗时 | 依据 |
|---|---|---|
| E0 + E2（体检 + 规划） | **< 1 s** | 纯计算，无 I/O 无网络 |
| **E1 抠图 ×3（串行）** | **约 90 s** | 主图 41.9s · 内容物 35.8s · 竞品 12.0s【实测】 |
| **E3 位置 4 调用模型** | **约 63 s** | 【实测】qwen-image-3.0 单张 |
| E3 其余六路 | < 1 s | 纯 PIL 合成 |
| E4 + E5 | < 1 s | — |
| **一轮合计** | **约 154 s** | 抠图串行在前，**不是"最慢那一路"** |

> ⚠️ **抠图前移的代价**（M5 引入，本文修正时实测）：所有抠图被提到模型调用**之前**
> （为了"抠图失败就不花钱"与"一轮只抠一次"），于是**一轮总时长 ≈ 抠图 + 模型**，
> 不再是 66–70 s 那一个数。抠图本身波动也大：同一张主图三次实测
> **41.9s / 20.7s / 37.5s**（模型加载与内存压力不同）。
> **所以"一轮多久"只能给区间（2—3 分钟），不能给点值。**


**模型调用成本 = 1 张图的调用费。** 七张和两张花一样的钱。

> ⚠️ 这里说的是**调用费**，不是总成本。总成本还含**拍摄**（见 §4.2）——
> 不调模型省下的那部分，转手花在了"把素材拍齐"上。别把这句读成"这套系统很便宜"。

> ⚠️ 这是**结果**，不是选型理由。调用次数由 §4.1 的判据决定（合法上限 3 路），**不由成本决定**。
> 把"省钱"当设计理由，是先有结论后找理由 —— 本文档此前犯过这个错，已改。

## 6 生成之后能验什么

**能自动验的只有 4 项**（有规则、有参照物）：

- 尺寸：边长 / 比例 / 文件大小
- 主图白底纯度：四角 + 边缘采样是否 RGB(255,255,255)
- 主体占比：位置 1 是否 ≥85%（`alpha_coverage` 自检能拦"抠图没生效"）
- 文件名含 UPC

**验不了的（别声称验了）**：

- 文字对错 —— 除非接 OCR，否则 native 文字**无人校验**
- "像不像实物" —— 只能人看
- "好不好看" —— 只能人看

**所以最小可行的验证策略不是"多加校验器"，而是"减少需要验证的东西"**：
文字由代码画 → 必然正确；主体不进模型 → 一致性结构上不可能错。
校验器只兜底"确定性环节自身出错"（比如抠图没生效）。

## 7 人工干预点（5 个，不多不少）

| # | 环节 | 人做什么 | 不做会怎样 |
|---|---|---|---|
| 1 | 商品事实录入 | 给 `bullets` + `specs` | **虚假宣传** |

| 背景错 | **70 s，计费** | 重新调模型 |

强制三选一 = 零成本的归因数据。

## 8 形态：坑位表驱动与渲染器编排（对提案的评估）

> **提案**：*"一生七不是特定的吧。最小可行应该是做好一个封装云 API 的调用界面，
> 其他的提示词优化增强相当于 SKILL，一生七相当于 SKILL 编排，
> 用户可能还可以自己决定组装触发哪几个生成任务。"*

### 8.1 提案里对的部分（三条，全部采纳）

1. **"七不是特定的"—— 对，而且这是本文档已经被逼出来的结论。**
   §4.2 的齐套校验已经意味着：**实际能出几张 = 坑位表 ∩ 素材齐套**，不是常数 7。
   只有一张正面图时，可靠产出是 4 张。**7 只是一个实例，不是系统的常数。**

2. **"提示词是可插拔的一层"—— 对。** 提示词属于**控制面资产**，
   不该写死在 `planner.py` 里。抽出来之后，换提示词不改代码。

3. **"用户可以决定做哪几个"—— 对，但只在「重做」这一侧。** 见 §8.3。

### 8.2 一处必须纠正：把「调用层」当成了最小可行

**"封装云 API 的调用界面"是全系统里最不承重的一层**，三条理由都在前面：

| 它有多小 | 出处 |
|---|---|
| 只有 **5 个参数**（正负词、模型、尺寸、seed） | §2 |
| 只被 **1 个坑位**使用（位置 4） | §4.1 |
| **人工现状里就已经有它**：运营打开生图工具、上传图、写词、出图 | 面试原话 |

**把最不承重的一层做成 MVP，等于把 MVP 定义在现状上。**
那个"调用界面"就是运营今天已经在用的东西 —— 把它包一层，**"七轮循环"一轮都不会少**。

真正承重的是**编排**：哪几步调模型、哪几步拼装、缺料怎么退、重做重放哪一条。
这一步现在**没有**，而它才是面试官说"很重复"的解药。

### 8.3 一处必须限位：装配权放在「重做」，不放在「首次」

"用户自己组装"如果成为**默认交互**，就是把编排劳动推回用户 ——
而他原本要交出来的就是这个（"很重复" = 七轮重复的"选图 + 写词 + 等 + 挑"）。
**让他勾七个复选框，只是把七轮对话换成七个勾。**

正确切口是**两个入口、两种自由度**：

| 入口 | 默认 | 用户自由度 |
|---|---|---|
| **首次生成** | **一键全量**：按坑位表跑全集，缺料的自动跳过并报 | **只可减**（关掉某几个坑位），不需要从空开始勾 |
| **重做** | 指定粒度 | **可精确指定**：改文案 / 改位置 / 重生成背景（三粒度，见 §7） |

**为什么首次要"默认全集"**：工具的价值恰恰是"**你不用知道亚马逊需要哪几张**"。
如果默认是从空表开始勾，这份知识就没沉淀进系统 —— 工具退化成"更快的表单"。

**"自选"还必须受两条约束**（否则与 §4.2 直接冲突）：

- **必选集不可关**：位置 1 主图是平台强制项，不能选"这次不做主图"。
- **选项只有"做 / 不做"，没有"换种做法"**：不能把缺料的坑位改成"让模型凑一张"——
  那正是 §4.2 标红的那三格。**缺就是缺，跳过是唯一合规选项。**

### 8.4 修正后的部件划分（提案的四个部件都在，只是权重不同）

提案说的四样东西**全都存在**，只是"调用层"不是最小可行的那一个：

| 部件 | 提案里的叫法 | 本文档里的位置 | 承重 |
|---|---|---|---|
| **坑位表** | （未提） | `slots.yaml`：每坑位声明像素来源 / 是否调模型 / 文案槽位 / 缺料行为 | **最高** |
| **渲染器注册表** | "SKILL" | §4 的七行：每坑位一个 renderer | **高** |
| **执行器 / 编排** | "SKILL 编排" | 遍历表 → 齐套校验 → 分派 renderer → 扇出 | **高** |
| **调用层** | "封装云 API 的调用界面" | §2 的 5 个参数 | **最低**（1/7 用、现状已有） |

**"SKILL"这个词要放宽一处**：若 SKILL 只指"提示词"，它只覆盖 **1/7** 的坑位 ——
其余六个**根本没有提示词**，它们是合成管线。
**把 SKILL 从"提示词"放宽到"渲染器"，这个抽象才对，而且它就是我 §4 那张表的另一种写法。**

### 8.5 这一节改掉了我前面一个说法

前面写"P0 只做位置 1 + 位置 2，其余五张同构复刻"。**这句话不够准确。**
"同构复刻"本身就意味着表驱动 —— 那么 P0 该做的不是"两张图"，而是：

> **一张表 + 一个执行器 + 两个 renderer。**

差别在于：做两张图，证明的是"能出图"；做表和执行器，证明的是"**能扩展**"。
后者才是这套设计要讲的事。**"七"进代码，还是进表 —— 这是架构分水岭。**

## 9 模块结构（可扩展性落在哪）

### 9.1 三条判据：什么叫"可扩展"

**① 扩展是加法，不是改法。**
加一个坑位 = 加一行数据；加一种做法 = 加一个文件 + 登记一行。**执行器代码不动。**
反例：`if slot == 4: call_model()` —— 加坑位就得改判断，这不是可扩展，是"预留了位置"。

**② 一个配置项只被一个模块解释。**
两处读同一个字段并各自解释，迟早漂移（本项目已踩：`render_path` vs `bg_kind` 两个真相源）。

**③ 配置必须分类，并拒绝"派生配置"。**

| 类型 | 是什么 | 谁能改 | 本项目例子 |
|---|---|---|---|
| **策略配置** | 业务选择 | **用户可改** | 位置 2 / 3 用纯色底还是生成背景 |
| **机制配置** | 环境事实，不是选择 | **用户不可改** | 端点、模型名、尺寸上限、负向词长度上限 |
| **派生配置** | 能从别的配置算出来的 | **禁止存在** | "这套图要几张" ← 由 坑位表 ∩ 素材齐套 算出 |

**"一生七"的 7 是派生配置，不是输入。**
这就是 §8.3 那条限位的根据 —— 不是不让配，是**它本来就不该是手填的**。

### 9.2 三条接缝，其余无配置

本项目真实的替换方向只有三个：

| 接缝 | 换什么 | 怎么加 |
|---|---|---|
| ③ **坑位表 + 类目模板** | 业务：加坑位、换类目 | 加一行 YAML |
| ② **renderer 注册表** | 做法：新的合成 / 生成方式 | 加一个文件 + 登记一个键 |
| ① **调用层 provider** | 厂商 / 模型：换 wanx、加 `-edit` 方案 | 换一个实现 |

**其余全是实现，不该有配置项**：契约校验、执行器、校验器、命名交付 ——
它们的行为由上面三层的数据决定，**多一个开关就多一个真相源**。

### 9.3 目录落点

```
config/
  slots.yaml             坑位表（业务数据，N 行，可增删）
  catalog/<类目>.yaml     类目模板（推荐子集 + 参数偏离）
  providers.yaml         机制配置（端点 / 模型 / 尺寸上限）
assets/
  fonts/  icons/         含来源与授权记录
src/
  contract.py            入参 + 齐套校验（唯一入口，无配置）
  table.py               slots.yaml → Slot 对象（schema 校验）
  registry.py            renderer 注册表 {name: callable}
  renderers/             每坑位一个文件（compose_white / flat_overlay / gen_bg_paste / closeup_crop / ...）
  providers/qwen_image.py  5 个参数
  orchestrator.py        遍历 → 扇出 → 收集
  verify.py              确定性校验
  deliver.py             命名 + 落盘
```

**关键性质**：`orchestrator.py` 里**没有 `if slot == 4`**。
它只做 `registry[slot.renderer](...)`。**坑位行为全部在数据里，不在代码里。**

### 9.4 回到"配置性就是应该灵活使用"—— 对，但方向反了

**可配置 ≠ 该暴露。** 两者之间隔着一个判断：**这个决定该由谁的知识来答？**

- "亚马逊要哪几张" → **工具的知识**（写进坑位表和类目模板）→ **不该问用户**
- "这次要不要做对比图" → **用户的知识**（他手上有竞品图没有）→ **该让用户改**

所以正确形态是**系统先给推荐全集，用户只做"减"**：

```
推荐全集（坑位表 ∩ 素材齐套）  →  用户关掉不要的  →  执行
                                        ↑ 只在这里有自由度
```

**从零开始勾是错的**：那等于把"亚马逊要几张"这份知识设成 0，工具退化成"更快的表单"。
**灵活性不是"什么都能配"，是"系统先把最优解摆出来，你只改你要改的那一处"。**

### 9.5 一个必须避开的陷阱：通用编排引擎

"可扩展"最容易滑向"做个 DAG / 工作流引擎 / SKILL 市场"。**不要做。** 三个理由：

1. **扩展性无方向**：能编排一切 = 不擅长任何。本项目扩展方向只有三个（§9.2），
   架构只为它们优化就够了。
2. **把设计决定变成用户配置**：用户得自己搭流程 —— 又回到"让他勾七个框"。
3. **永久成本押低概率需求**：DAG 引擎的复杂度是**永久的**，"用户自定义工作流"是**未必发生的**。

**判据**：一个扩展点，若未来一年内没有明确的使用者，就不要为它建抽象。
（这条同时是本文档反复自我纠正那个病的架构版 —— **用更精致的机制，替代更简单的实际**。）
