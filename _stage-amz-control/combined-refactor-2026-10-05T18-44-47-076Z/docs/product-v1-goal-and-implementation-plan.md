## 1. 已确认的产品边界

### 1.1 产品定位

Product V1 是供 **2–5 名内部电商运营人员**使用的 Amazon Listing 图片生产工具，不是公开 SaaS。
它运行在 Windows 本地或受控局域网环境，由操作员完成最终事实验收和发布决定。

它解决的不是“调用模型生成七张图”，而是：

> 操作员能把一份经过确认的商品资料，稳定地变成一组可审核、可单图返工、可恢复、可追溯、可导出的 Listing 图片；生成模型只能提出候选，不能直接把候选变成发布结果。

### 1.2 V1 范围内

- 商品事实、参考图、卖点和类目信息的收件与校验；
- 可配置的图片槽位计划，不把“七张”写成不可改变的平台事实；
- 确定性渲染与参考图生成路线并存；
- 逐图候选、机器规则检查、可选 VLM 风险检查、人工事实验收；
- 单图返工、候选选择、断点恢复、版本化导出；
- 模型调用的数据权限、预算、幂等、超时核对和审计；
- 一个主品类和一个差异明显的验证品类；
- Windows 目标环境的可重复安装、启动、操作和回退。

### 1.3 V1 范围外

- 公开 SaaS 所需的租户、订阅计费、公开注册和互联网级运维；
- Listing 文案、关键词、A+ 页面、视频生产；
- 自动登录或自动发布到 Amazon；
- 未经单独授权的人像生成、人物模特图和竞品图片上传第三方；
- 无人工发布门的全自动上架；
- 在 Product V1 验收前删除 v2 确定性路线；
- 采购或替换商用授权字体。V1 只要求 `font_license` 这条签字项为真
  （授权不是程序能判的事，见 `src/intake.py`）；`config/brand.json` 的 `fonts` 留空时
  自动探测系统中文黑体。要改成自有授权字体是**改一行配置**，所以它不进 V1 边界 ——
  但「系统字体通常不含商品图商用权」这条风险由签字人承担，不由代码掩盖。

## 2. 系统 Goal 文本

以下文本可原样用于创建 Goal；本文件是全文权威，系统 Goal 只保存可执行摘要。

> 将 `amz-listing-kit` 建成可供 2–5 名内部运营人员在 Windows 本地或受控局域网中独立使用的 Amazon Listing 图片生产产品：操作员输入经确认的商品事实、参考图和卖点后，能够生成可配置的完整图片组，逐图查看候选和检查结果，完成单图返工与人工事实验收，并导出带版本和追溯清单的不可变交付包。以 20 个真实 SKU、至少 2 个品类和 2 名操作员完成产品验收：所有被接受图片的关键商品事实错误为 0，至少 18/20 个任务无需开发者介入即可完成，两个操作员各自独立完成至少 5 个任务；前 5 个 SKU 用于测量并由用户冻结单任务成本与完成时间上限，其余试点不得突破已批准上限。模型调用必须具备数据授权、任务身份、预算硬限制、重复提交防护和超时后的 Unknown 核对；系统必须通过断点恢复、单图返工、干净 Windows 环境安装、v2 回退演练、现有完整回归及新增产品验收。V1 不包含公开 SaaS、文案/视频、Amazon 自动发布、人像或竞品图的默认外发，也不以删除旧渲染器作为完成条件。若数据外发权限、成本/时间上限或关键事实验收标准不能获得授权，或单槽位影子实验不能证明相对现有路线的净收益，则停止扩大生成优先路线并保留/降级到确定性方案，不得降低完成标准来宣布 Goal 完成。

### 2.1 Goal 完成的必要条件

以下条件是“并且”，不是任选其一：

1. **工程行为成立**：正常、拒绝、失败、超时未知、恢复和回退路径都有可执行判据。
2. **产品可独立使用**：至少 18/20 个真实任务无需开发者介入完成。
3. **商品真实性成立**：所有被接受图片的关键商品事实错误为 0。
4. **成本与时间受控**：首 5 个 SKU 后冻结阈值，其余试点不越线；超线自动停止而非事后报告。
5. **权限与审计成立**：每次外部调用可回答谁授权、发了什么、调用了谁、花了多少、结果属于哪个任务。
6. **发布与恢复成立**：目标环境可安装运行，中断可恢复，V2 可回退。

文档写完、代码合并、测试通过、模型自评高分，都不能单独证明 Goal 完成。

## 3. 成功指标与测量口径

| 指标 | 分母与样本 | 通过线 | 权威证据 |
|---|---|---|---|
| 关键商品事实错误 | 20 个试点任务中所有被接受图片 | **0** | 操作员逐图事实清单 + Review 记录 + 图片哈希 |
| 无开发者介入完成率 | 20 个试点任务 | **≥ 18/20** | Task 事件日志；介入原因必须机器可归类 |
| 双操作员独立使用 | 2 名操作员 | 每人 **≥ 5 个任务** | 操作员身份、任务与导出记录 |
| 品类覆盖 | 真实 SKU | **≥ 2 个品类**，每类至少 5 个 SKU | ProductPackage 与试点清单 |
| 单图返工隔离 | 选定 Shot 的返工用例 | 未选 Shot 的已接受版本和哈希不变 | 返工前后 OutputVersion/候选哈希对照 |
| 中断恢复 | 生成前、已提交待回执、审核中至少 3 个断点 | 重启后不丢状态、不重复付费提交 | 恢复探针 + provider task id/ledger |
| 成本与耗时 | 首 5 个 SKU 建基线；其余 15 个验证 | 不超过用户冻结阈值；预算超线时提交前熔断 | CostLedger、Task 时间线、阈值版本与批准记录 |
| 可安装性 | 一套无项目历史状态的目标 Windows 环境 | 按文档安装并完成 1 个演示任务 | 安装记录、环境清单、演示导出包 |
| 工程回归 | 当前 v2 回归 + Product V1 新增验证 | 发布候选上连续 2 次通过；环境阻塞不得伪装成通过 | 带代码/配置版本的回归报告 |
| 回退能力 | 发布候选 | 不丢已接受产物和审计记录，可切回 v2 完成演示任务 | 回退演练报告 |

### 3.1 关键商品事实错误

下列任一项在被接受图片中与权威商品资料不一致，即计为关键错误，不能被平均分掩盖：

- 商品轮廓、部件、开口、盖子、手柄、接口等结构；
- 数量、套装构成、配件；
- 主色、图案、Logo、标签和包装文字；
- 尺寸、容量、材质、兼容性等事实性表达；
- 模型凭空增加、删除或替换商品组成；
- 发布平台明确禁止的主图元素；
- 画面或文字表达了 ProductFacts 中不存在的卖点或承诺。

审美偏好、构图优劣和关键事实错误分开记录；审美高分不能抵消事实错误。

### 3.2 首 5 个 SKU 的作用

首 5 个 SKU 是校准集，不是 Goal 完成证据。它们用于：

- 测量每个任务的调用次数、费用、端到端耗时和人工审核时间；
- 冻结成本上限、完成时间上限和候选数量 `k`；
- 校准严重错误分类和人工清单；
- 决定生成优先路线继续、缩小、降级或停止。

阈值必须记录批准人、批准时间和版本；未批准不得进入其余 15 个 SKU 试点。

### 3.3 测量口径（跑第一个校准任务之前必须定）

「单任务成本上限」只有在**成本的定义**固定之后才有意义 —— 否则同一个数字可以指预估、实付、
不含重跑、不含等待……于是「后 15 个不得突破已批准上限」这条根本无法审计。
本表**不重复** §3.2 要测什么，只定每项的**边界**。

| 指标 | 边界 | 为什么必须先定 |
|---|---|---|
| 一个任务 | 一个 SKU 的一次完整交付（收件 → 导出包落盘）；同一 SKU 的重复交付是**同一任务**的重试，不再计入分母 | 让「20 个任务」「18/20」有确定的分母；「重做一次算两个任务」能把分母注水 |
| 费用 | 计入该任务触发的**每一次计费调用**（生成 / 质检 / 重试 / 重跑），按供应商回执记实付；派发前的**预留**另记一列 | 只记一次预估会让重跑的成本隐形 —— 参考范例里一轮自动重跑最多把单 SKU 成本低报约 3 倍（见 `docs/drafts/ref-mining-ecom-2026-09-23.md` §4.3） |
| 调用次数 | 按动作身份去重的提交次数；因重试产生的重复提交**分别**计（它不是零成本） | 重复提交既是成本也是风险，合并计数会把两者一起藏起来 |
| 端到端耗时 | 从任务进入 running 到导出包落盘；机器段与人工等待段**分开记** | 只记机器段会高估「一天能做几单」 |
| 人工时长 | 从第一次看到候选到接受或结束返工；口径（界面在场时间 / 操作员自报）在 C7 前选定并写进阈值文件 | 这条含主观成分，不许当成准确值，也不许拿它做个人考核 |
| 候选数 k | 每个坑位**实际生成**的候选数（含返工产生的），不写「系统支持的最大值」 | 阈值里写上限，就得知道当时实际用了多少 |
| 返工 | 每次返工记类型（合规化 / 重生成 / 换素材）与发起人；其调用计入该任务成本 | 三种返工后果不同（`docs/drafts/ref-mining-ecom-2026-09-23.md` §3.3），混记会让「返工后达标」说不清是哪一种 |

## 4. 产品行为合同

### 4.1 权威对象

```text
Task
  └─ ProductFactVersion
      └─ PlanVersion
          └─ Shot
              └─ GenerationAttempt
                  └─ Candidate
                      └─ Review
                          └─ Selection
                              └─ OutputVersion
```

| 对象 | 身份 | 权威内容 |
|---|---|---|
| Task | `task_id` | 一次完整图片交付任务及其状态 |
| ProductFactVersion | `facts_version` + 内容哈希 | 经人工确认的商品事实、卖点、素材授权 |
| PlanVersion | `plan_version` + 内容哈希 | 槽位、依赖、渲染路线、验证和预算计划 |
| Shot | `task_id + plan_version + slot_id` | 可独立执行、审核和返工的最小业务单元 |
| GenerationAttempt | `action_id` | 一次可能收费的外部动作、供应商任务号和最终/未知状态 |
| Candidate | `candidate_id` + 文件哈希 | 模型或确定性渲染产生的候选物，不等于结果 |
| Review | `review_id` | 规则、VLM 和人工的独立结论及证据 |
| Selection | `selection_id` | 有权限的人选择候选并说明依据 |
| OutputVersion | `output_version` + manifest 哈希 | 已接受图片组成的不可变交付包 |

模型上下文不保存权威状态；状态必须持久化到本地数据库/事件日志和文件清单中。

### 4.2 必须、可以、禁止

**必须：**

- 每个外部付费动作提交前生成稳定 `action_id`，写入预算账本和审计记录；
- 每张候选图绑定事实版本、计划版本、提示词、模型/参数、参考图哈希和供应商任务号；
- 确定性规则先于 VLM，人工拥有接受和发布决定权；
- 缺素材、业务拒绝、技术失败和超时未知使用不同状态；
- 只返工受影响的 Shot，依赖未变化的已接受 Shot 不得被隐式重做；
- OutputVersion 只能引用已经通过人工事实验收的候选；
- 预算、数据外发和发布动作 fail-closed。

**可以：**

- 同一 Shot 生成多个候选；
- 将 VLM 用作风险提示或排序信号；
- 当生成路线不能满足事实保真或预算时自动建议确定性路线；
- 在计划批准前 dry-run 展示预计外部调用和预算占用。

**禁止：**

- 把模型输出、VLM 自评或“任务创建成功”当作可发布结果；
- 对状态不明的付费请求直接重新 POST；
- 未经授权把人像、竞品图或商品参考图发给外部供应商；
- 失败后静默换模型、降质量或减少图片而仍标记完成；
- 新失败模式未经审批自动进入生产提示词；
- 为满足进度而降低关键事实错误为 0 的完成标准。

### 4.3 关键状态

**Task：**

```text
DRAFT → READY → RUNNING → NEEDS_REVIEW → ACCEPTED → EXPORTED
             ↘ BLOCKED / FAILED / CANCELLED
```

**GenerationAttempt：**

```text
PLANNED → SUBMITTING → SUBMITTED → SUCCEEDED
                       ↘ FAILED
                       ↘ UNKNOWN → RECONCILING → SUCCEEDED / FAILED / ESCALATED
```

超时只说明“当前没有足够证据”，因此进入 `UNKNOWN`。系统必须使用原 `action_id` 或 provider task id 查询权威外部状态；只有确认原动作没有被接受，才能创建新的 GenerationAttempt。

**Review：**

```text
PENDING → MACHINE_CHECKED → HUMAN_REQUIRED → ACCEPTED / REJECTED
```

任何关键事实检查不通过都不能被审美评分覆盖。

## 5. 目标架构边界

```text
ProductPackage / ProductFacts（事实权威）
        ↓
Plan Compiler（确定性生成 PlanVersion）
        ↓
Policy Gate（素材授权、预算、能力、人工批准）
        ↓
Renderer / Provider Adapter（确定性或模型执行）
        ↓
Candidate Store + Event Log（不可覆盖、可恢复）
        ↓
Deterministic Validators → VLM Risk Review
        ↓
Human Fact Review / Selection（提交权威）
        ↓
Immutable OutputVersion + Manifest
```

### 5.1 各层责任

| 层 | 负责 | 不负责 |
|---|---|---|
| ProductFacts | 商品事实和授权的唯一来源 | 不描述生成实现 |
| Plan Compiler | 槽位、输入依赖、路线、预算和验证计划 | 不执行付费调用 |
| Policy Gate | 判断是否允许提交动作 | 不生成图片 |
| Provider Adapter | 能力声明、提交、查询、下载、费用观察 | 不决定候选是否可发布 |
| Candidate Store | 保存候选、输入与哈希关系 | 不改变事实版本 |
| Validators/VLM | 找风险、提供证据 | 不拥有最终接受权 |
| Human Review | 事实验收、选择、拒绝 | 不直接改写历史记录 |
| Exporter | 只组装已接受候选和 manifest | 不补图、不自动降级 |

### 5.2 保留与迁移原则

- v2 在整个 Product V1 Goal 内保持可运行和可回退；
- 主图默认继续走确定性白底路线；
- 文字、尺寸和竞品对比默认保留确定性路线；
- 生成优先路线先以一个适合场景化的槽位进入 shadow mode；
- 是否扩展到其他槽位由阶段证据决定，不由架构愿望决定；
- 删除旧渲染器是 Product V1 之后的独立决策，不是本 Goal 的里程碑。

## 6. 详细实施计划

执行纪律：任一时刻最多一个阶段处于 `active`；只有阶段门禁取得权威证据后，下一阶段才能开始。
计划状态使用 `pending / active / done / blocked / superseded / dropped`，不使用含糊的“基本完成”。

### Phase -1：项目管理文档控制面校准（开工前置）

**依赖：** 系统 Goal 已创建，且 `goal_id` 已回填进 `state.md`。

**结果：** 「实现 / 产品目标 / 执行状态」三类事实各有**唯一**权威，且权威漂移能被机器发现，
而不是靠人记得。

| 任务 | 输出 | 验收与证据 |
|---|---|---|
| P-1.1 管辖事实登记 | `docs/INDEX.md` 增「管辖事实」列；`实现 / 产品目标 / 执行状态` 三类全表唯一 | `tools/check_docs.py` 分别报「管辖事实不在取值域」「只能有一个权威」「没有任何出处」 |
| P-1.2 执行状态入册 | `_working/**/state.md` 进受管范围并被登记 | 它在仓库里却不登记时，守卫报「未登记」 |
| P-1.3 项目管理守卫 | `tools/check_project_state.py`：Goal 绑定、阶段图与计划逐字一致、阶段门证据、任务依赖、唯一 `next_action`、记录状态与阶段一致 | 基线退出码 0；每类漂移各自报红，且只报该报的那一类 |
| P-1.4 反向校准 | `evals/probes/project_state.py`：基线 + 多向注入 | 全部方向与预期一致；报告落 `evals/control_plane_calibration.txt` |
| P-1.5 精简执行状态 | `state.md` 只留阶段 / 任务 / 阻塞 / 下一动作与**引用**，不重抄目标与范围 | `tools/check_project_state.py` 报「重抄」 |

**Gate G-1：** 上述守卫与反向校准全部通过，且 `state.md` 的 `goal_id` 指向已创建的系统 Goal。
未通过前不得开始 Phase 0。

**为什么单列一相**：本项目的腐化不是"信息丢失"，是**"哪份信息有效"没有登记**。
开工前若"做到哪、下一步做什么"没有机器可查的权威，后面每一相的门禁都会退化成
一句没人守的声明 —— 而声明比没有更糟。

**范围边界：** 本相只校**管理面**（目标 / 计划 / 状态 / 证据的权威与一致性），
不校**运行面**（预算门、幂等、UNKNOWN 核对那些是 Phase 2 的事）。
两者都叫"控制面"，但对象不同：一个管文档，一个管外部动作。

**P1.2 开工前已定口径（2026-09-23，随 P1.2 落地；判据见 `evals/product-v1/p1/p1.2-policy.txt`）：**

| 口径 | 决定 | 为什么必须先定 |
|---|---|---|
| 默认值 | 素材类别的 `default` 只许 `unapproved` / `denied`；没命中写死的规则就按默认走 | 默认 `allowed` 等于「忘了写就是批准」，而外发动作发出去就收不回来 |
| 键的写法 | 键 = 素材类别 × provider × model × 用途，四项都写具体值，**不许通配** | 通配会让「哪一条说了算」变成运气，也会让「人像 / 竞品图必须单独授权」变成一句空话 |
| 谁算批准 | 每条 `allowed` 必须有 `approver` + `approved_at`；整份清单还必须被 `signed_by` 签署 | 「没人的批准不算批准」；未签署时规则表里写什么都不生效 —— 完成证据里那句「用户签署 allowlist」就是这一次签字 |
| 过期 | `expires_at` 到期的次日按 `unapproved` 处理（到期日算最后一天） | 授权是有时限的：过期后无声继续用，等于把「批过一次」变成「永久批准」 |
| 范围外素材 | 人像与竞品图默认 `denied`（不是「还没批」），逐条单独授权才 `allowed` | 计划 §1.3 把这两类放在 V1 之外；默认 `unapproved` 会让人以为「补一条就行」 |
| 密钥 | 政策文件里出现 key / secret / token 这类键、或像密钥的值 → **加载即报错** | 这份文件要进版本库和交付追溯清单；密钥只能走环境变量 |
| 版本 | `policy_version = dpv1-<语义字段内容哈希前 12 位>`，`updated_at` 不参与；每次决策带上它 | 「当时批的是哪一版」要能事后对回来；手写的版本号迟早和内容对不上 |
| 版本的原文存哪 | 每次改动都先把上一版、再把这一版的**语义内容**存进 `contracts/data-policy-versions/<版本号>.yaml`；把存档重算一遍必须得出同一个版本号 | 版本号是内容算出来的 —— 内容一改就再也算不回旧号，而本项目没有版本库。只留版本号，答得出「批的是哪一版」，答不出「那一版写了什么」 |
| 谁执行签署 | `tools/sign_allowlist.py`：批准人、日期、有效期、保留删除约束都要人给，工具**不填默认值**；写之前先跑校验器，不过就不落盘 | 「谁批的」不能由工具代填 —— 它一填，批准就变成程序自己的主张。手写九字段 + 两条唯一性约束必然写漏，而漏在第几项上只有校验器知道 |

| 口径 | 决定 | 为什么必须先定 |
|---|---|---|

| 结论状态有哈希 | `state_hash = rvh1-<结论状态哈希>`，随每条结论变化 | 交付包要能回答“当时这张图是在哪一份结论状态下被接受的” |

|---|---|---|
| 什么算数 | 只算**真实且 ready** 的条目；`sample: true` 一律不计数 | 样例凑数会把「用真实样本证明过」降级成「摆够了行数」 |
| 状态是算的 | 缺事实版本 / 授权版本 / 素材 / 品类 / 操作员 → 自动 `not-ready`，且**不参与**配额计算 | 写出来的状态可以撒谎，算出来的不会；「先算上、回头补」正是要堵的空子 |
| 批次归属 | order 1–5 = calibration，6–20 = official；写反直接报错 | 前 5 个的作用是测量并冻结成本/时间上限（§3.2）；顺序与批次打架会让「校准集」变成一句空话 |
| 匿名化 | id = `SKU-NN`、operator = `OP-X`；出现 UPC / ASIN / 标题 / 价格 / 链接 / 品牌名 → 报错 | 登记表会进交付追溯；真实商品身份与商业数据留在受控目录 |
| 素材引用 | 只放受控目录下的**相对路径 + sha256**；kind 取自 `src/assets.py` 的 `IMAGE_KINDS` | 原图不入库，但「后来还是同一张图」要能证明 |
| 素材放在哪 | 项目根下的 `materials/<SKU 匿名编号>/<kind>.<ext>`（例：`materials/SKU-01/front.jpg`）；登记表只记这个相对路径 | 约定好目录，拿到真实素材时才不用猜该放哪。原图不进 `docs/`、不进证据包；`materials/` 也不在 v2 基线与回归的受管范围内（基线只覆盖 `config/ src/ tools/ web/` 与 `evals/**/*.py`） |
| 事实来源放同一处 | 每个 SKU 的 ProductFacts 输入是 `materials/<SKU 匿名编号>/product.json`；`facts_version` 就是照着它现场算出来的 | 版本号手抄必漂；按 id 推路径、不另开字段，拿到素材时就顺带放进去了。这个文件不在 → 该条 `not-ready`，不是「版本号写错了」 |
| 版本要现场算 | `facts_version` 用 `src/product_facts.py` 重算、`data_policy_version` 对 `contracts/data-policy-v1.yaml` 活的那一版重算、每个 `assets[].sha256` 重新算 | 只验形态的话，随手写一个格式合法的版本号就能把门变绿。那正是本项目一直在堵的「声明了校验但静默跳过」；P1.5 的 `inputs[]` 用的是同一招 |
| 三种结果分开报 | 在（`ok`）/ 还没放（`pending_input`）/ 对不上（`mismatch`）；前两种退 1，后一种退 2 | 「还没做到」和「对不上」要对不同的人、走不同的动作：一个是去放素材，一个是去查为什么不一样（可能是图被换了） |
| 空表不许算绿 | 核对器必须报出**真的核到输入的条目数**；一条输入都没有时这个数是 0，并写成待补项 | 「没报错」不等于「核过了」；零输入时的绿是最容易骗过自己的那种绿 |
| 谁写哪几列 | 人只写 `order / id / category / operator`；`batch` 由 order 推；`facts_version` / `data_policy_version` / `assets[]` 由 `tools/fill_pilot_registry.py` 补齐（缺料留空，不编） | 20 条 × 每张图的 sha256 = 上百个哈希，手写写不对；写错了门退 2，人却会以为是自己格式写错。分工写死，才不用靠人算哈希 |
| 两个退出码 | 1 = 样本没齐 / 素材还没放（业务）；2 = 登记表写错了或与真实输入对不上（人得改） | 和文档守卫同一个教训：两类失败混报，人会把「活没干到」看成「自己写错了」 |
| 空表是诚实的起点 | `pilot/pilot-registry.yaml` 现在就是 0/20，不去填样例 | 任务卡的失败/回退写着「不得用样例 SKU 补足真实样本数」 |

**P1.5 开工前已定口径（2026-09-23，随 P1.5 落地；判据见 `evals/product-v1/p1/p1.5-dataset.txt`）：**

| 口径 | 决定 | 为什么必须先定 |
|---|---|---|
| 输入绑定 | 每条记 `inputs[{kind, ref, sha256}]`，并记 `facts_version`；加载时**现场把输入算一遍**来核对 | 手抄的版本号迟早和输入脱钩；现场算出来的才算真的绑住了 |
| 样本从哪来 | 真实样本由 `tools/add_dataset_sample.py` 从 `pilot/pilot-registry.yaml` 的那条 SKU 生成；人只写它**想考什么**（`case_class` / `design_note` / `exercised_items`） | 一条样本要写好几个哈希加一个版本号，手抄必然抄错；抄错了那条样本不进统计，人却以为已经加上了。而且「先过 P1.4 再加样本」这条依赖得靠代码挡，不能靠记性 |
| 样例不计数 | 只有 `source_kind=pilot` 的样本进 G1 覆盖统计，`sample` 一律不计数 | 样例能把判据与工具链跑通，但不能拿来证明产品在真实样本上可用（与 P1.4 同一条纪律） |
| 标签人 | 标签人必须登记在 `dataset.json` 的 `labelers` 里；没有标签人、或标签人没登记，该样本一律不进统计 | 「待标注」与「已判定」在结果上必须不同；把一个人加进名单是**人事决定**，不是技术动作 |
| 标签版本 | 标签文件的名字就是它内容的版本（`gcv1-<前 12 位>`）；就地改会被发现，同一版不能冻两次 | 交付追溯要能回答「当时是哪一版标签判的」；可覆盖就永远答不上来 |
| 冲突 | 同一版里同一条样本两条结论不同 → 显式列出并退出统计，等人裁决（裁决的结果是新版本） | 取「最后一条」或「多数」都是替人裁决，而裁决是要负责的 |
| 关键项正反例 | 六条关键事实项各要有正例（被接受且检过）与负例（被拒且判失败） | 「明显关键错误」这一类必须真的抓得住，否则数据集只是一堆样本 |
| 候选图绑定 | 本卡只绑**输入**；候选图不在这里 | P5.3 校准时按「样本 × 候选」记结果，候选哈希写进校准报告 —— 现在还没有 V1 候选可绑，先绑一个不存在的产物才是假绑定 |

P1.2 与 P1.3 在合同稳定后技术上可并行，
但本项目维持单任务 WIP；需要用户权威的节点只有 allowlist、事实字段/单位、试点登记和数据集标签人（`labelers`），不用实现细节换取代签。

#### 任务证据与变更协议

每个任务的最小证据包固定为：`task.json`（任务身份/依赖/代码树哈希）、`checks.txt`（正向判据）、
`probes.txt`（反向样例）、`decision.md`（仅在需要人类批准或路线决策时）、`rollback.txt`（备份与恢复结果）。
二进制图片不复制进证据正文，只记录受控路径、大小和 SHA-256。

任务执行顺序默认严格按编号；只有计划明确列出的依赖全部 `done` 后才可把任务设为 `active`。低风险研究可提前做
只读探针，但不能借此提前启用真实 provider、写正式状态或绕过阶段门。任何真实外部调用仍遵循：

`Candidate → Data/Permission Gate → Budget Reserve → Idempotent Executor → Observation → Reconcile → Verifier → State Transition`

决策权分工如下：用户批准素材外发范围、试点名单、成本/时间阈值和生成路线扩张；系统守卫批准格式、状态转换、
预算和完整性；模型只提出 Facts 候选、Prompt、Review 风险或修正建议，不拥有事实确认、付费提交和最终接受权。

## 7. 贯穿控制

### 7.1 每个实施切片必须说明

- 本次改变哪个用户可见行为；
- 哪些既有不变量保持不变；
- 允许修改哪些模块和数据；
- 新增或变化的状态、身份和权限；
- 正常、拒绝、失败、未知和恢复路径；
- 自动判据、反向样例和人工证据；
- 迁移、回退和下一切片。

### 7.2 外部动作权限卡

每种真实 provider 调用在首次启用前必须登记：

```text
action_type:
business_purpose:
allowed_data_classes:
provider/model:
preconditions:
approver_or_policy:
idempotency_key:
timeout_meaning:
retry_limit:
cost_limit:
audit_fields:
reconcile_method:
rollback_or_compensation:
human_escalation:
```

### 7.3 失败模式治理

Failure Mode 不是自动积累的提示词素材。每条必须记录：

- 原始失败候选与输入版本；
- 失败分类和可观察证据；
- 影响品类/槽位/provider 范围；
- 候选修复及副作用；
- 审核者、批准者和生效版本；
- 对 Golden/Counterexample 集的回归结果；
- 退役条件。

### 7.4 变更后的最低验证

- schema/静态合同；
- 受影响组件测试；
- 状态轨迹和恢复探针；
- 文档登记与文档命令；
- 当前完整回归；
- 若改变生成语义，增加对应真实/固定样本评估。

测试只证明覆盖到的工程行为；内部评估不能替代操作员独立使用和真实 SKU 结果。

## 8. 继续、降级和停止规则

| 观察 | 决策 |
|---|---|
| 单槽位实验出现未能被门禁捕获的关键事实错误 | 冻结该路线；补证据、规则或改架构，不能扩槽位 |
| 生成路线没有显著运营价值，或收益小于额外成本/审核负担 | 停止生成优先扩展，保留 v2/确定性路线 |
| provider 不支持任务查询或可靠去重 | 不接真实付费流量；更换 provider 或增加受控代理层 |
| 数据外发授权缺失/撤回 | 禁止相应调用，降级到本地/确定性能力 |
| VLM 严重错误漏检不可接受 | 仅作提示或关闭；人工门保持 |
| 首 5 个 SKU 的成本或耗时不可接受 | 调整候选数/轮次/槽位，或停止，不进入 15-SKU 试点 |
| 试点中出现关键事实错误 | 相关 OutputVersion 无效；暂停同类路线并加入回归样本 |
| 环境无法提供完整回归所需资源 | 标记 `unverified`，解决环境后重跑，不使用 `--force` 制造结论 |
| 完成需要新增人像、竞品外发、自动发布或公开 SaaS | 停止并请求新的产品授权；不得静默扩 Goal |
