## 0. 摘要

**一句话定位**

> 面向电商 SKU 的 AIGC 商品视觉素材生产系统：把「商品参考图 + 经确认的商品事实 + 业务选择的图型清单」编译为可执行、可复现、可断言的图像任务，输出供设计人员筛选与精修的**事实性视觉底图**。

**三个核心判断**（全文的承重墙）

| # | 判断 | 它挡掉了什么 |
|---|---|---|
| 1 | **模型只能创作它不承担事实责任的部分** —— 即环境。物体事实归实拍照片，文字断言归卖家 | 挡掉了"靠提示词要求模型复用同一个主体"的整条思路 |
| 2 | **主体一致性必须是数据层面的约束，不是提示词层面的期望** | 挡掉了"多调几遍提示词"，把一致性从感觉变成 `subject_hash` 断言 |
| 3 | **修复动作必须落在出错的那一层上** —— 主体/文字/环境三层，责任严重性与修复成本分级定价 | 挡掉了"整张重出"作为默认修复手段 |

**成本结构的根本变化**：链路从「N 次整张生成」降为「1 次背景生成 + N 次确定性装配」。7 坑位场景下模型调用数 **7 → 1**。

## 1. 定位与边界

### 1.1 系统做什么

| 层次 | 职责 |
|---|---|
| 输入 | SKU 商品参考图、业务确认的商品事实、目标平台与图型需求 |
| 处理 | 商品事实结构化 → 事实门禁 → 图型任务拆分 → 主体资产一次性生成 → 提示词与参数编排 → 多供应商执行 → 分层装配 → 校验归档 |
| 输出 | 按 SKU 与图型定位的候选视觉底图 + 可复现的 `plan` + 可断言的 `subject_hash` + 结构化日志 |
| 闭合 | 人工评审记录回写，badcase 按层路由到改进点 |

### 1.2 系统不做什么（四条绝对边界）

1. **不负责最终嵌字与版式定稿** —— 文字由卖家提供、设计定稿；
2. **不负责平台合规验收** —— 只做程序可判定的规则预检（尺寸/白底/占比），不做人工审核替代；
3. **不负责自动上架**；
4. **不声称对结果有确定性控制** —— 环境层天生是生成性的，只能收窄不能锁定。

> 边界必须**主动声明**。系统聚焦"首轮候选生成"，反而比假装是"全链路平台"更可信、更好防守。

### 1.3 角色与职责（四类）

| 角色 | 负责 | 不负责 |
|---|---|---|
| **运营/业务** | 定义"为什么生成、生成什么"；提供不可由图片推断的事实；确认卖点有真实依据 | 模型权重、采样参数 |
| **设计** | 候选筛选、局部修复、排版嵌字、最终导出；标注不可用原因 | 定义商品事实 |
| **系统** | 重复、可规则化的工作：分析、校验、拆分、编排、调用、归档 | 替代业务做图型决策 |
| **开发者** | 字段与图型分类、模板与适配器、badcase 归因、指标口径、能力边界控制 | 声称超越证据的能力 |

### 1.4 证据等级约定（贯穿全文）

本方案的每一条能力声明都标注等级；**看到 A/B/C/D 才敢写进简历**。

| 等级 | 定义 | 可用的动词 |
|---|---|---|
| **A 直接实现** | 代码/配置/运行产物可直接证明 | 实现、搭建、支持 |
| **B 合理抽象** | 多段代码共同支撑一个抽象，但无同名模块 | 设计、构建、编排 |
| **C 待补证** | 可能做过，但缺代码/日志/原始数据 | 暂不写完成态 |
| **D 扩展方案** | 仅技术设想或行业可选路线 | 可规划、可扩展 |

## 2. 第一性原理

### 2.1 起点：一对方向相反的约束

卖家必须让图片同时满足：

- **可售** —— 好看、有说服力、推转化
- **诚实** —— 与实物一致，否则是「实物不符 + 虚假宣传」

"好看"可以由生成承担，"诚实"不能。**整条链路的设计，就是这条分界线画在哪。**

### 2.2 分解：一张商品图只有三样东西

| 组成 | 承载什么 | **谁持有这个事实** | 错了会怎样 | 模型可否生成 |
|---|---|---|---|---|
| **物体** | 商品长什么样 | **实拍照片** —— 唯一见过它的东西 | 实物不符 → 平台处罚 + 法律风险 | **否** |
| **文字** | 卖家对商品的断言（"保温 24 小时"） | **卖家** —— 只有他知道 | 虚假宣传 → 法律风险 | **否** |
| **环境** | 处在什么场景、什么氛围 | **没有人** —— 环境不是事实，是设计 | 图不好看 → 只影响转化 | **是（全部）** |

### 2.3 判据

> **模型只能创作它不承担事实责任的部分。**

模型的处境很具体：它既没见过这个杯子（不是"物体"事实的持有者），也不知道保温几小时（不是"断言"事实的持有者）。
**它唯一有资格创作的地方，恰恰是它没有任何事实主张的地方 —— 环境。**

这条判据比其他表述更根本：后者描述症状（"能不能被对照发现"），它归属责任（"谁有权做这个主张"）。

**反例的价值**：模型直出（native）时能自动把卖点用引线连到杯身对应部位，版式更自然 —— 但**那份引线之所以画得出来，恰恰是因为模型看见了杯子**，而"看见杯子"正是它越权做物体事实主张的那一刻。**版式收益换不来事实失控。**

### 2.4 四条不变量及其逻辑根据

四条不变量不是工程约定，各自能一路推回 2.2 那张表：

| # | 不变量 | 逻辑根据 | 强制时刻 | 机制 |
|---|---|---|---|---|
| **A** | 主体只有一份，N 个坑位读同一个 PNG | **主语同一律**：整组图回答的是"这个东西怎么样"；若各组里的东西各不相同，这组断言没有共同主语 | S2 产出，S4 只读 | 文件系统 + `subject_hash` 写入每路日志 |
| **B** | 生成层看不见主体（提示词禁产品类词） | 看不见主体 ⇒ 无法对物体做事实主张；"顺手画一个杯子"就是**虚构事实** | S3 组装提示词 | `SUBJECT_EXCLUSION_CLAUSE` 无条件拼接 |
| **C** | 文字层不参与画面生成 | 文字是**断言**，断言必须有出处，模型不是那个出处 | S4 叠字与生成代码路径分离 | overlay 分支独立 |
| **D** | 位置 1 零模型调用 | 位置 1 的**信息密度 100% 是事实**，模型合法作用域为空 | S4 的 `white` 分支 | 无网络调用 |

> **D 的强理由**：不是"平台规则不允许"，是**没有环境可生成**。平台规则只是这个事实的外部投影。

### 2.5 判据的三个推论

**推论 ①：坑位不是平台的格位，是买家决策问题的枚举。**

买家从点进来到下单要问完一串问题：这是什么 → 有什么好处 → 多大 → 用在什么场景 → 质量如何 → 买回来有什么 → 比别的好在哪。**"七张"不是数字约定，是这串问题的枚举长度。** 平台上限 9 张、桌面端显示 7 张，都是外部约束。

> 工程含义：模板**不该从运营现存的手工七张反向抽取**，而应先枚举买家问题，再拿现状对照 —— 现状可能答错了问题，也可能漏了问题。**照抄现状 = 把现状的错误一并固化成模板。**

**推论 ②：分期依据不是技术风险，是决策阶段。**

- **决策必需**（没有它没法看）：主图 + 卖点
- **决策充分**（没有它下不了决心）：规格 / 场景 / 细节 / 内容物 / 对比

第一版做前两张，理由从"先跑最难路径"升级为**"先交付决策必需的两问"**。

**推论 ③：验收口径。** 不再需要"你挑，挑不出来算不合格"。

> **验收 = 每个买家问题都被一个「可发布的事实性回答」覆盖。**
> "可发布" = 过平台规则；"事实性" = 物体与文字未被模型改写。

### 2.6 事实责任分配的工程含义

**修复成本按责任严重性分配，不按技术难度分配。**

| 层 | 失败的严重性 | 处置强度 | 重做成本 |
|---|---|---|---|
| 主体层 | 实物不符（平台 + 法律） | **零容忍** —— 宁可要求重拍，也不许模型补画 | 需重拍 |
| 文字层 | 虚假宣传（法律） | **严格** —— 字体绘制，必然正确 | ~0.1s · ¥0 |
| 环境层 | 图不好看（转化） | **宽容** —— 随便重生成 | ~1s（纯色底）/ ~70s（生成背景） |

这正是"重做三粒度"的定价依据：**不是按耗时定价，是按责任层级定价。**

## 3. 领域模型

### 3.1 对象图谱

```
SKU (商品变体 · 任务归属单位)
 └── ProductProfile (商品事实档案 · 带来源与置信度)
      └── ImageTask[] (图型任务 · 业务目的单位)
           └── Attempt[] (一次实际提交 · 计费与重试单位)
                └── Candidate[] (一次提交返回的一张图 · 评审单位)
                     └── Review (人工判定 + 结构化拒绝原因)
```

**为什么必须分层**：如果一个任务生成 4 张图，技术成功率按 **ImageTask** 统计，人工可用率按 **Candidate** 统计。**不能用 4 张图片把一个成功任务膨胀成 4 个成功任务。**

### 3.2 ProductProfile 字段的三种语义

| 语义 | 说明 | 示例 | 处理原则 |
|---|---|---|---|
| **商品事实** | 商品客观是什么 | 颜色、轮廓、真实尺寸、配件数量、接口位置 | 进入生成任务后是**约束**，不是创意建议 |
| **视觉特征** | 图片中可观察到的表现 | 哑光质感、圆柱轮廓、透明仓体 | 服务于 Prompt，**不一定等于工程规格** |
| **营销意图** | 希望图片传达什么 | 目标人群、场景、氛围、风格 | 可以变化，**不得反向修改商品事实** |

> 三类必须分开，否则"现代简约"这种营销风格会被错误当成商品结构描述。

### 3.3 字段来源与置信度模型

每个高风险字段至少记录四元组：`value` / `source` / `confidence` / `confirmed`。

| source | 含义 | 默认处理 | 可进入的图型 |
|---|---|---|---|
| `vision_observed` | 模型从图片直接观察 | 可用于初稿；关键字段需人工检查 | 全部 |
| `vision_inferred` | 模型根据外观推断 | 仅作候选 | **不进事实型图片** |
| `operator_input` | 运营手工录入 | 需格式与范围校验 | 全部（受校验约束） |
| `master_data` | 来自商品主数据 / PIM | 高可信事实 | 全部 |
| `operator_confirmed` | 人工确认过的模型结果 | 可作为生成保护字段 | 全部 |

> `confidence` **不是装饰字段**。它必须影响流程：低可信材质不能进入"100% 真丝"表达；未确认尺寸不能创建规格图。**一个字段如果没有任何代码位置消费它的置信度，它就是死字段。**

### 3.4 事实门禁规则（硬门禁表）

| 图型 | 必需事实 | 缺失时的处理 |
|---|---|---|
| 白底主图 | 主视角参考图 + 真实颜色轮廓 | 阻止创建 |
| 核心卖点底图 | 已确认卖点（有出处） | 降级为无文字主体图 |
| 尺寸规格图 | 已确认规格 + 单位 | **阻止创建**（不得由模型推测尺寸） |
| 材质图 | 真实材质局部图 + 业务确认材质名 | 降级为"细节图"，不写材质断言 |
| 使用场景图 | 商品主参考图 + 目标场景 | 可用默认场景，标记为弱 |
| 对比图 | 双方真实图片 / 可验证条件 | **阻止创建**（无证据宁可不生成） |
| 组合/内容物图 | 每件商品的参考图 | **阻止创建**（避免虚构商品） |

### 3.5 图型的三层分类（最容易被讲乱的地方）

| 层 | 是什么 | 举例 | 生命周期 |
|---|---|---|---|
| **业务套图层** | 一次上新/营销要交付的一组图 | "亚马逊上新的七张" | 每次业务决策 |
| **页面模块层** | 承载位置 | 主图位、PDP 详情模块、广告位、社媒位 | 随平台/渠道变化 |
| **执行图型层** | 可独立生成与评审的任务 | 白底、细节、材质、场景、对比、组合 | 与模板/代码一一对应 |

> **"详情页"属于页面承载层，不是单一执行图型。** 一张详情页由主视觉、材质、结构、场景、规格、对比等多个模块组成。把容器概念与执行图型混为一谈，是分类混乱的根源。

### 3.6 执行图型的六类业务逻辑

图型不按模型能力分类，**按它帮消费者解决什么决策问题分类**：

| 一级分类 | 消费者问题 | 典型执行图型 | 模型参与度 |
|---|---|---|---|
| **识别类** | 这是什么、长什么样？ | 白底主图、标准展示图 | 零（确定性合成） |
| **理解类** | 有哪些结构、材质、特点？ | 细节结构图、材质图、卖点底图 | 零 / 仅背景 |
| **代入类** | 在真实环境里怎么用？ | 使用场景图、模特展示图 | **高（唯一合法生成域）** |
| **比较类** | 前后/型号/方案差异？ | 对比图 | 零（需真实依据） |
| **关系类** | 套装里有什么、关系如何？ | 组合图、多产品图 | 零 / 仅背景 |
| **承接类** | 页面下一段传达什么？ | 详情页模块任务 | 混合 |

## 4. 总体架构

### 4.1 六模块 + 二横切

```
业务入口（SKU 资料、目标渠道、图型选择）
  │
  ▼
①  商品信息解析与校验      ── ProductProfile（含来源与置信度）
  │                              ▲
  │                              │  横切 A：商品事实与视觉一致性控制
  ▼                              │  （贯穿数据 → Prompt → 参考图 → 模型）
②  图型任务配置            ── ImageTask[]
  │                              ▲
  ▼                              │  横切 B：平台 / 投放位置约束
③  Prompt 与生成参数编排    ── GenerationRequest      （贯穿任务配置 → 参数 → 验收）
  │
  ▼
④  供应商适配与任务执行      ── TaskResult / Error
  │
  ▼
⑤  结果归档                ── 候选资产 + 可复现 plan + 断言
  │
  ▼
⑥  人工评估与反馈          ── Review / badcase → 回流到 ① ③
```

**两个横切的准确含义**：

- **一致性控制不是独立模块**，而是在四个位置施加约束：数据层（保护字段）/ 编排层（复用描述 + 负面词 + Style Lock）/ 输入层（按图型选参考图）/ 模型层（高风险任务升级控制手段）。**它不是最后调用一次的函数。**
- **平台适配是贯穿上下文**，不是事后万能转换函数。它影响：图型组合、比例分辨率、主体尺度与安全区、是否允许图内文字、导出与审核要求。

### 4.2 模块 I/O 与证据

| 模块 | 输入 | 核心职责 | 输出 | 主要失败 | 等级 |
|---|---|---|---|---|---|
| 商品信息解析 | 商品图、模型配置 | 多图编码、视觉分析、JSON 提取 | 商品信息草稿 | 图不可读、API 失败、JSON 非法、事实误判 | **A** |
| 商品信息校验 | 草稿 + 人工事实 | 区分可见/推断/精确字段 | 已确认 ProductProfile | 未确认事实污染下游 | C（设计态） |
| 图型任务配置 | ProductProfile、平台、业务选择 | 拆分图型、绑定比例/数量/参考图 | ImageTask[] | 类型不适配、资料不足 | **B** |
| Prompt 编排 | ImageTask、事实、模板 | 组织主体/构图/场景/风格/负面词 | Prompt | 约束冲突、提示过载、事实遗漏 | **A** |
| 参数编排 | 图型、provider 能力 | 模型、画幅、参考图、超时 | GenerationRequest | 参数不兼容 | **A** |
| 一致性控制 | 保护字段、参考图、Style Lock | 降低主体与风格漂移 | 约束集合 | 结构幻觉、风格漂移 | **B/D** |
| 供应商适配 | GenerationRequest | 转换请求与响应格式 | provider 请求/结果 | 认证、限流、协议变化 | **A** |
| 任务执行 | provider 请求 | 同步调用 / 异步提交轮询 | TaskResult | 超时、远端失败、进程中断 | **A** |
| 结果归档 | 图片、结果、错误 | 下载、命名、保存上下文 | 本地候选资产 | 下载失败、文件冲突、上下文丢失 | **A** |
| 人工评估 | 候选图、事实、目标 | 可用性判断与原因标注 | Review / badcase | 标准不一致、缺双人复核 | C |

### 4.3 模块依赖原则（五条）

1. 商品信息未确认，**不应创建高风险图型任务**；
2. 图型任务**只描述业务目的**，不直接包含供应商私有字段；
3. 编排依赖任务，但**执行层不得重新决定业务目的**；
4. 一致性策略**必须知道要保护哪些事实**，不能只写"保持一致"；
5. 评估结果**必须能回到 SKU / 图型 / 模板 / provider**，否则无法定位改进点。

### 4.4 与"直接调 API"的差别

API 调用只是执行末端。调用之前至少完成三层工作：

1. 把多张商品图分析成**可消费的结构化商品事实**（带来源与门禁）；
2. 按图型组织**不同的构图、场景、参考图和负面约束**；
3. 适配**同步/异步供应商协议**，并处理状态、下载、失败隔离和脱敏日志。

> 严格地说，当前形态是**工作流原型**，不是生产级平台。"不是简单调 API" ≠ "已具备完整平台工程能力"。

## 5. 图型体系

### 5.1 执行图型枚举（9 种，A 级）

`white_bg` · `key_features` · `selling_pt` · `material` · `lifestyle` · `model` · `multi_scene` · `detail`（新增领域类型）· `bundle`（新增领域类型）

### 5.2 类目 × 图型矩阵

| 类目 | 推荐 | 条件性使用 | **高风险（禁/慎）** |
|---|---|---|---|
| 服装/穿戴 | 白底、材质、模特/场景 | 尺寸、搭配、组合 | 单图生成真实背面、多角度结构 |
| 3C 数码 | 白底、接口细节、场景 | 尺寸、组合、对比 | 爆炸图、内部结构、虚构参数 |
| 家居家电 | 白底、结构、材质、场景 | 尺寸、配件组合 | 功能效果、承重对比 |
| 美妆个护 | 白底、包装细节、质地、场景 | 使用步骤、组合 | **功效前后对比、成分与认证** |
| 食品 | 白底、包装、场景、组合 | 制作步骤、规格 | **虚构配料、份量、营养效果** |

> 矩阵的作用是**门禁**，不是自动化决策。系统给推荐，业务保留最终选择权。

### 5.3 平台规范（控制面常量）

| 平台 | 推荐尺寸 | 主图硬约束 | 文案语言 | 套图优先级 |
|---|---|---|---|---|
| 淘宝/天猫 | 800×800 (1:1) | 纯白底，商品 ≥80% | 中文 | 主图 + 卖点 |
| 京东 | 800×800 | 白底无水印，居中 | 中文（专业理性） | 主图 + 核心卖点 |
| 拼多多 | 750×750 | 白底或场景（白底转化高） | 中文（简洁直白） | 主图 |
| 抖音/小红书 | 1:1 或 3:4 / 1080×1440 | —— | 中文（年轻化） | 场景 + 模特 |
| **Amazon** | **≥1000，推荐 2000×2000** | **纯白 RGB(255,255,255)，商品 ≥85%，禁文字/水印/边框/装饰，禁多商品** | 英文 | 主图 |
| Shopify/独立站 | 2000×2000 或 4:3 | 自由度最高 | 品牌化多语言 | 模特 + 场景 |
| eBay | ≥500，推荐 1600×1600 | 白底为主 | 英文 | 主图 |

**导出统一规格**：sRGB / JPEG q92 / 长边 1600（≥1600 才启用放大镜）/ 单张 ≤10MB / 文件名含产品标识（UPC/EAN/ISBN/JAN），否则过审受阻。

### 5.4 图型 × 三层 × 生成调用（亚马逊七坑位）

| 坑位 | 主体层 | 背景层 | 文字层 | **生成调用** |
|---|---|---|---|---|
| 1 主图 | 实拍抠图 · 居中 85% | 纯白底，不生成 | — | **0** |
| 2 卖点 | 实拍抠图 | 纯色底，不生成 | 叠字 | **0** |
| 3 规格 | 实拍抠图 | 纯色底，不生成 | 叠字 + 标注线 | **0** |
| 4 场景 | 实拍抠图 | **生成场景 · 需环境融合** | 叠字 | **1** |
| 5 细节 | 实拍局部裁切 | — | 叠字 | **0** |
| 6 内容物 | 实拍多件合照 | 纯色底，不生成 | 叠字 | **0** |
| 7 对比 | 实拍抠图 + 竞品图 | 纯色底，不生成 | 叠字 + 标注线 | **0** |

> **模型只在"背景层"列有标记的位置出现。** 整条链路从"7 次整张生成"降为 **1 次背景生成**。
> 位置 2/3/6 由"生成留白"降为纯色底是最实际的简化：卖点图解与规格图要的是**可读性**，纯色底更清晰、更便宜、效果不会更差。**能用确定性做的，就不调模型。**

## 6. 控制面资产

控制面 = 决定系统行为的**声明式配置**。它与代码的耦合必须显式，否则产生死字段。

| 资产 | 内容 | 消费方 |
|---|---|---|
| **坑位/图型规范表** | 用途、尺寸、是否允许文字、主体占比、背景类型、校验强度、渲染路径 | S3 规划、S4 渲染、S5 校验 |
| **平台规范库** | 尺寸、主图规则、文案语言、套图优先级 | S0 收件、S3 规划、S6 导出 |
| **视觉模板库** | 构图、镜头、光线、留白、版式变体 | S3 编排 |
| **Campaign Style Lock** | 色板、冷暖调、背景语言、尺度留白、图标风格 | S3 编排（本批次逐张复用同一段） |
| **品牌资产** | 字体文件、品牌色、Logo（**确定性层**，非生成层） | S4 叠字 |
| **事实门禁表** | 图型 → 必需事实 → 缺失处理 | S1 门禁 |

### 6.1 规范表字段字典（`slots.yaml` 语义）

| 字段 | 取值 | 说明 |
|---|---|---|
| `render_path` | `compose` / `generate` / `generate_then_text` | 决定是否调模型、是否叠字 |
| `bg_kind` | `white` / `solid` / `generated` / `crop` | 画布来源，决定是否调模型 |
| `text_mode` | `none` / `overlay` / `native` | 文字由谁产生 |
| `text_allowed` | bool | **平台强制项**，false 时不可被命令行覆盖 |
| `subject_placement` | 落点 + 占比 | 接缝控制（视角/尺度） |
| `lighting` | 光位描述 | 接缝控制（让背景迁就主体） |
| `validate_level` | `strict` / `medium` / `loose` | 校验强度 |

### 6.2 关于 `native` 的结论

| `text_mode` | 文字怎么来 | 可复现 | 改一个字 |
|---|---|---|---|
| `none` | 不出字 | — | — |
| `overlay`（默认） | 生成层禁字 + 代码叠字 | ✅ | 重画文字层 · 0.1s · ¥0 |
| `native` | 模型直出 | ❌ | 重出整张 · ~70s · 1 次调用 |

`native` 唯一不可替代的价值是**引线标注**（文字与画面产生空间关系）。**但 α 路线下它结构上不成立**：模型看到的背景是**一个没有主体的空场景**，它不知道杯子在哪，画不出指向杯子的引线。

> 主体确定性 ⇒ 背景必须"看不见主体" ⇒ native 失去存在理由 ⇒ **结构性排除，不是暂缓。**

### 6.3 死字段禁令

> **每条不变量/配置必须有一个消费它的代码位置，否则就是死字段。**
> 本项目已出现过三个：`text_style`、`DASHSCOPE_IMAGE_MODEL`、`text_layout` —— 都是声明了但没人读。
> **准入规则：新增字段必须同时提交「谁读它」的证据（代码位置或消费方），否则不准入。**

## 7. 接口契约：每个环节的输入 / 处理 / 输出

八个环节。**S1 与 S2 可并行**（都只依赖 S0）；**S3 是全链路唯一的前置**（N 路都读它的产物）；**S4 是唯一的扇出点**。

> 与 `架构设计.md` 的 E0–E5 映射：S0=E0；S1/S2 是原 E1 拆分为"事实建档"与"主体资产"两个独立关注点（这是本次设计的实质改进 —— 事实与像素是两件事，不该挤在一个环节）；S3=E2；S4=E3；S5=E4；S6=E5；S7=新增。

### S0 收件与体检

| | |
|---|---|
| **输入** | `inbox/<UPC>/`：`main.jpg`（商品原图）、`copy.json`（卖点文案，含出处）、可选 `competitor.jpg`、可选 `facts.json`（规格/材质等业务事实） |
| **处理** | ① UPC 格式校验；② 原图可解码且 ≥1000px；③ 文案非空、条数 ≤6、**每条带 source**；④ **原图体检**：检测是否含文字/水印/多件商品/强透视 |
| **输出** | `job` 对象：`{upc, src_path, copy[], competitor_path, facts, site, category}`；**或拒收** |
| **失败** | **拒收** —— 入口拦，不产生任何下游动作 |

> ④ 是关键：工具**修不了**不合规的输入（水印压在主体上抠不掉、道具擦不净）。**必须在入口拦，不是等出口报错。**

### S1 事实建档与门禁

| | |
|---|---|
| **输入** | `job.src_path`（+ 多视角图）+ `job.facts` + 视觉模型配置 |
| **处理** | ① 多图编码为多模态消息；② 视觉模型输出结构化 JSON；③ **字段打标**：`vision_observed` / `vision_inferred`；④ **与 `job.facts` 合并**，冲突时以业务事实优先；⑤ **事实门禁**：按 3.4 表判定每个图型是否可建 |
| **输出** | `ProductProfile`：每字段 `{value, source, confidence, confirmed}` + `gated[]`（被拦的图型及原因） |
| **失败** | 单字段失败 → 标 `unknown`，不臆造；全部失败 → 降级到"无事实模式"（只允许纯视觉图型） |

> **Prompt 必须明确要求"无法确认时返回未知，而不是补全"。** 规格/成分/认证/功效字段**只接受业务资料**。

### S2 主体资产（全局唯一一次抠图）

| | |
|---|---|
| **输入** | `job.src_path` + 抠图配置（`CUTOUT_MODE`、模型目录） |
| **处理** | ① 加载 BiRefNet 会话（**本地优先，缺模型不下载**，直接降级 floodfill）；② 抠图得 RGBA；③ 取最大前景、去碎斑；④ 算 bbox / alpha 覆盖率 / **`subject_hash`**（alpha 通道 sha256 前 12 位） |
| **输出** | `subject.png`（RGBA）★**唯一共享资产** + `subject.json`：`{mode, bbox, coverage, subject_hash, warnings[]}` |
| **失败** | **全局失败** —— N 路都依赖它，不能局部降级 |

> `subject_hash` 是"整组图主体同一"的断言依据，**必须在这里算出并落盘，不能是常量**。

### S3 任务规划

| | |
|---|---|
| **输入** | `ProductProfile` + `job.copy[]` + `subject.json` + `config/slots.yaml` + 业务图型选择 |
| **处理** | ① 读图型模板（用途/尺寸/允许文字/主体占比/背景类型/校验强度）；② **按类目推荐默认图型组**，业务可增删；③ 文案条目**分配到各图型**；④ 生成排版参数（字号/位置/色值）；⑤ **仅 `generated` 背景**生成提示词（禁产品本体 + 描述环境 + 光位迁就主体）；⑥ 算 `slot_hash` |
| **输出** | `plan.json`：每条 `{slot_id, image_type, purpose, bg_kind, subject_placement, callouts[], text_mode, prompt?, validate_level, slot_hash}` |
| **失败** | 无 —— 纯确定性。文案不足时降级（该图型少几条），不报错 |

> **plan 是这条流水线唯一的状态。** 人可以在这里改（改文案、改排序），改了下游全部重放。**落盘即"可复现"的定义：复现的是 plan，不是图**（图有随机性）。

### S4 单路渲染（×N，彼此无依赖）

唯一有分支的环节，内部三个子步。

**S4a 画布**

| | |
|---|---|
| **输入** | plan 单条 + `subject.png`（`crop` 时用原图） |
| **处理** | 按 `bg_kind` 分派：`white` → 纯白 RGB(255,255,255)；`solid` → 品牌色平铺；`crop` → 原图按比例裁切；`generated` → **调模型**出无主体背景 |
| **输出** | `canvas.png` 1600×1600 |
| **失败** | 单路失败，写日志，不影响其余路 |

**S4b 贴主体**

| | |
|---|---|
| **输入** | `canvas.png` + `subject.png` + `subject_placement` |
| **处理** | ① 等比缩放主体到目标占比；② 按落点定位；③ 从 alpha 底部轮廓生成**接触阴影**；④ alpha 合成 |
| **输出** | `composed.png` |

**S4c 叠文字**

| | |
|---|---|
| **输入** | `composed.png` + `callouts[]` + 品牌色 / 字体文件 |
| **处理** | 用字体文件逐条绘制标题与正文 —— **不让模型画字** |
| **输出** | `final.jpg` 1600×1600 sRGB |

> `crop` 路径下 S4b 空跑（裁切结果本身就是主体）。该路是纯确定性。

### S5 校验

| | |
|---|---|
| **输入** | `final.jpg` + 该图型 `validate_level` |
| **处理** | `strict`（主图）：白底纯度 / 主体占比 ≥85% / 边缘带纯净 / 无文字块 / 尺寸 / 命名；`medium`（卖点/规格/对比）：尺寸 + 文字存在性 + 无水印；`loose`（场景/细节/内容物）：尺寸 |
| **输出** | `validation`：`{passed, failed[], metrics{}}` 写进日志 |
| **失败** | **不阻断交付** —— 标 FAIL 交人工，运营看到的就是"这张要重做" |

> 校验在写盘之前跑，验的是自己刚生成的图。**所以它只能验它定义得了的东西**（尺寸、白底、占比），验不出"抠干净了没 / 有没有错字"。**不得把"程序校验通过"说成"质量合格"。**

### S6 归档交付

| | |
|---|---|
| **输入** | N 张 `final.jpg` + `plan.json` + `subject.json` + `profile.json` + 全部日志 |
| **处理** | ① 按 `{UPC}_{序号}_{用途}.jpg` 命名；② 写 `run.jsonl` 逐环节结构化日志；③ 目录名加微秒防并发撞车；④ 汇总通过/失败清单 |
| **输出** | `out/<UPC>_<时间戳-微秒>/`：N 张图 + `plan.json` + `subject.png/json` + `raw/` + `run.jsonl` |

### S7 评审回流

| | |
|---|---|
| **输入** | 候选图 + 商品事实 + 图型目标 |
| **处理** | ① 判定 `可用 / 可修 / 拒绝`；② 结构化拒绝原因；③ **按层归因**：主体问题 → 数据层；文字问题 → 叠字层；环境问题 → 模板层；④ 汇总图型/类目/provider 维度指标 |
| **输出** | `Review` + badcase 数据集 + 模板优化依据 |
| **等级** | **C** —— 业务闭环必需，但当前缺直接代码证据。面试按"设计态"表述 |

**结构化拒绝原因枚举**（8 项）：

`subject_shape_drift`（主体轮廓/结构错误）· `color_or_pattern_drift`（颜色/印花错误）· `component_hallucination`（部件增减）· `material_mismatch`（材质不可信）· `composition_unusable`（构图不可用）· `scene_mismatch`（场景不合理）· `text_artifact`（乱码/多余文字）· `platform_mismatch`（比例/留白不符）

### 7.1 流程控制规则（七条）

1. **唯一顺序依赖是 S0 → (S1 ∥ S2) → S3 → S4。** 抠图必须在 N 路渲染前完成，且**只做一次**。
2. **S1 与 S2 可并行** —— 事实建档（语义）与主体资产（像素）互不依赖，是两条独立关注点。
3. **S4 内部 N 路无依赖**，可串可并。因为只有场景图调模型，实际耗时 ≈ 抠图 26s + 生成 70s + 装配数秒 ≈ **2 分钟**。
4. **失败隔离按层级分。** S2 失败 = 全局失败（没有主体，N 路全废）；S4/S5 单路失败 = 局部失败（写日志继续，其余路照常交付）。
5. **重做 = 重放 plan 第 k 条**（`--only k`）。只重跑 S4(k) → S5(k) → S6，不重新规划、不重新抠图。改文案只动 `plan.json` 的 `callouts`，`subject.png` **一个字节都不变**。
6. **重做必须先选原因**（文案/位置/背景）—— 这不是 UI 设计，是 §2.2 三层的直接映射：**修复动作必须落在出错的那一层上。**
7. **落盘边界 = 可复现边界。** 落盘的是 `subject.png` / `plan.json` / `profile.json` / 日志 —— 这四样决定了能不能重做、能不能断言、能不能算钱。其余中间产物（canvas / composed）只作调试用。

## 8. 运行时与流程控制

### 8.1 状态机

**ImageTask 状态**：`created` → `validated` → `submitted` → `running` → `succeeded` / `failed` / `timed_out`
**SKU 汇总状态**：`all_succeeded` / `partially_succeeded` / `all_failed`

> 注意：脚本级实现的实际状态很轻，**不应声称已有持久化状态机**（C 级）。生产化必须先做状态持久化。

### 8.2 部分成功可交付（核心业务策略）

8 种图型中 2 种失败时，合理返回是 **6 个成功结果 + 2 个失败记录**，而不是让整个 SKU 只返回一个布尔值。

- 调用方可**交付成功图片**并**只重跑失败类型**；
- 这是"单张重做"能被运营接受的前提；
- 每路**独立输出目录**（目录名加微秒），避免并发运行互相截断日志。

### 8.3 幂等与重放

- **幂等键**：`sku_id + image_type + profile_version + strategy_version + attempt`；
- 重试前**先查询已有远端任务和本地结果**，避免重复计费；
- 提交远端任务后**立即保存 `provider_task_id`**，进程重启后可恢复轮询，而不是重复提交。

### 8.4 并发与限流

| 维度 | 策略 |
|---|---|
| 粒度 | 每个图型作为**独立消息** |
| 并发度 | 按 provider 配置并发上限，避免单 SKU 串行过慢、也避免触发限流 |
| 退避 | 指数退避 + 抖动；尊重 `Retry-After` |
| 成本 | 按 provider / 模型 / 租户记录 QPS、并发、单图成本与预算 |

> **路由不能只看"API Key 是否存在"。**

### 8.5 降级链

| 环节 | 主路径 | 降级 |
|---|---|---|
| 抠图 | 本地 BiRefNet | floodfill（**缺模型不下载**） |
| 生成尺寸 | 1600×1600 | 1024×1024 → auto |
| 生成模型 | 主模型 | 备用 provider（**能力差异由适配器吸收**） |

**位置 4 的 `inpaint_bg` 分支预留但未实现**，必须在 `slots.yaml` 与代码中**显式标注**（不得成为第四个死字段）。

### 8.6 接缝控制（本架构唯一的新增风险）

位置 1 没有接缝问题（纯白底无缝可拼）。位置 2/4 有：主体与背景来自两个来源，硬拼会露。

| # | 失败模式 | 根因 | 对策 |
|---|---|---|---|
| 1 | **悬浮感**（像贴纸） | 主体与背景之间没有接地关系 | 接触阴影（合成层通用） |
| 2 | **光照/色温错位** | 两个来源各自成图 | **让背景迁就主体**：把主体光位写进提示词（`lighting` 字段） |
| 3 | **视角与尺度错位** | 生成层不知道主体多大、从哪看 | 提示词约束视角 + 规范表定义落点（`subject_placement`） |

> 三个对策指向同一原则：**接缝不能靠"改主体"解决，只能靠"约束背景 + 后处理弥合"。**
> 这是 §2.3 判据的直接推论：主体是事实，环境是设计 —— **冲突时只能改设计，不能改事实。**

**α / β 路线决策**：

| | α：合成后适配 | β：mask 补背景 |
|---|---|---|
| 做法 | 模型只画空背景，主体确定性贴入 | 主体先贴好，mask 遮背景区，用 image-edit 补背景 |
| 主体保真 | **绝对**（像素级不变） | **近似**（保留区是否被改动未知） |
| 接缝自然度 | 靠工程；场景图可能偏"假" | 天然（模型看得见主体与光） |
| 可验证性 | **主体哈希可断言** | 只能肉眼看 |

> **决定：第一版走 α。** β 的前置条件是一次实测：验证 image-edit 在 mask 外区域到底有没有改动。**在验证之前，β 不是选项。**

## 9. 一致性控制（五层）

### 9.1 先区分两种一致性

| 类型 | 要求 | 由谁解决 |
|---|---|---|
| **商品事实一致性** | 不同候选图中颜色、轮廓、图案、部件数量、Logo 位置与真实商品一致 | 参考图 + 事实 + Prompt 锁（**不是 Style Lock**） |
| **批次视觉一致性** | 同套图的色板、光线、背景语言、构图节奏、留白协调 | Campaign Style Lock |

> **Style Lock 写得再严格，也不能替代参考图和结构控制来解决第一类问题。**

### 9.2 五层控制

| 层 | 手段 | 作用 | 上限 |
|---|---|---|---|
| **① 商品事实结构化** | 保护清单（主色/关键结构/透明部件/禁止项） | 所有图型共享同一保护清单，给人工评审判断标准 | 不能直接控制像素 |
| **② 参考图约束** | 按图型选参考图；edits/图生图；多图输入 | 让模型**直接看到**商品 | 受模型能力、参考强度、视角、图片质量限制 |
| **③ Prompt 锁定** | 参考锁 + `print_design_lock` + 负面词 | 提高遵循概率，成本低，适用所有文本接口 | **软约束**，模型仍可能违反 |
| **④ Campaign Style Lock** | 同批次逐张复用同一段视觉规范 | 统一色板/光线/背景/留白/字体 | **不能**解决按钮数量、包装文字、几何结构 |
| **⑤ 可控生成扩展** | ControlNet / IP-Adapter / LoRA / ComfyUI | 空间控制 / 外观注入 / 品牌专项 | **当前无证据，D 级** |

### 9.3 手段选择表

| 问题 | 第一选择 | 何时升级 |
|---|---|---|
| 色板光线不统一 | Campaign Style Lock | 仍不稳定 → 固定工作流 / 后期调色 |
| 商品颜色印花漂移 | 事实 + 参考图 + Prompt 锁 | 高频失败 → IP-Adapter / 局部编辑 |
| 人物姿态不稳定 | 姿态参考 | 需严格动作 → ControlNet Pose |
| 构图轮廓失控 | 参考图 / 蒙版编辑 | 需严格空间控制 → ControlNet |
| 固定品牌角色长期复现 | 参考图 / IP-Adapter | 有足够数据和复用价值 → LoRA |
| **Logo / 包装文字必须准确** | **后期合成真实资产** | **不建议依赖生成模型重绘** |
| **未展示侧背面** | **补拍真实参考图 / 3D 资产** | **不用控制模型"猜真相"** |

> 最后两行是本系统最重要的两条**禁令**。它们直接来自 §2.3：模型不是物体事实的持有者，**不能让它代替补拍**。

### 9.4 一致性如何评估

- 主色是否一致；
- 商品轮廓与长宽比例是否合理；
- 关键部件数量、形状、位置是否一致；
- 图案、Logo、包装元素是否改变；
- 同批次背景、色温、光线、留白是否统一；
- **高风险字段实行人工硬判定**。

> CLIP / 视觉 embedding **只能辅助相似度排序，不能代替关键部件与事实核验**。

## 10. 失败模式与处理矩阵

| 阶段 | 失败模式 | 分类 | 自动重试 | 当前处理 | 目标处理 |
|---|---|---|---|---|---|
| 配置 | API Key 缺失 | 技术 | 否 | 明确退出 | 配置检查 + 健康状态 |
| 输入 | 本地图片不存在 | 技术 | 否 | 抛文件错误 | 阻止任务并提示具体文件 |
| 输入 | URL 临时超时 | 技术 | 有限 | 请求失败 | 指数退避 + 记录来源 |
| 输入 | 图片视角标错 | 事实/质量 | 否 | 可能静默选错 | **显式 `view` 字段 + 人工确认** |
| 输入 | 原图含水印/文字/多件 | 合规/质量 | 否 | —— | **入口拒收**（S0 ④） |
| 分析 | 多模态 429/5xx | 技术 | 有限 | 返回异常 | 分类重试 + provider 健康监控 |
| 分析 | 输出不是 JSON | 技术 | 一次修复 | 解析失败 | Schema 校验 + 保留 raw + 低温重试 |
| 分析 | 材质识别错误 | 事实 | 否 | 可能进入结果 | **标弱推断，必须人工确认** |
| 编排 | 未知图型 | 技术 | 否 | 可能通用 Prompt 回退 | **严格枚举拒绝** |
| 编排 | 无文字与嵌字冲突 | 质量 | 否 | 模型自行权衡 | `text_mode` 预校验 |
| 编排 | 缺规格却创建尺寸图 | 事实 | 否 | 无统一门禁 | **阻止任务**（事实门禁） |
| 提交 | 401/403 | 技术 | 否 | HTTP 异常日志 | 告警并停用 provider 配置 |
| 提交 | 429 限流 | 技术 | **是** | 异常 | 尊重 `Retry-After` + 抖动退避 |
| 提交 | 参数不支持 | 技术 | 否 | 异常 | **capability matrix 预校验** |
| 提交 | 内容审核拒绝 | 合规 | 否 | 异常 | 修改输入 + 人工复核 |
| 同步 | 请求超时 | 技术/未知 | **谨慎** | 异常 | **避免立即重提**，先查服务端语义 |
| 异步 | 远端 failed | 技术 | 视错误码 | 失败退出/记录 | 结构化错误分类 |
| 异步 | 本地轮询超时 | 未知状态 | 否 | 超时 | **保留 `task_id`，延迟恢复查询** |
| 下载 | URL 过期/超时 | 技术 | 有限 | 下载失败 | 尽快下载 + 有限重试 + 重查任务 |
| 归档 | 磁盘写入失败 | 技术 | 视原因 | 异常 | 空间检查 + hash + 对象存储 |
| 结果 | 意外文字/水印 | 质量 | 可重生成 | 人工发现 | **OCR / 视觉预检 + 人工审核** |
| 结果 | 商品主体漂移 | 事实 | 修改策略后 | 人工发现 | badcase 分类 + 升级参考图/控制路线 |
| 结果 | 构图不可用 | 质量 | 可换模板 | 人工发现 | 标注构图原因 + 优化图型模板 |
| 结果 | 虚假对比/功效 | **合规** | 否 | 人工发现 | **拒绝交付 + 追查输入来源** |

### 10.1 重试决策树

```
失败发生
├─ 配置或业务事实错误 ──→ 修正输入，不自动重试
├─ 429 / 网络瞬断 / 部分 5xx ──→ 有上限的退避重试
├─ 异步轮询超时 ──→ 查询原 task_id，不重新提交
├─ 质量失败 ──→ 修改模板 / seed / 参考图后新 attempt
├─ 事实失败 ──→ 修正 ProductProfile 或升级控制手段
└─ 合规失败 ──→ 阻止交付并人工审核
```

> **为什么不能统一自动重试**：网络瞬断、429、部分 5xx 可退避重试；API Key 错误、参数非法、内容审核拒绝**不应盲重试**；质量不可用需改输入；异步本地超时后远端任务可能仍在运行，**直接重提会重复计费**。

## 11. 质量评估与指标

### 11.1 评估对象的四层级

| 层级 | 对象 | 用途 |
|---|---|---|
| SKU | 一件商品或变体 | 套图耗时、交付完整度 |
| **ImageTask** | 一个 SKU 下的一种图型任务 | 技术成功率、图型覆盖 |
| **Attempt** | 某任务的一次实际提交 | 重试、供应商稳定性、成本 |
| **Candidate** | 一次提交返回的一张图片 | 人工可用、事实一致性 |

### 11.2 六个指标

**① 任务技术成功率**

```
= 技术成功的 ImageTask 数 / 实际提交执行的 ImageTask 总数
```
- 分母：**已通过输入校验并提交供应商**的任务；被业务门禁拦下的计入 `blocked_task_count`，**不进分母**；
- 分子：状态 `succeeded`，或按事先规则将 `partial_output` 视为成功；
- **仅收到 task_id、仅有 URL 但下载失败、空文件均不算成功。**

**② 首轮人工可用率**

```
= usable 的首轮 Candidate 数 / 已完成评审的首轮技术成功 Candidate 数
```
- **首轮** = 首次采用预设档案、模板与参数生成的候选，**不含**针对结果改 Prompt / 换图 / 换模型 / 手工合成后的重跑；
- **"可用"五项同时满足**：①主体无重大事实漂移 ②图型目标与构图成立 ③无明显合规风险 ④修复成本低于重做 ⑤可进入正常精修；
- 局部阴影、轻微背景瑕疵 → 可修；**按钮数量错误、轮廓改变、虚构认证 → 必须拒绝。**

**③ 事实一致性**

```
重大主体漂移率 = identity_drift=major 的候选数 / 已评审候选数
保护元素通过率 = 全部保护元素均正确的候选数 / 已评审候选数
```

**④ 图型完成度**：按 `image_type` 分组统计 `layout_fit`，**不能只给总平均掩盖高风险类型**。

**⑤ 首轮 SKU 耗时**

```
= 最后一个首轮图型任务完成归档时间 − SKU 首轮任务批次创建时间
```
- 必须记录**串行还是并行**；
- **包含**：分析、编排、提交、轮询、下载、归档；
- **不包含**：业务资料准备、人工确认、候选筛选、精修、嵌字、最终导出；
- 报**中位数 + P90**，不报范围。

**⑥ 成本**

```
单候选成本     = 总生成调用成本 / 成功归档候选数
单可用底图成本 = 总生成调用成本 / usable 候选数   ← 更接近业务价值
```
> 低价模型若可用率过低，**单张接口价格低并不代表总成本低**。

### 11.3 样本集设计（防选择偏差）

- **不只保留成功图片，失败 attempt 也必须入表**；
- 不在生成后删除困难 SKU；
- 记录输入图片数量、视角、质量；
- 首次执行与调参后的最佳结果**分开统计**；
- 不把开发调试样例混入正式评测；
- 按**风险**而非平均分配样本（服装/3C/家居/美妆/食品）。

### 11.4 数据结构

| 文件 | 一行 = | 关键列 |
|---|---|---|
| `evaluation_runs.csv` | 一次 **Attempt** | sku、图型、provider、时间、状态、输出、成本 |
| `人工评审表.csv` | 一个 **Candidate** 的评审 | 可用性、漂移、构图、事实风险、拒绝原因 |

两表通过 `run_id` + `candidate_index` 关联。

> **四项指标不能合成一个模糊的"生成成功率"。** 技术成功率、人工可用率、事实准确率、合规通过率必须分开。

## 12. 安全与合规

| 维度 | 措施 |
|---|---|
| **平台规则** | 主图硬约束程序化预检（白底纯度、占比、无文字、尺寸、命名含 UPC） |
| **虚假宣传红线** | 卖点必须有出处；**未经证实的功效/认证/材料/参数禁止生成**；对比图无证据不生成 |
| **内容安全** | 禁止生成违规内容；禁用词表（人物/服饰类敏感词做替换） |
| **密钥** | 仅存本地环境变量，直连官方 Endpoint；不经过第三方中转；权限最小化 + 定期轮换 |
| **日志脱敏** | 认证头只保留少量前后字符；Prompt / 商品描述 / 响应体含业务敏感信息，需**访问控制 + 保留期限 + 字段级脱敏** |
| **TLS** | ⚠️ 本地兼容措施（全局关闭证书校验）**必须标记为风险项并给出生产修正**，不得包装为生产能力 |

## 13. 演进路线

### 13.1 当前工作流原型 vs 生产化

| 当前 | 生产化需要补充 |
|---|---|
| CLI / 对话入口 | 业务工作台、权限、审核 |
| JSON 参数传递 | Schema、版本、数据校验 |
| 进程内顺序执行 | 队列、并发、幂等、限流 |
| 部分异步轮询 | **持久化状态机 + 重启恢复** |
| 本地文件归档 | 对象存储、数据库、资产版本 |
| 错误日志文件 | trace、指标、告警、成本监控 |
| 人工口头判断 | 结构化评审 + badcase 数据集 |

> 面试中**主动区分这两栏**，比隐藏差距更能体现架构判断。

### 13.2 三期分期

| 期 | 范围 | 判据 |
|---|---|---|
| **P0 最小闭环** | 主图 + 卖点两张；主体资产共享；1 次背景生成；`subject_hash` 断言 | 交付"决策必需"的两问 |
| **P1 完整套图** | 补齐规格/场景/细节/内容物/对比；事实门禁；S5/S7 落地 | 覆盖七个买家问题 |
| **P2 平台化** | 多平台规范、状态持久化、并发队列、评审工作台、指标口径固化 | 从"能跑"到"能运营" |

### 13.3 新增项准入判据（挡范围膨胀）

任何要加进这个系统的功能，先问：

> **它是在扩大「事实保真」，还是在扩大「呈现能力」？**

- 扩大**事实保真**（更强主体保真、更准文字渲染、更严合规检测）→ **做**
- 扩大**呈现能力**（更多场景、更多版式、跨站点本地化）→ **做**
- **都不是** → 它是外壳（权限、审批流、历史列表、仪表盘）→ **推迟**

> **两者都不扩大，就不是这个系统在进化，只是它在变胖。**

| ⭐ | 主体光照特征来源 | `lighting` 字段手工填 / 从实拍图自动估计 | S4b |

### 14.1 目前可回答的两道验收题

**Q1：为什么不是简单调 API？**

> API 调用只是执行末端。调用之前至少完成三层工作：①把多张商品图分析成可消费的结构化事实（带来源与门禁）；②按图型组织不同的构图、场景、参考图与负面约束；③适配同步/异步协议并处理状态、下载、失败隔离与脱敏日志。
> 严格地说，当前是**工作流原型**而非生产平台，"不是简单调 API" ≠ "已具备完整平台工程能力"。

**Q2：两套参考仓库没有统一调用链，为什么还能作为一个项目讲？**

> 只有在确实把它们作为**同一业务目标下的两类实现资产**并能讲清二次抽象时才成立。应主动说明：一个提供**分析和批量执行骨架**，另一个提供**模板化视觉策略与单图生成工具**；项目工作是把这些能力按 SKU 任务链重新组织。
> **若实际并未做整合，就应说"参考并验证了两类方案"，不能说"完成代码级集成"。**

## 附录 B：术语表（精确定义）

| 术语 | 精确定义 | **不包含** |
|---|---|---|
| SKU | 一件具体商品或变体，也是一次套图任务的归属单位 | 不等于已有 SKU 数据库和后台 |
| 商品事实 | 可由参考图观察或由业务确认的颜色、外形、关键结构、材质描述和规格 | 模型对不可见结构的猜测 |
| 图型 | 为特定业务目的定义的一类图片任务 | 任意视觉风格标签 |
| 视觉底图 | 为精修、排版、嵌字准备的基础视觉画面 | 已通过平台审核的最终图片 |
| 候选图 | 一次任务生成的一个或多个备选结果 | 默认可直接发布的成品 |
| 首轮生成 | 未经过针对结果的人工返工得到的第一批候选 | 反复挑选最佳参数后的最终结果 |
| 人工可用 | 图片可进入正常精修，而非必须整张重做 | 没有任何瑕疵 |
| **Prompt 编排** | 将商品事实、图型规则、场景、构图、风格、负面词和参考图说明按规则组装 | 简单拼接一句提示词；或完全由 Agent 自主规划 |
| **参考图约束** | 将商品图/模特图传给支持的模型，并在 Prompt 中强调需保留的特征 | 等同于 IP-Adapter 或保证 100% 一致 |
| **Campaign Style Lock** | 多图共用的色板、光线、背景、构图和视觉语言约束 | 锁定商品零部件和几何结构 |
| **状态轮询** | 异步任务提交后，用 `task_id` 定期查询完成/失败/超时 | 所有 API 的统一执行方式 |
| **一致性控制** | 降低商品事实或整套视觉风格在多张图之间的变化 | 对结果完全确定性控制 |
| **主体资产** | 抠图产出的、被 N 路共享的 RGBA 文件 + `subject_hash` | 提示词里写的"请使用同一个主体" |

### 四条绝对边界（背诵级）

1. 模型看到的商品特征 **≠** 经过业务确认的商品事实；
2. 接口返回图片 **≠** 图片达到人工可用；
3. 共享风格 Prompt **≠** 商品结构被严格锁定；
4. 有可扩展技术路线 **≠** 已完成对应模型和平台建设。
