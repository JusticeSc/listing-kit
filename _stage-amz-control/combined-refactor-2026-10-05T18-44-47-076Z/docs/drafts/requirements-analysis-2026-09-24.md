## 9. 使用与培训边界

2026-09-24，项目发起人确认：产品应让陌生人能够理解；真实业务使用可以接受一次简短培训。

据此形成下面的候选行为合同，后续用可用性走查验证：

### 不依赖培训也必须做到

- 看懂产品解决什么问题，以及一次任务需要提供什么；
- 使用内置演示商品启动任务，不接触命令行、JSON 或内部目录约定；
- 看懂当前处于准备、生成、待审核、返工还是可导出状态；
- 对单张结果选择接受、保留旧候选或按原因返工；
- 知道哪些检查已通过、哪些需要人判断、为什么暂时不能导出；
- 完成导出，并找到图片与交付说明；
- 遇到缺料、模型不可用或调用失败时，看到可执行的下一步，而不是技术堆栈。

### 可以通过简短培训获得

- 不同平台图片规范及品类差异；
- 一组 Listing 图片各自承担什么购买信息；
- 怎样判断商品保真、卖点真实性、品牌风格和视觉质量；
- 什么情况下应该重生成、调整输入、换素材或放弃候选；
- 谁对最终发布承担责任。

### 不允许转嫁给培训

- 安装和启动中的隐含步骤；
- 手写结构化配置、素材路径或签字代码；
- 理解 renderer、slot、FactsVersion、Attempt 等内部术语；
- 靠记忆判断按钮后果、费用或是否会覆盖旧结果；
- 发生错误后找开发者修改状态或补写文件。

这一边界意味着演示产品不是“零学习产品”，而是“零技术门槛产品”：业务判断需要学习，系统操作不应依赖开发者口授。

## 10. 目标结果

2026-09-24，项目发起人将演示产品最重要的结果明确为：

> 降低原先复杂生图任务的使用门槛。

这里的“门槛”暂时拆成六种待验证负担，而不是笼统理解为少点几个按钮：

| 原先需要使用者承担的复杂性 | 产品应怎样承接 |
|---|---|
| 理解一组图片分别要表达什么 | 根据商品事实、平台和目标生成可解释的图片计划 |
| 为每张图编写、补全和维护提示词 | 把视觉规范、场景、角度、构图、留白和否定约束编译成提示词 |
| 选择模型、尺寸、参数并处理调用 | 提供经过验证的默认路线，只暴露会改变业务结果的选择 |
| 让多张图保持商品与视觉风格一致 | 使用商品参考图、事实约束和成套视觉锁，并在结果中显式检查 |
| 发现“不好”后判断应改什么 | 用业务语言收集问题，映射为改计划、改场景、改文案、换素材或重新生成 |
| 管理候选、旧版本、失败重试和最终文件 | 保留候选与依据，支持单图返工和明确导出，不让使用者手工整理目录 |

### 当前结果假设

> 一个懂自己商品、但不会编写专业生图提示词，也不熟悉模型/API 的人，在简短业务培训后，可以仅提供商品资料并作业务选择，由系统完成视觉计划、提示词构造、模型执行、结果解释、单图返工和交付整理，最终得到可检查、可选择、可导出的商品图片组。

“降低门槛”不能靠降低图片标准实现。代理验收至少要同时证明：

1. 使用者无需命令行、JSON、API 或自由编写完整提示词；
2. 使用者能理解并完成正常任务和一次单图返工；
3. 产物通过明确的平台与事实底线；
4. 视觉结果不是占位图或机械排版，而是模型实际参与生成、具有可比较的商业视觉价值；
5. 系统保留必要选择权，不能用“全自动”掩盖错误或替使用者发布。

目前尚不能声称真实业务的学习时间、完成时间或返工次数下降；演示阶段只能用同一代理任务的操作步骤、所需知识、人工输入和最终产物进行前后对照。

## 11. 人与系统的决策边界

2026-09-24，项目发起人确认：系统提供默认方案，用户也可以选择手动调整。

### 默认方案的合同

- 输入达到最低齐套条件后，系统必须给出一套完整、可解释、可直接启动的建议方案；
- 默认方案应包含图片计划、视觉方向、场景与角度分配、成套一致性约束、每张图的生成指令和检查要求；
- 推荐必须说明依据，例如商品特征、目标平台、卖点、参考素材和图片用途，不能只给一个风格名称；
- 用户不调整任何高级选项，也应能跑完正常任务；
- 默认值必须来自已登记的策略或模型建议并保存版本，不能散落在界面和代码中各写一份。

### 手动调整的合同

- 调整入口使用业务语言，并按图片计划、整套视觉方向、单张创意和事实资料分层；
- 调整前显示影响范围、是否会触发模型调用、预计成本以及哪些旧候选仍然保留；
- 单张调整默认只使受影响图片失效，不隐式重跑整套；
- 用户可以查看并直接编辑系统实际使用的完整提示词；编辑行为按第 12 节版本化并继续受硬约束；
- 用户可以一键恢复推荐方案，恢复动作也产生新版本，不覆盖历史；
- 手动选择不能绕过商品事实、数据授权、平台硬规则、预算和最终验收门。

### 渐进式界面

```text
提供资料
  → 系统给出完整推荐方案和理由
  → 用户可直接生成
  → 需要时展开业务级调整
  → 生成候选、比较、按原因单图返工
  → 人最终选择并导出
```

这样“可调整”不会重新把复杂生图工作推回给使用者：默认路径负责降低门槛，高级路径负责保留控制权。

## 12. 提示词高级编辑

2026-09-24，项目发起人确认：允许用户直接查看和编辑系统生成的完整提示词。

这项能力的产品边界如下：

- 默认路径不要求用户查看提示词；编辑器放在可展开的高级区域；
- 展示的必须是本次实际发送给模型的最终完整提示词，而不是另一份仅供展示的摘要；
- 用户编辑从系统推荐版本派生出新的 `PromptVersion`，保留作者、时间、基准版本、差异和内容哈希；
- 每次生成结果必须绑定实际使用的提示词版本、模型、参数和参考素材版本；
- 支持查看修改差异、撤销未提交修改、恢复系统推荐版本和基于旧版本创建新版本；
- 编辑器应提示哪些段落负责商品保真、视觉风格、单张目标、构图、文字和否定约束，降低误改成本；
- 原始提示词修改可以改变创意方向，但不能绕过数据外发授权、预算、平台硬规则和最终人工验收；
- 若用户删除商品保真或事实约束，系统必须在提交前明确指出风险；会造成已知硬违规的修改应拒绝提交，而不是生成后再解释；
- 单张提示词编辑默认只影响对应图片；修改整套共享风格段才会提示影响整套并创建新的计划版本。

因此，提示词编辑是“可审计的高级控制权”，不是另一个无状态文本框。

## 13. 首个端到端演示任务

2026-09-24，项目发起人接受以下首个演示边界：

- 平台：Amazon US；
- 品类：家居厨具；
- 商品：无复杂品牌文字的保温杯；
- 用途：验证完整产品链路，不把平台、品类、商品或图片数量固化成产品永久边界。

### 13.1 演示参与者

一个了解自己商品、但不熟悉专业提示词、图像模型或 API 的陌生使用者。

### 13.2 起始输入

- 同一只真实保温杯的正面、斜侧、杯盖/杯口细节和随包装内容物照片；
- 已确认的可见事实与规格，未知字段保持未知；
- 有依据的卖点，不使用无法证明的保温时长、食品等级或绝对化宣传；
- Amazon US 作为目标平台；
- 可选视觉参考，不把参考图中的商品事实抄到本商品上。

### 13.3 默认任务轨迹

```text
打开产品
→ 选择内置演示商品或导入素材
→ 系统检查素材与事实是否齐套
→ 系统推荐整套图片计划、视觉方向、场景、角度和理由
→ 用户直接确认，或调整业务选项/完整提示词
→ 模型使用商品参考图生成视觉候选
→ 系统展示平台检查、事实风险和视觉候选
→ 用户保留旧图并对一张图定向返工
→ 用户逐图选择
→ 导出图片组和可读交付说明
```

默认建议可以包含主图和若干补充图，但“完成”由已确认计划是否齐套决定，不由固定七张决定。

### 13.4 演示必须证明

1. 新手不写提示词也能得到完整默认方案并启动真实模型生成；
2. 高级用户能看到并修改实际提示词，修改后结果与提示词版本绑定；
3. 至少一张场景/视觉图让模型直接使用商品参考图，而不是只生成空背景；
4. 商品轮廓、颜色、杯口、杯盖及可见结构能与源照片逐项比较；
5. 主图、事实表达和文件规格有独立检查，审美选择不能覆盖事实错误；
6. 单图返工保留旧候选，不重跑未受影响图片；
7. 缺料、模型不可用和结果不合格都有非技术化下一步；
8. 导出包中的图片、用途、来源版本和检查状态可被陌生人理解。

### 13.5 Amazon 当前平台底线

依据 Amazon US 官方 `Product image guide`（2026-09-24 核验）：

- 每个商品至少要有一张合规主图，Amazon 建议另提供至少六张图片和一段视频；
- 主图必须准确、专业地呈现实物，完整入镜、只出现一次，并准确表现尺度、数量和颜色；
- 主图背景为纯白 `RGB(255,255,255)`，商品约占画面 85%；
- 最长边最低 500 px、最高 10,000 px；建议至少 1,000 px 以启用缩放；
- 支持 JPEG、TIFF、PNG 和非动画 GIF，JPEG 为推荐格式；
- 所有图片都必须准确呈现所售商品并与标题一致；禁止客户评价、五星图形、免邮等声明、卖家专属信息以及 Amazon 商标/徽章。

官方来源：`https://sellercentral.amazon.com/help/hub/reference/external/G1881?locale=en_us`

平台规则只回答“平台是否可能接收”，不回答图片是否有视觉吸引力，也不证明 Amazon 实际审核一定通过。

## 14. 当前样本缺口

现有 `examples/input/cup_source.jpg`、`cup_closeup.jpg` 和 `cup_contents.jpg` 不能作为可信演示商品包：

- `cup_source.jpg` 右下角带“AI生成 WORKBUDDY”水印；
- `cup_closeup.jpg` 只是同一张图的裁切，不能提供新的角度或结构事实；
- `cup_contents.jpg` 把实拍杯体与示意纸盒、刷子拼在一起，不能证明真实包装内容物；
- `product_fullset.json` 中的 500ml、316 不锈钢、24 小时保温等字段没有与这些图片绑定的权威来源。

这组素材可以继续用于软件回归，不能用于证明“真实商品资料 → 可发布图片”的完整演示结论。

## 15. 无真实商品素材时的演示策略

2026-09-24，项目发起人确认无法提供自有保温杯照片及真实规格资料。

因此首个演示商品调整为**明确标注的虚构私牌保温杯**，并采用以下证据边界：

### 可以证明

- 陌生人能否理解并完成端到端操作；
- 系统能否从一套商品资料生成默认图片计划、视觉方向和完整提示词；
- 真实图像模型能否使用参考图生成具有商业视觉质量的候选；
- 生成候选相对内置参考图是否保持轮廓、颜色和可见结构一致；
- 平台像素规则、候选管理、提示词编辑、单图返工、失败处理和导出是否成立；
- 系统是否明确区分商品事实、创意建议、模型候选和人工选择。

### 不能证明

- 产物与某个真实在售商品一致；
- 商品容量、材质、性能或卖点经过真实商家确认；
- 图片已经获得 Amazon 审核或适合直接用于真实上架；
- 产品降低了真实运营的学习时间、制作时间或返工率。

### 内置演示商品包要求

- 使用虚构商品名和虚构品牌，不冒充真实品牌；
- 建立一张规范化商品参考板，明确正面、斜侧、杯盖、杯口、底部与随附物；
- 所有事实字段标记为 `demo_fixture`，事实卡与参考图共同版本化；
- 只使用参考板能支持的事实，不凭空增加认证、性能时长或材质等级；
- 所有页面与导出清单显示“虚构演示商品 / 不用于真实上架”；
- 主图只验证白底、占比、尺寸、清晰度等技术形态，不声称满足 Amazon 对“实际商品照片”的真实性要求；
- 将来导入真实商品时复用同一流程，但演示证据不得自动升级成真实业务证据。

### 验收口径调整

原表述“得到真正可上架的图片”调整为：

> 得到一组在视觉、技术格式和内部事实一致性上达到演示验收线的 Listing 图片候选；系统能够清楚说明仍缺少真实商品与真实平台审核证据。

完整演示仍必须真实调用生图模型，不能用预置成品冒充本次生成结果。

## 16. 实时生图依赖与当前能力缺口

2026-09-24，项目发起人确认：演示产品使用阿里云百炼 `qwen-image-3.0`，项目已经具备该模型的调用条件。

### 16.1 已核实事实

- 当前进程环境存在 `DASHSCOPE_API_KEY`；只确认可用条件，不在文档或日志中记录凭证内容；
- 当前 `src/imagegen.py` 的 `generate_image()` 只接受提示词、反向提示词、输出路径、模型和尺寸等文本生成参数，没有商品参考图参数；
- 当前请求发送至 `/services/aigc/image-generation/generation`，`input.messages[].content` 只有 `text`，没有 `image`；
- 当前生成路线因此是“模型生成背景，再由确定性程序贴入商品主体”，不是“模型直接参考商品图生成完整视觉候选”；
- 百炼官方 `qwen-image-3.0` API 同时支持文生图和图生图/图像编辑；图生图可输入 1–3 张参考图，DashScope 请求使用 `/services/aigc/multimodal-generation/generation`，在消息内容中先传 `image`、再传编辑指令文本；
- 三个电商图片技能范例都把源商品图作为模型参考输入，并把保持商品外观、不变量和人工质检作为生成合同。它们能作为交互与提示词设计参考，但其中固定张数、模型选择、经验性参数和效果口径不能直接当成本项目事实。

官方来源：`https://help.aliyun.com/zh/model-studio/qwen-image-generation-and-editing-api-reference`

### 16.2 对需求与现状的判断

当前程序能证明“纯文本背景生成 + 本地合成链路可运行”，不能证明：

- 模型实际读取了商品参考图；
- `qwen-image-3.0` 能在本演示商品上保持杯体轮廓、颜色、杯盖、杯口和可见结构；
- 模型直接生成的场景图具有可接受的商业视觉质量；
- 多张参考图、提示词增强和参数选择在当前商品上形成了稳定路线。

因此，第 13.4 节第 3、4 项仍是待实验的产品风险，不能通过继续完善确定性排版或增加提示词规则替代。

### 16.3 下一项最有价值的验证

在继续扩展界面或整组工作流之前，先完成一条最小但真实的图生图验证：

1. 使用明确标注的虚构演示商品参考板，不使用真实商家或第三方未授权素材；
2. 将 1–3 张商品参考图真实发送给 `qwen-image-3.0` 图生图端点；
3. 固定一项场景任务和一份版本化提示词，生成多个候选；
4. 保存请求所用的模型、参数、参考图版本、提示词版本、任务身份及原始响应；
5. 按杯体轮廓、颜色、比例、杯盖、杯口、底部和禁止新增部件逐项对照；
6. 由人工判断视觉质量，并将“事实错误”与“审美不喜欢”分开记录；
7. 根据结果决定继续使用直接图生图、退回“主体保留 + 背景生成 + 合成”，或只对部分图型开放直接生成。

这项验证回答的是“该模型与这套参考素材能否支撑产品承诺”，不是证明所有商品或真实业务都可靠。

### 16.4 参考图调用边界

2026-09-24，项目发起人废除“逐次确认参考图外发、拒绝后降级为纯文生图或本地拼贴”的候选方案。

当前产品合同改为：

- 商品参考图送入阿里云百炼 `qwen-image-3.0` 是生成可用商品视觉候选的固定前提，不设计关闭开关；
- 产品在导入与生成界面明确告知素材将发送给阿里云百炼及其用途，但不把这项核心前提设计成每次任务的选择题；
- 不提供“拒绝外发后继续生成”的伪等价路径；纯文生图背景和本地拼贴可以保留为工程实验或故障诊断手段，不能作为正式产品生成模式；
- 无法接受这一调用前提的使用者不在当前产品支持范围内，系统应在开始任务前清楚说明，而不是运行到一半再失败；
- 每次生成记录实际发送的参考图版本、模型、参数和提示词版本，但日志不复制凭证或无关隐私数据。

这一决定只确定产品行为，不替代将来真实部署所需的隐私说明、服务条款和组织授权。

## 17. 虚构商品参考板与首个图生图实验规约

本节不是正式产品实现计划，而是 Phase 0 的关键能力验证合同。它的作用是用最小真实实验回答：`qwen-image-3.0` 是否足以支撑“系统替用户完成专业生图，同时保持商品可见事实”的核心承诺。

### 17.1 演示商品身份

商品身份固定为：

```text
fixture_id: demo-tumbler-aster-01
display_name: Aster 01 保温杯（虚构演示商品）
fact_source: demo_fixture
usage: 仅用于产品演示与模型能力验证，不用于真实上架
```

`Aster 01` 只作为系统内的虚构名称，不在杯体上生成品牌文字。参考板只定义可直接观察的外观事实，不声明 316 不锈钢、容量、保温时长、食品等级或认证。

### 17.2 规范化外观事实

参考板必须共同支持以下可见事实；任一视图与它们冲突，整套参考板不得进入实验：

| 编号 | 必须保持的可见事实 | 明确禁止 |
|---|---|---|
| F1 | 单个高直筒杯体，高宽视觉比例约 3.1:1，主体侧壁近乎平直 | 变成矮胖杯、锥形杯、马克杯或瓶状收腰 |
| F2 | 上部约 72% 为哑光深青绿色 `#0F6B66` | 改成其他主色、金属裸色、渐变或图案 |
| F3 | 下部约 28% 为深炭灰 `#252A2A` 防滑套，带三条浅水平筋 | 防滑套消失、变色、改变高度或筋条数量明显错误 |
| F4 | 杯盖为低矮深炭灰结构，具有两层清楚可见的同心阶梯环 | 杯盖被简化成单层、增加翻盖、吸嘴或第二只盖子 |
| F5 | 杯盖与杯体之间有一圈窄陶土橙色 `#D97A45` 装饰环 | 装饰环缺失、变宽或出现在杯体其他位置 |
| F6 | 平底，底部有窄深灰防滑圈 | 增加支脚、尖底或明显悬浮 |
| F7 | 无把手、无侧握、无提带、无吸管、无杯嘴 | 新增任何上述部件 |
| F8 | 外表无文字、数字、Logo、标签和水印 | 生成品牌字、伪标签、容量字样或装饰符号 |

颜色十六进制值是该虚构夹具的设计定义，不代表模型可以仅凭像素比较绝对还原；验收同时查看相对色相、色块位置和跨候选一致性。

### 17.3 参考资产组成

正式参考包由一个供人核对的参考板和三个供模型输入的单视图文件组成：

| 文件角色 | 内容 | 主要证明 |
|---|---|---|
| `reference-board.png` | 2×3 参考板：正面、30° 斜侧、纯侧面、杯盖俯视、底部、杯盖近景 | 人工核对整套外观是否自洽 |
| `ref-01-front.png` | 单杯正面闭盖全身图，纯中性背景 | 轮廓、比例、色块和部件数量 |
| `ref-02-three-quarter.png` | 同一杯体 30° 斜侧闭盖全身图 | 立体结构、杯盖层次和防滑套 |
| `ref-03-lid-detail.png` | 同一杯体上部与杯盖近景 | 两层阶梯环和橙色装饰环 |

进入实验前必须满足：三个单视图属于同一设计；无水印和文字；长边至少 1,024 px；商品完整入镜；文件哈希、尺寸、来源方法和参考包版本写入 manifest。参考板自身经过人工选择才成为权威夹具，生成它的模型输出不能自动升级成事实。

### 17.4 首个能力任务

首个任务只验证一个高价值变化：**保持商品外观与基本角度，将纯背景变为具有商业摄影质感的现代厨房场景。** 不同时测试旋转到新角度、开盖、人物手持、文字排版或功能示意。

目标画面：浅色洞石厨房台面，背景为现代简约厨房并适度虚化；清晨柔和侧光从左前方进入；杯体完整、物理接触台面、阴影方向一致；商品占画面约 35%–40%，右侧保留可用于后期版式的干净空间；正方形商业商品摄影，无文字、Logo、水印和额外杯具。

提示词使用稳定分段：任务目标、商品不变量、允许变化、构图与光线、禁止项。首轮展示并发送同一份已版本化的完整提示词，不让界面摘要和实际请求分叉。

### 17.5 固定实验条件

| 项目 | 首轮条件 | 原因 |
|---|---|---|
| 模型 | `qwen-image-3.0` | 用户已确认的实际依赖 |
| 模式 | DashScope 图生图 / 图像编辑 | 必须真实发送参考图，而非只发文字 |
| 参考图 | `ref-01-front.png`、`ref-02-three-quarter.png`、`ref-03-lid-detail.png` | 在官方 1–3 张输入范围内覆盖整体与杯盖细节 |
| 输出 | 1:1，首轮保留服务返回的原始 PNG | 与首个 Listing 场景一致，避免 JPEG 转换先引入损失 |
| 候选 | 四次独立请求，每次一张；固定登记四个 seed | 既观察变异，又能逐次追踪请求与结果 |
| `prompt_extend` | 首轮显式 `false` | 提示词已经详细，优先保持实际指令可复现 |
| 水印 | `false` | 输出不可带模型水印 |
| 最大尝试 | 首轮 4 张；必要时只允许一次受控复验，累计不超过 8 张 | 防止靠无界重试掩盖路线不稳定 |

若首轮商品硬事实通过但视觉表现普遍平庸，可在第二轮只改变 `prompt_extend=true` 且使用 `direct`，其他输入保持一致；I2I 不使用官方不支持的 `agent` 改写模式。若首轮商品事实已经明显失真，不能同时改提示词、参考图和参数后宣称找到原因。

### 17.6 每次请求必须留下的证据

- 稳定的实验、请求和候选身份；
- 模型、端点类型、区域、输出尺寸、seed、`prompt_extend` 和水印参数；
- 三张参考图的版本与哈希，以及请求体确实包含图像字段的机器检查；
- 用户可见的最终提示词版本与内容哈希；
- 百炼任务身份、开始与结束时间、原始状态、失败信息和用量字段；
- 原始输出文件及其哈希，不用后期修图覆盖；
- 每张候选的事实检查、人工视觉结论和理由。

凭证、完整 Base64 图片内容和临时授权 URL 不写入普通日志。

### 17.7 候选验收

每张候选先过事实底线，再进行视觉判断。

**事实硬失败：** F1–F8 任一明显不成立；商品重复、残缺或被裁切；杯体悬浮或与台面严重穿插；出现不可辨认伪文字。硬失败候选不能用审美分数补救。

**视觉人工结论：**

- `keep`：构图、光线融合、材质真实感和商业画面完成度足以保留为候选；
- `redo`：商品事实基本正确，但场景、构图或质感需要定向重做；
- `reject`：事实硬失败，或明显没有商业使用价值。

这里不虚构自动“美学分”。人工必须写出影响决定的具体原因，例如主体太小、光影不一致、背景抢主体或材质塑料感。

### 17.8 继续、复验与改线条件

| 首轮结果 | 决定 |
|---|---|
| 四张中至少两张通过 F1–F8，且至少一张被判为 `keep` | 直接图生图路线获得进入产品垂直切片的初步证据 |
| 只有一张通过事实底线，或通过者全部是 `redo` | 只允许一次受控复验；必须事先写明只改变哪个变量以及为什么 |
| 四张全部事实硬失败 | 当前参考包与直接图生图路线不成立；停止扩展产品流程，先定位参考图、提示词或模型能力问题 |
| 受控复验后仍没有 `keep` | 不得用本地拼贴冒充完成；应修改产品承诺、重新设计模型路线或停止该能力 |

上述比例是演示项目的工程继续线，不是模型普遍成功率，也不能外推为真实商品生产指标。

### 17.9 这项实验不能证明什么

即使实验通过，也只证明这一个虚构杯、一个场景任务和当次模型版本出现了可用候选。它不证明其他商品类别、复杂 Logo、人物交互、多个角度、批量稳定性、真实商家认可或 Amazon 实际审核通过。

## 18. 拟创建的正式 Goal 合同

### 18.1 Goal 文本

> 将 `amz-listing-kit` 做成一个陌生使用者能够独立完成任务的完整本地演示产品：使用内置虚构保温杯资料，从素材与事实检查开始，由系统生成可解释的 Listing 图片计划和默认视觉方案；用户无需编写提示词即可启动阿里云百炼 `qwen-image-3.0` 的真实参考图生成，也可查看并版本化编辑实际提示词；系统支持候选比较、保留旧图、按原因单图返工、逐图选择，以及导出图片组与可读交付说明。完成必须由一条全新的端到端运行证据证明：所有计划必需图均有被选候选；适用的商品外观事实、Amazon 技术形态与文件检查全部通过；至少一张直接图生图场景候选通过 F1–F8 且被人工判为 `keep`；单图返工不覆盖旧候选、不重跑无关图片；模型请求确实携带参考图且不是 mock；一名首次接触产品的代理使用者无需命令行、JSON、API 或开发者口授即可完成正常流程和一次返工。若直接图生图在第 17 节规定的一次首轮加一次受控复验后仍无 `keep`，停止扩展工作流并重新确认技术路线或产品承诺，不得以本地拼贴降低完成标准。

### 18.2 完成条件

Goal 只有在以下条件全部有新鲜证据时才能完成：

| 编号 | 必须成立的结果 | 接受证据 |
|---|---|---|
| G-A | 陌生人可从入口理解产品用途、演示边界和完整任务路径 | 首次使用页面、内置引导及无口头技术指导的代理操作记录 |
| G-B | 内置虚构商品包自洽、可追溯且不冒充真实商品 | 参考板、三个模型参考文件、事实卡、manifest、哈希和“仅供演示”标记 |
| G-C | 系统给出完整默认计划，图片数量由计划和事实决定 | 计划版本、推荐理由、图型职责和素材依赖；不以固定七张作为通过条件 |
| G-D | 默认用户不写提示词也能生成，高级用户能编辑实际提示词 | 默认路径记录；提示词编辑前后版本、差异、内容哈希和结果绑定 |
| G-E | 至少一个高价值场景由模型直接参考商品图生成 | 请求体图像字段、参考图哈希、百炼任务身份、原始输出和非 mock 证明 |
| G-F | 图像质量先过事实底线，再由人判断视觉可用性 | F1–F8 逐项结果；事实硬失败不可被美学判断覆盖；至少一张场景图为 `keep` |
| G-G | 主图与所有导出文件通过适用的确定性检查 | 白底、主体占比、尺寸、格式、禁用元素、文件可读性及检查版本记录 |
| G-H | 用户可以比较、选择并只返工有问题的一张图 | 旧候选保留；返工原因、派生版本与新候选可追溯；未受影响图片没有新模型任务 |
| G-I | 失败不会伪装成完成 | 缺料、请求拒绝、调用失败、结果未知、事实不合格均有非技术化状态与下一步 |
| G-J | 导出物能够被第三方理解 | 图片、用途、选中版本、来源、检查状态、演示免责声明和 manifest 一致 |
| G-K | 项目控制面与核心回归保持绿色 | 文档权威唯一、活动状态唯一、项目状态守卫、文档守卫、针对性测试和端到端演示检查通过 |

### 18.3 代理验收任务

代理使用者只获得以下业务目标：

> 为内置的虚构 `Aster 01` 保温杯准备一组 Amazon US Listing 图片候选。先采用系统推荐方案生成；检查结果后，保留可用图片，选择一张不满意的图说明原因并单独重做；最后选定各图并导出交付包。

允许产品内提供简短业务说明，例如主图与场景图的用途、事实错误和审美偏好的区别；不允许开发者在旁指挥点击顺序、解释内部术语、修改文件或替使用者恢复状态。

### 18.4 非目标

本 Goal 不承诺：

- 真实商品、真实商家或真实 Amazon 审核通过；
- 已降低真实运营的学习时间、制作时间、成本或返工率；
- 覆盖 Amazon 以外平台、其他品类、复杂品牌文字、人物手持或批量 SKU；
- 自动发布、替用户作最终选择、多用户权限、生产级云部署或离线模型；
- 通过无界增加生成次数获得偶然好图；
- 将现有纯文生图背景加本地贴图路线包装为直接参考商品图生成。

### 18.5 权限与边界

- 允许修改当前项目中的产品代码、配置、文档、测试和内置演示资产；
- 允许在明确的实验预算内调用已确认的百炼模型；首个能力实验遵守第 17 节最多 8 张输出的上限，扩大调用前重新说明依据；
- 不发布到真实商城、不上传真实商家素材、不替用户购买额外服务或改变外部账号配置；
- 模型候选不自动成为已选结果，发布责任始终不属于系统；
- API 凭证只从运行环境读取，不进入文档、仓库、导出包或普通日志。

### 18.6 停止或重新确认条件

出现以下任一情况时，不通过降低验收标准继续：

- `qwen-image-3.0` 在规定的首轮与受控复验后仍没有一张场景候选同时通过 F1–F8 并被判为 `keep`；
- 百炼实际账号、地域或接口不支持已核实的图生图请求形态；
- 创建一致的虚构参考包本身失败，导致后续无法判断模型是否失真；
- 为实现任务必须引入真实商品、真实业务方或本 Goal 明确排除的外部系统；
- 用户要求改变核心模型、平台、品类、数据外发前提或演示证据边界；
- 完成声明需要依赖未执行的检查、旧运行结果或开发者主观自评。

### 18.7 尚未发生的证据

本节是待确认的 Goal 合同，不是完成声明。参考资产尚未创建，图生图实验尚未运行，完整产品尚未实现，陌生人代理验收也尚未发生。

### 18.8 Goal 启动后的首条实施切片

第一条切片不是先扩展整套界面，而是完成“参考资产 → 真实图生图请求 → 候选与证据报告”的最短闭环：

1. 创建并人工冻结 `demo-tumbler-aster-01` 参考包和 manifest；
2. 为百炼适配器增加 1–3 张参考图输入，确保请求走图生图端点，并让现有请求体守卫能证明图像字段真实存在；
3. 按第 17 节固定条件生成首轮四张原始 PNG 候选；
4. 逐张记录 F1–F8、`keep/redo/reject` 和理由，输出可复核实验报告；
5. 依据第 17.8 节决定进入产品垂直切片、只做一次受控复验，或停止并重新设计路线。

只有这条切片获得继续证据后，才实现完整默认计划、候选管理、提示词编辑、单图返工、导出和陌生人验收界面，避免先把工作流做完整再发现核心模型路线不成立。
