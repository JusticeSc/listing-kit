## 2. 怎么跑

依赖锁在 `requirements.txt`（可选 `requirements-rembg.txt`）。准备动作改的是**这台机器**，
所以放在 `text` 围栏里 —— 守卫只真跑 `bash` 围栏（见 `tools/check_docs.py` 的 `EXEC_LANGS`），
不会替你去建环境、装包：

```text
# ---- 准备（一次）----
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
# 可选：位置 1 想真用 rembg 抠图就再装这个（不装会自动降级 floodfill，且不会联网下载）
.venv\Scripts\python.exe -m pip install -r requirements-rembg.txt
```

```bash
PY=.venv/Scripts/python.exe       # 相对路径：不写死本机解释器

# ---- 入口 A：命令行 ----
$PY run.py --product examples/product_fullset.json            # 真跑（位置 4 调模型）
$PY run.py --product examples/product_demo.json --dry-run     # 干跑：只报数，不产图
$PY run.py --product examples/product_fullset.json --only 1   # 只做位置 1

# ---- 入口 B：审核台界面（v2 的主要用法）----
$PY web/server.py --open        # 127.0.0.1:8777

# ---- 入口 C：v1.20 Mock 工程测试台（不是当前产品前端基线）----
$PY app/server.py --offline-fixture demo/fixture/aster-01 --check   # 先自检：零联网 / 零写盘 / 单页五区 + Mock 轨迹（这条不写 `--open`：守卫只跑能结束的命令）
```

界面是**五步页**：收件 → 齐套判定 → 生成 → **审核台** → 控制面。

```
收件      只读展示 E0 体检事实、商品包切换、签字缺哪几条
齐套判定  张数 = 表 ∩ 素材齐套（缺什么、跳过谁，逐条列出）
生成      真实进度条；只有位置 4 是橙色（那是「调模型」的声明，不是写死的坑位号）
审核台    七张卡片 · 版本对比 v1/v2 · 三档重做 · 采纳 · 导出
          键盘 1-7 选格 / A 采纳 / R 重做 / Enter 确认
控制面    只读：坑位表 + 渲染器声明 + 类目色板 + 取景池
```

入口 C 去掉 `--check` 就是启动旧测试台（常驻进程，文档守卫不跑它）：浏览器打开 `http://127.0.0.1:8778/`，
页头固定显示「离线 Mock · 不调用模型」，不会联网、不会写出交付文件；页内「切换演示情形」可在
正常 / 部分失败 / Unknown 三种结果间复跑。单页的走查说明与观察表在 `evals/product-demo/d2-r2/`。

**界面上的每个数字都来自接口，界面不推导业务结论。** 张数、跳过、成本、版本、采纳状态，
全部由 `src/orchestrator.run_state()` 从 `run.jsonl` 派生 —— 界面不是第二个真相源。

## 3. 四条不变量（改代码时不得破坏）

| # | 不变量 | 落地位置 | 破坏它的后果 |
|---|---|---|---|
| **A** | **主体只有一份** | `src/subject.py` 一轮 run 产出一张 `subject.png`；`compose_white` / `flat_overlay` 里**没有任何抠图调用** | 系统里会有七个主体，七张图里的杯子不是同一个杯子 |
| **B** | **生成层看不见主体** | `gen_bg_paste` 的提示词里只有环境；负向词**无条件**排除产品本体；主体由代码 paste 进画布 | 主体变成模型的"近似品"，与实物不符 |
| **C** | **文字层不参与画面生成** | `src/textlayer.py`：文字用**字体文件**绘制，模型一个字都不画 | 图上印着错字，且发布后才发现 |
| **D** | **位置 1 零模型调用** | `compose_white` 是纯确定性合成 | 用概率工具做零容错的任务（主图违规 = 降权/下架） |

**A 与 B 合起来是这套东西最值钱的一句话**：主体从来不是模型画的，所以
「七张图是不是同一个商品」这个问题**结构上不可能答错**，不需要靠"验"来保证。

**另有两条同样有判据的落地纪律（不是第五个不变量，是对"无静默丢失"的要求）：**

| 纪律 | 落地位置 | 判据 |
|---|---|---|
| **跳过必须带机器可读的成因** | `slot_skipped` 记录带 `cause`（`intake` 计划内缺料 / `cutout_error` 环境降级），控制台与验收都读它，**不解析给人看的 `reason` 散文** | `verify_m5.py` A 条：成因不在白名单即红；未知成因要先红一次，逼人回来归类 |
| **每一格都要有下文** | 产物 ∪ 跳过 == 齐套可做；两处都不在的坑位是最坏的一种 —— 日志里也查不到 | 同上（集合比较，按坑位聚合而非数文件） |

前后两类"跳过"对运营的意义相反：`intake` 要补素材照片，`cutout_error` 要关审核台重跑。
只写散文 `reason` 的后果很具体：控制台会笼统说「缺料」，运营照着错方向查半天。

## 4. 表驱动：改数据 → 行为变

控制面唯一核心资产是 `config/slots.yaml`。坑位的一切行为都在表里：

```yaml
- id: 5
  renderer: closeup_crop       # 像素怎么来（必须是已注册的 renderer 名）
  text: overlay                # 文字由谁产生（只允许 none | overlay）
  needs: [closeup]             # 缺料 → 跳过该坑位，不凑数
  background: from_photo
```

判据（写进代码，每次都跑）：

```bash
# orchestrator 里不许按坑位号分支 —— 零输出才算过
grep -En 'slot\["id"\] ==' src/orchestrator.py

# 表本身自洽（renderer 已登记 / needs 非空 / mandatory 满足站点档位 / 校验规则名已实现）
python -m src.schema          # → OK: 7 slots, 6 renderers registered；表内 1/7 路调模型
```

**验收方式是"改数据试验"，不是"跑通了"**：把位置 2 的 `renderer` 改成 `compose_white`，
**不改一行代码**，输出里位置 2 的像素来源就从"纯色底 + 字"变成"纯白底"。
跑通只证明链路通；**改数据能生效，才证明架构对。**

死亡纪律：**每个字段必须写明消费它的代码位置**，写不出消费方的字段不许进表。
本项目已因"声明了但没人读"返工三次（`text_style` / `DASHSCOPE_IMAGE_MODEL` / `text_layout`），
v1 的 `export` 块里还藏着三个，以及两个**假装被校验**的规则名（`no_watermark` / `text_render_ok`）——
后者最危险：它让人以为有保护。

## 6. 七坑位表

| 坑位 | 用途 | renderer | text | 需要素材 | 背景 | 调模型 | 校验 |
|---|---|---|---|---|---|---|---|
| 1 | 主图 / 纯白底 | `compose_white` | none | front | 纯白 | ✗ | strict |
| 2 | 卖点图解 | `flat_overlay` | overlay | front + bullets | 色板 | ✗ | medium |
| 3 | 尺寸规格 | `flat_overlay` | overlay | front + specs | 色板 | ✗ | medium |
| **4** | **场景使用** | **`gen_bg_paste`** | none | front | **生成** | **★ 是** | loose |
| 5 | 细节材质 | `closeup_crop` | overlay | **closeup** | 来自原片 | ✗ | loose |
| 6 | 包装内容物 | `contents_compose` | overlay | **contents** | 纯白 | ✗ | loose |
| 7 | 对比 / 信任 | `compare_side` | overlay | front + **competitor** | 色板 | ✗ | medium |

**七个坑位里只有一个调模型** —— 而这个"只有一个"不是写死的判断，是
`registry` 里每个 renderer 的 `calls_model` 声明数出来的（界面上那条橙色标记读的就是它）。

**为什么只有位置 4 可以生成**：环境是唯一**没有任何人持有事实**的东西
（人工做图时背景也是设计师凭感觉搭的）。其余坑位画的是**事实** ——
材质长什么样、盒子里有什么、竞品长什么样 —— 生成它们等于编造。

**位置 5 必须来自特写原片**：缺特写就跳过，**不许把正面图放大充数**。
**位置 6 缺内容物原片就跳过**：图里根本没有盒子，画一个出来就是假配置。
**位置 7 缺竞品图就跳过**：别人的东西，模型无权编。

## 7. 重做：四档粒度，代价可见

| 粒度 | 语义 | 复用 | 耗时（实测） | 花钱 |
|---|---|---|---|---|
| `text` | 文字层变了 | 拿上一轮文字底重新叠字 | 0.06s | ✗ |
| `placement` | 位置 / 大小变了 | 只动落点与缩放，背景与文字都不变 | 0.22s | ✗ |
| `bg` | 背景像素变了 | 重新生成空背景 | ~60s | ★ |
| `cutout` | 抠得不干净 | 本地重抠主体**与素材**，所有读它们的坑位一起重出 | 主体 21.6s | ✗（本地） |

**四档与架构三层一一对应，不是随手分的档** —— 而这个划分本身就是给运营的**代价提示**：
七成情况（文案、构图）不花钱，只有背景花钱，而背景恰好是唯一本来就该由模型产生的东西。

两条配套规矩：

- **版本不覆盖**：重做出 `slot02_feature_2.jpg`，不覆盖 `_1`。理由不是怕丢文件 ——
  `_1` 记录着"运营当时看过它，然后决定重做"，**那是"哪一版被采纳、为什么"的唯一证据。归因数据就是资产。**
- **「已采纳」由日志顺序判定**：最后一条 `accept` 晚于最后一条 `redo` → 已采纳。
  这样"重做后旧采纳作废"与"比较后仍采纳旧版"两种情形同时正确。
  **导出交付的是 `accepted_version`，不是 `latest`** —— 交付"运营签字认可的那一版"。

## 8. 薄后端：十个接口，不做工作流引擎

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/table` | 控制面：坑位表 + 渲染器声明 + 色板 + 取景池 + `layers` + `kinds` |
| GET | `/api/products` | 商品包枚举（**投递是目录约定，界面不设上传表单**） |
| GET | `/api/plan?product=` | 零副作用干跑 —— 与 `run.py --dry-run` 同一个函数、同一个数 |
| GET | `/api/runs?upc=` · `/api/runs/{id}` | run 列表 / 状态（来自 `run_state`） |
| GET | `/api/runs/{id}/log` | 日志原文 + **坏行单独列出** |
| GET | `/api/file?path=` | 只允许**项目根内**的绝对路径（越界 → 403） |
| POST | `/api/run` | 起一轮，**同步返回 `run_id`**，执行在后台线程 |
| POST | `/api/runs/{id}/slots/{n}/accept` | 采纳 |
| POST | `/api/runs/{id}/slots/{n}/redo` | 重做（body: `{"layer": "text"}`） |
| POST | `/api/runs/{id}/export` | 交付（**未全采纳 → 409**，不是"什么都没发生"） |

三条实现纪律：

- **单实例串行锁**：并发第二次 `/api/run` → 409。缺省串行，因为并发抠图偶发内存不足，
  且并发重做会撞版本号。
- **状态只有一个源**：所有状态从 `run.jsonl` 派生，接口层不自己记状态。
- **参数错误有明确返回码**：`only=[]` → 400（空列表会被当成"全部"，所以显式拒绝，不猜你的意思）；
  非法 layer → 400 并列出可选值；不存在的 run → 404。

v1.20 单页测试台按「核对商品资料 → 生成推荐方案 → 一键生成套图 → 检查候选 → 修改提示词 →

**文档守卫把两类失败分开报，退出码就是这么定的**：
`stale`（产物未同步 → 跑生成器，退出码 2）与 `problems`（写错了 → 人得改，退出码 1）。
混报的后果很具体：人看到一屏红会以为文档烂了，而九成其实是"该跑生成器了"。

**守卫自己也要能被证明会红**：`check_table_guards.py` 直接在真表上改、跑完无条件还原；
`evals/probes/invariants.py` 的每条判据都配一个**植入违规样本**的反向对照。
一个不会失败的断言等于装饰 —— 这一条在本项目里是对所有判据生效的。

`verify_m7.py` 的部分 B 会**起一个真服务**（随机端口）跑 HTTP 契约 ——
因为 M7 实测抓到的两个缺陷（`run_id` 在计划落盘前 404、`only=[]` 被吞成 `None`）
**都是"界面第一次点下去"才会碰到的问题**，进程内验收碰不到。
**契约的错只在边界上现形。**

这些脚本的价值看它们抓到过什么：主体贴边（校验规则查不出的缺陷）、
静默降级换像素、验收脚本自身的假断言（数文件个数）、历史半行日志炸掉四次验收 ——
**每一条都不是"跑通了"能发现的。**

**清理不得改变结论**（2026-09-22 修正，第三类"验收脚本自身的缺陷"）。

收尾的删除动作原来排在结论路径**上**，而本机的批量删除有闸：删**早先轮次留下的内容**
且数量过线时要显式确认，拦下即 fail-closed、直接以非零码结束。
于是长出一类最坏的失败 —— **"删不掉沙箱"冒充成"验收失败"**：
同一天、同一份代码，`verify_m7.py` 13:5x 绿、14:14 红，报出来是"未通过"，
而"未通过"里连一条断言都没红 —— 画面根本没变，是删除被拦了。
`verify_m7.py --keep` 单跑 exit 0 才把它钉死。

两条修正（都往"不需要删"的方向走，而不是想办法绕过删除限制）：

| 脚本 | 原来 | 现在 |
|---|---|---|
| `tools/verify_m7.py` | 结论之前 `if not KEEP: rmtree(SANDBOX)` | **默认不删**（沙箱本来就不需要被删），要删得显式 `--clean`；清理移到结论之后；`except Exception` |
| `evals/run_golden.py` | 固定目录 + 开头 `rmtree(TMP)` | 沙箱改 `evals/.tmp/golden/<时间戳>/`，**不再 rmtree** |

`run_golden` 那处尤其要记：它原先删除的理由是"保证每轮跑在空目录上，否则快照一致
可能只是因为**没真的重跑**"。这个理由依然成立，但**保证方式换了** ——
"目录是不是新的"由时间戳保证（代码说了算），而不是由删除保证（环境说了算）。

判据是一条：**验收脚本的退出码只能是它所验东西的函数。**
会因为自己收尾而变红的验收，比没有验收更坏 —— 人会习惯它的红。

**环境条件长到第二类（2026-09-22 补）。** 上面那类是"删不掉"，新一类是"抠图因内存不足
连续失败" —— 它不是缺陷（产品的行为是对的：重试 3 次、不静默降级、成因可读），
但它让这一批**比齐套可做的少**，于是 `verify_m5.py` 走**退出码 7**，不并入"未通过"。
理由与上面同一条：判定是干净的，少的张数是机器内存的函数，不是代码的函数。

`tools/regress_all.py` 把两类环境条件写成 `ENV_SIGS` 一张表
（签名 + 各自话术 + **只有哪个步骤才能算**），报告里**按签名分组** ——
因为两类的下一动作完全不同（一类等下一轮额度重置，一类要腾内存重跑），合成一句会把人指向错的动作。
若"全链路真跑"被拦下，读它产物的 M3/M4/M5/M6 红就是**连带**，报告里会显式写明 ——
不然人会去改没坏的东西。

**"归到第三类"本身也必须能被证伪（2026-09-22 补，被自己的误判逼出来的）。**
签名原来只看"输出里有没有它"，于是**转述别人输出的脚本会被误判**：
`evals/probes/skip_cause.py` 失败时打印了 M5 输出的尾部（里面带着 `M5-DEGRADE:`）→
一个**真失败**被认成"被环境拦下"，连「未通过」都进不去。
这不是报错，是**红被吃掉了**，比报错更坏。修法两条：
① 每条签名必须写清 `applies_to`（`M5-DEGRADE:` 只在「M5 验收」这一步算，
删除闸对任何写盘的步骤都算）；② 探针不整段照搬被验脚本的输出，只摘失败行。

|---|---|---|---|

两个进程各要一份，后启动的那个必然失败。产品侧此时的行为是正确的（重试 3 次 → 显式报错，
不静默降级），错误文案也已写明这个量级。

**跑验收前先看内存余量。** `tools/regress_all.py` 会自己量，不够就**拒跑**（退出码 8）并指名道姓说

## 12. 实测发现（跑起来才暴露的问题 —— 这是本项目最大的资产）

### v2 期间（表驱动架构）

1. **主体贴边（校验规则抓不到的缺陷）。** `subject.png` 是紧裁切的，当"可用区高度"
   成为约束时（位置 2 有五条文案、文字条吃掉半屏），主体会**精确填满**可用区 ——
   贴图框 `y=0`。它比"观感不好"严重：贴边的商品图平台侧通常不接受，
   而位置 2/3 的校验只有尺寸与文字存在性，**查不出贴边**。
   → 只能由几何保证（`PAD_RATIO = 0.035` 从可用区里扣掉），**不能指望校验兜住**。

2. **色板的双所有者。** 同一张图上强调色有两个来源：标注线箭头读 `catalog.palette.accent`，
   项目符号读 `brand.accent_color`。两者恰好都是 `#C8102E`，所以**看不出来**；
   改一处就会出现"箭头变了、圆点没变"的半套色。
   → 按"随谁变"重新划线：**色板随类目变**（归 catalog），**字体与文字条随品牌不变**（归 brand）。

3. **`forbidden_on_image` 的假保护。** `brand.json` 的 notes 声称"位置 1 命中任意一条即违规"，
   但**没有任何代码读它** —— 与 v1 那个"写着 `no_watermark` 却从未实现"同型。
   → 现在 `planner.extract_facts` 取两份清单的**并集**并逐条记录**命中哪一份规则**
   （下架申诉时要拿这个作依据），`gen_bg_paste` 再把它用作**负向词**：一处数据，两个消费点。

4. **静默降级换像素（全链路最贵的缺陷，M6 抓出）。** `layer=cutout` 重做时素材重抠失败，
   `synth` 里还留着"推理失败就降 floodfill"的旧逻辑 → **同一格的两版图，主体是两条不同抠图路径的产物**，
   而日志只写了"重做成功"。**版本对比的前提被抽掉了**：运营看到的"重做后变好了"其实是换了算法。
   → `INFER_ATTEMPTS = 3`，**每次丢掉缓存的会话**再试（那才是真重试），仍失败抛 `CutoutError`，
   **绝不静默换 floodfill**。
   **第二层（同型缺陷，复审才抓出）**：光丢缓存 + 把局部名置 `None` 其实**没释放** ——
   真正钉住会话的是异常对象自己（`exc.__traceback__` → 栈帧链 → 帧里的 `session`）。
   受控实验（只改"清不清 traceback"这一个变量）：不清 = 旧会话仍活着 `True`（新旧 arena 并存，
   峰值翻倍）；清了 = `False`。内存本就不够时，峰值翻倍 = 重试**必然继续失败**，
   而日志只写"连续失败 3 次"，**看起来像运气不好，其实是自己制造的**。
   → 已修，并加了**机制级**回归断言（`verify_m6.py` K 段用 `weakref` 观测"新会话分配那一刻旧会话是否已回收"），
   否则这个修复下次会被"看起来等价"的写法无声改回去。**"释放资源"要证明，不能声明。**

5. **抠图必须前移。** 同一个抠图调用，进程刚起来时稳，**跑完一次 55—63s 云端生成之后就不稳**
   （ORT `bad allocation` / numpy `MemoryError`）。而位置 6/7 恰好排在位置 4 后面 → "整格失败"。
   → 所有抠图提到模型调用**之前**。这一改同时兑现三条已有规矩：抠图失败不该再去调模型、
   不烧冤枉钱、**一轮只抠一次**（否则"只改了位置"这句话不成立）。

   后来量出了它的真实量级：**一次 `birefnet-general-lite` 抠图（1024² 输入）约需 6 GB 物理 /
   9 GB 可提交内存**（实测：抠图前 availPhys 6851 MB → 抠完 889 MB）。这不是"有点占内存"，
   是**同机第二个进程必然拿不到内存**的程度 —— 两个各揣一个会话的进程会互相挤死
   （后启动的那个 ORT 会在 decoder 的 Sum 节点报 `RUNTIME_EXCEPTION`，**重试也没用，内存是真没有**）。
   → 由此定的两条：报错文案写**量级**（"实测约需 6—9 GB"比"内存不足"有用得多）；
   **不要一边开着审核台一边命令行跑抠图**（见 §10）。

6. **`orchestrator.py` 里偷偷长出的 `if`。** 防线写成 `grep` 并每次改动后跑 ——
   **无输出才通过**。它是"加一个坑位 = 加一行数据"能成立的唯一保证。

7. **验收脚本的收尾删除，冒充成了验收失败（2026-09-22，第三类"验收脚本自身的缺陷"）。**
   从零回归跑出来 12/14，红的两项是 `M7` 与位置 4 快照，报的是"未通过"，但**没有一条断言红**。
   真因：两个脚本的收尾 `rmtree` 撞上了本机的批量删除闸 —— 删**早先轮次留下的内容**、
   数量过线要显式确认，拦下即 fail-closed 退出 1。而清理又排在**结论之前**，
   于是进程死在清理那一步，结论一个字都没打出来。
   同一天、同一份代码，`verify_m7.py` 13:5x 绿、14:14 红 —— 画面根本没变。**这是"看起来偶发"的教科书形态。**
   → 把它钉死的是一个对照：`verify_m7.py --keep`（完全不删）单跑 **exit 0**。
   改法是让沙箱**天然不需要被删**：`verify_m7.py` 默认保留沙箱、清理移到结论之后、
   `except Exception`；`run_golden.py` 沙箱改时间戳目录、不再 rmtree。
   **判据：验收脚本的退出码只能是它所验东西的函数。** 会因为自己收尾而变红的验收，比没有验收更坏。

   同一轮还踩到一个**更浅但更丢结论**的坑：我把"从零回归"写成一次性脚本，
   结果它在写报告前被网络掐断 —— `out/` 里产物齐全、**结论一个字没留下**。
   → 现在每跑完一项立刻整份重写 `evals/last_regress.txt`。

### v1 期间（保留为证据，不删）

7. **抠图曾是整条链路最脆弱的一环，三次都栽在这里。**
   色差阈值法把整图判成前景；洪水填充留碎斑与桌边斜线；`rembg` 从 GitHub 下载读超时 30s。

   工具要在运营机器上跑，就不能假设它能连上 GitHub。

8. **抠图失败会让"边缘类校验"全部假通过。** 四周留白是合成上去的白画布，校验器看到一片纯白，

9. **生成层的禁字条款不能 100% 依赖。** 提示词里已强制写入禁字，模型仍在一张图上画出了 "500ml"。

10. **工具修不了不合规的输入。** 示例输入图里有亚麻布（道具），而主图禁止道具。
    即使抠图完美，只要原图带道具，这张主图就不合规。
    → 位置 1 真正的前置条件是"输入图只有产品本体"，**这应该在入口拦，不在出口报错**。
    （这条正是 M2 的 E0 体检清单的由来。）

11. **示例输入图自带水印（AI 生成的角标），而主图禁止水印。** 本次是"抠图只保留主体"顺带裁掉的 ——
    **这不是去水印功能，是运气**：水印一旦压在主体上就跟着进图了。

12. **同一 UPC 并发运行会撞输出目录 —— 静默摧毁可审计性。** 目录名相同 → `run.jsonl` 以 `"w"` 打开
    截断前者（实测留下半行残片）、图片互相覆盖、**且依然全部 PASS**（校验跑在写盘之前，验的是本进程自己的图）。
    → 目录名加微秒。这是**并发的前置条件**，不修则每次并发都在静默毁日志。
    （那半行残片后来还炸掉了四次验收 —— 见第 13 条。）

13. **验收脚本读日志的口径必须与产品一致。** `verify_m3..m6` 各自写了一份**严格** jsonl 读取器，
    历史遗留的半行日志把它们一起炸掉。→ 统一为 `orchestrator.read_records(d, tolerant=True)`。
    **否则它测的是脚本，不是产品。**

14. **主体外观不可复现 —— v1 最大的风险（架构缺陷，不是参数问题）。**
    同一商品、同一提示词、连续三次生成，产品外观三次都不同（银灰细筒 / 深灰粗筒 / 白色粗筒）。
    后果：**副图里的杯子和主图里的杯子不是同一个东西**。
    → 正确的切法是 **主体层 = 确定性（取自实拍图）／背景层 = 生成／文字层 = 确定性**。
    **这条就是 v2 四条不变量的直接来源** —— A（主体只有一份）与 B（生成层看不见主体）都是它的答案。

15. **探针说「已还原」，但它顺手改掉了行尾（2026-09-23，第三类「验收脚本自身的缺陷」的第二次）。**
   `check_table_guards.py` 与两个反向对照探针改的是**真文件**（`config/slots.yaml`、
   `docs/INDEX.md`、`README.md`、`_working/**/state.md`），还原却用
   `read_text()` + `write_text()` —— 读时把 CRLF 归一成 LF，写时按 Windows 默认补回 CRLF。
   于是**凡是 LF 的文件，跑一次探针就被改成 CRLF**：内容一样、字节不一样，
   「已还原」从"字节一致"退化成"内容大概一致"。而本仓库同时存在两种行尾（README/卡片/slots.yaml 是
   CRLF，计划与新写的工具是 LF），**没有任何守卫管这件事** —— 所以它一直没人发现。
   → 改成备份**字节**（`read_bytes()`）、还原**字节**（`write_bytes()`），
   并在 `finally` 里比一次：不一致就多报一条红，让「已还原」这句话本身也有判据。
   证据：三个探针的还原行现在打印「（字节一致）」；改动前后 `README.md` / `docs/INDEX.md` /
   `config/slots.yaml` / `state.md` 四份文件的 sha256 不变。

## 13. 交付单元：一份对应一个动作，且有人守

### 13.1 改的是交付单元的**粒度**，不是文档数量

此前有 9 份文档，每份对应一个**横切面**（业务逻辑 / 使用形态 / 架构设计 / …）。
后果不是"文档多"，而是：**每个新接触的人（包括隔两周回来的自己）都必须现场把 9 份
在脑子里合成一次**，才拼得出"这一格该怎么用"。

参考的三个电商图技能库是 26 份 `skill.md`，每份对应**一个动作**
（触发语 / 能力边界含"不做" / 输入阈值 / 参数带理由 / 模板 / 执行步骤 / 现象-原因-处理）——
**读一份就能干活**。差别不在篇幅（它们 10364 行，本项目 4662 行），
在交付单元是"卡"还是"章节"。

现在交付单元是 7 张**由表生成**的坑位卡：`docs/cards/slot-N.md`。

**分工（这条分工是行数上限逼出来的，不是排版偏好）**：

| 文件 | 写什么 |
|---|---|
| `docs/cards/README.md` | 该读哪一张 + **七格共有**的规矩（齐套怎么算 / 主体为什么只有一份 / 抠图为什么提前 / 导出阈值 / 要签什么字） |
| `docs/cards/slot-N.md` | 只写**这一格与别格不同的**：像素从哪来、要不要文字、缺什么料跳过、失败走哪一级、照抄哪条命令 |

第一版把每张卡都写成"自给自足"的：七格的共有规矩每张抄一遍 → 4 张越过了 70 行上限，
而砍掉的字里**没有一句是这一格特有的**。改成分工之后卡都落在上限内 ——
**而"谁把共有段落抄回卡里，行数上限会先炸"就是这份分工的守卫。**

### 13.2 卡是生成的，不是手写的

```bash
$PY tools/gen_slot_cards.py           # 改 slots.yaml 那一行 → 跑这个
$PY tools/gen_slot_cards.py --check   # 只比对；不一致 → 退出码 2
```

每张卡带横幅、由 `tools/check_docs.py` 守卫一致性。卡里**没有一句新知识**：
行为/素材/阈值来自 `slots.yaml`，像素来源与 `calls_model` 来自 `registry` 的声明，
"失败走哪一级"来自 `fixers.CHECK_RUNG`，"要签的字"来自 `intake.ATTEST_ITEMS`。
**卡只是把散在代码里的判断点，按坑位重新排版的一个视图。**

### 13.3 文档守卫：让文档里的话有人守

`tools/check_docs.py` 六项检查，两类失败**分开报**：

| 类 | 含义 | 怎么办 | 退出码 |
|---|---|---|---|
| `stale` | 产物未同步（卡与表不一致、幽灵卡） | 跑生成器即可 | 2 |
| `problems` | 写错了（README 七坑位表与表不符 / 抄的数字不对 / 命令跑不通 / 卡超限） | 人得改，生成器修不了 | 1 |

混报的后果很具体：人看到一屏红会以为文档烂了，而九成其实是"该跑生成器了"。

其中"命令真跑"这条：受管文档 ```bash 围栏里的命令**会被真跑**（缺 `--dry-run` 就自动补一个），
rc 必须 0。它验的是那句"**照抄能跑**"，而不是"我抄的时候是对的"。
跳过哪些命令、为什么跳，`--explain` 会全说出来 —— 没有理由的跳过就是一条被悄悄关掉的断言。

守卫自己有一处值得记的坑：README §4 那句
`grep -En 'slot["id"] ==' src/orchestrator.py` **不能**被守卫照抄执行 ——
`grep` 在零匹配时退出码是 **1**，而这条铁律的判据正是"零匹配才算过"。
照抄会把判据整个反过来（通过变失败、失败变通过）。所以守卫用 Python 自己实现了一遍那个判据。
**"命令要真跑"的前提是命令与判据同向；不同向时，正确做法是把判据实现一遍。**

### 13.4 修复阶梯 L0：把机器一步能修的从人手里拿回来

此前只做了"检出"这一半：校验失败 → 跳过该格 → 交人签字。于是
**机器一步能修的**（白底偏灰 / 占比不足 / 非 1:1 / 分辨率不足 / 体积超限）
**被写成了人的责任**，而人看到的提示是"工具修不了"。

现在 `src/fixers.py` 实现 L0，阶梯是
`L0 确定性修 → L1 重放某层 → L2 重生成 → L3 签字`，**从便宜往贵试，不许跳级**。三条纪律：

- **修完必须复验。** 成功的判据不是"我执行了修改"，是"那条校验现在过了"。修了没修好 → 如实报 `unfixed`。
- **修不了要明说。** `has_text_block`（位置 1 出现文字）**绝不进 L0** —— 把文字擦掉是*掩盖违规内容*，不是修复。
- **默认关**（`--autofix`）。它会改像素；默认开会让"产物到底是不是渲染器直接产出的"变成要读日志才知道的问题。

`CHECK_RUNG` 是"失败 → 走哪一级"的**唯一分流点**：加一条校验规则时必须同时给它归类，
否则"它落到哪一级"就变成没人说得清的问题 —— 而那是阶梯失效的开始。

### 13.5 四条不变量：从"声明"变成"判据"

此前四条不变量只写在 README 和注释里 ——「改动不得破坏四条不变量」在工程上等于没有约束，
因为**"破坏"没有定义**，也就没有东西会在破坏发生时响。

`evals/probes/invariants.py` 给每条不变量配上判据，全部是静态/纯函数级（毫秒、不联网、不产图）：

| 不变量 | 判据 |
|---|---|
| **A** 主体只有一份 | 渲染器层零抠图调用；产出主体 alpha 的调用口只有 `subject.py` / `cutouts.py`；调 `make_main_image` 必须显式 `force_passthrough=True`（默认它会自己抠一遍） |
| **B** 生成层看不见主体 | 真实请求体无图像字段；**植入** `data:image` 的请求体必须被认出字段路径；守卫对干净请求与占位图**不许误报** |
| **C** 文字层不参与画面生成 | 提示词（正 + 负）里不含任何卖点字面 / 规格数值；禁字条款由代码追加，不由取景提示提供 |
| **D** 位置 1 零模型调用 | `compose_white` 那个文件里连 `imagegen` 都没有 —— 不是"声明为 false" |

**每条判据都配一个"植入违规样本"的反向对照**：只有正向（真实文件干净）不算证明 ——
万一判据本身是瞎的呢？15 条判据里 7 条带对照，而且对照必须变红。

顺带记一条判据拆分：`background_mask` 与 `remove_background` 看起来都是"抠图"，
但前者是**背景分割原语**（L0 刷白背景也在用它），后者才**产出主体 alpha**。
第一版没分，于是 `fixers.fix_background` 被报成了违规 —— **假报警的代价不是噪音，
是人开始不信报警。**

### 13.6 位置 4 冻结快照：只打在高风险的那一格

参考库里 26 个技能只有 4 个配了 golden case，而那 4 个全是同一类：**把源图送进模型**。
本项目的对应物就是位置 4（全链路唯一调模型、也是唯一"像素里有一部分不是事实"的那一格）。
其余六格是纯确定性合成 —— 给它们也配快照只是七倍工作量、零倍信息。

`evals/run_golden.py` 用**无 key + floodfill** 跑一格（离线、确定性；一个"有时会变"的快照
比没有快照更坏，因为人会习惯它的红），逐值冻结 23 项：提示词逐字、取景提示、
裁切框 / 缩放 / 贴图框、主体 sha256、校验结论，以及 `subject_excluded_from_model` 仍是 **null**。

最后那条锁的是**口径**：没发请求时不许宣称"我没把主体送出去" ——
对一次没发生的请求说这句话是句废话。

### 13.7 五级验收要有人跑得动，且结论要留得下

**两条都不是"顺手加的"**，各对应一个已经发生过的损失。

**① 结论要留得下。** 从零复跑一次约 3 分钟。前身脚本（`_regress2.py`）把结果攒在内存里、
最后一次性写文件 —— 结果在网络中断时 `out/` 里产物齐全、**结论一个字都没留下**，
只能从头判断"那 11 项到底绿没绿"。现在每跑完一项立刻整份重写
`evals/last_regress.txt`，中断后打开文件就知道停在哪一项。

**② 绝不许并发。** 单次抠图实测约需 6 GB 物理 / 9 GB 可提交（本机 14 GB）。
两个各揣抠图会话的进程同时跑，后启动的那个会在 ORT 里报 `bad allocation`，
落到底层是 `MemoryError: Unable to allocate 1.76 MiB` 这种**看着偶发、其实必然**的失败
（这个坑当场踩过：以为"回归本来就不稳"，实际是我自己同时起了第二个验收）。
所以 `regress_all.py` 起跑前先量内存余量，不够就**拒跑**（退出码 8）并指名道姓说
"另一个进程可能正揣着抠图会话" —— 发警告然后照跑等于没做，警告会被忽略，这已经被验证过了。

**③ 从零要真从零。** `--fresh` 先把 `out/` 挪到 `out_prev/`（重命名，不删，可回退），
跑完再**断言** `orchestrator.latest_run()` 指的就是这一轮新产的目录。
不挪走旧产物的话，"从零"只是说法 —— 而"这批图是不是当前代码产的"恰恰是这一步要回答的。

**④ 验收脚本的退出码只能是它所验东西的函数。** 见 §9「清理不得改变结论」。
清理排在结论之后、默认不删、`except Exception` —— 三条都是为了同一件事：
不让收尾动作有资格改结论。

### 13.8 跳过要说清"为什么"，而"环境拦下"也必须能被证伪

**A 条原来只会两分**（做了 / 没做）。真因不在判据写得笨，在**数据形状**：
`slot_skipped` 有两个生产者 —— `assets.resolve`（入口缺料）与 `orchestrator`（运行时抠图连续失败），
而两者**都只把成因写在散文 `reason` 里**。于是 `run.py` 收尾汇总只能笼统说「缺料」——
运营看到会去翻素材照片，而真正该做的是关掉审核台重跑。**两份真相里，机器读的那份必须是结构化的。**

修法：跳过记录带 `cause`（白名单 `intake | cutout_error`），判据按成因分流，三档退出码：

| 情形 | 退出码 | 含义 |
|---|---|---|
| 成因不在白名单 / 没有 `reason` | **1** | 假通过：无从分起，必须先红一次逼人回来归类 |
| `cause=intake`（入口缺料） | **0** | 计划内跳过，不降级、不凑图 —— 设计如此 |
| `cause=cutout_error`（运行时抠图失败） | **7** | 环境降级：本批比承诺的少，带 `M5-DEGRADE:` 标记 |

三档互不相同，`evals/probes/skip_cause.py` 用**单变量植入**把它钉住
（只改 `cause`，其余一字不动）：1 / 0 / 7 必须都对上，且 7 那份必须带标记。
**若某天它们合成同一个码，探针会红 —— 那是设计被改坏的信号。**
产物里一条跳过都没有时（7/7 全成），探针会先人工植入一条 ——
植入点必须挑"别的断言够不到"的坑位（不声明 `cuts`、不调模型、且不是别的断言点名的格子），
否则一去掉它的渲染痕迹，`assert_g` 的 want/got 就失衡、三个变体一起假红。**这也是实测撞出来的。**

**"归到第三类"本身也要能被证伪。** 这一步我一开始就写错了：`regress_all.py` 只看
"输出里有没有环境签名"，于是对照探针失败时打印 M5 的输出尾部（带 `M5-DEGRADE:`）→
**一个真失败被认成"被环境拦下"，连「未通过」都进不去。这不是报错，是红被吃掉了。**
修法：每条签名写清 `applies_to`；探针只摘失败行、不整段照搬被验脚本的输出。

另外两处"我引入又被自己抓出"的洞记在这里，因为同类会再犯：
① A 条第二判据比的是 `got ∪ skipped == doable` —— 但 `assets.resolve` 会把**入口缺料**的坑位
从 doable 摘掉，于是**一旦真缺料，计划内跳过的坑位被判成"多出来的"**（最该看准的时刻假红）。
改成比**全集** `doable ∪ 入口跳过`。
② 一处跳过在日志里出现两条（运行时立刻记一条 + 收尾整批重记一条，设计如此、被中断也留痕），
判据没去重 → 一处跳过报成"N 条未通过"，**把数量当成严重度**。改成按 `slot_id` 聚合。
