## 1. 一句话

**把一个商品，变成一组"买家一眼认出是同一个商品"的七张合规图。**

现状是运营手工做这七张：抠图、摆位、嵌字、生成背景，一步不落。
工具化之后产出的东西一模一样——**同样是这七张，同样的动作**。

所以这门业务的价值主张**不能是"我会做这七件事"**。那是美工本来就会的活，
而且他做得更好看。

真正的差别只有一条：

> **人工靠"同一个人、同一段时间、同一套模板"保证这七张是一套。
> 这份一致性长在人的脑子里，从来不需要被写下来。
> 一旦要并行、要批量、要换人做，它当场断裂——系统必须把它显式写下来，并钉到结构上。**

**动作一样，一致性的来源不一样。这是全部。**

## 2. 七张图的像素从哪来（这门业务的完整动作清单）

| # | 坑位 | 输入 | 做什么 | 输出 | 像素来源 |
|---|---|---|---|---|---|
| 1 | 主图 | 商品原片 | 抠出主体 → 按规则定位 → 合成白底 | 白底主图 | 实拍（抠） |
| 2 | 卖点图 | 白底主图 + 卖点文字 | 排版、叠字 | 卖点图 | 实拍 + 字体 |
| 3 | 规格图 | 白底主图 + 规格表 | 排版、叠字 | 规格图 | 实拍 + 字体 |
| 4 | 场景图 | **只有背景描述，没有主体像素** | 生成背景 → 把主体贴进去 | 场景图 | **模型生成（背景）** |
| 5 | 细节图 | 特写原片 | 裁切、放大 | 细节图 | 实拍（另一张） |
| 6 | 内容物图 | 白底主图 + 内容物原片 | 拼合 | 内容物图 | 实拍 |
| 7 | 对比图 | 白底主图 + 竞品原片 | 并排 | 对比图 | 实拍 |

三处容易看漏的地方：

- **第 5 张不读白底主图。** 细节图要展示的是"细节"，拿主体图去放大会糊——它必须读特写原片。
  推论：**没拍特写，这张就必然不做**，不是选择，是物理必然。
- **第 6 张不一定存在。** 商品本身没有内容物（例如一个整块抱枕），这张图就不存在。
- **第 7 张有法律风险。** 它会把竞品原图并排放进成品图，所以"竞品图里不能有别人的 logo"
  是一条额外责任。

### 分水岭：为什么七张里只有第 4 张调模型

**因为只有它的像素没有事实持有者。**

那块木桌、那束光，没有人拍过——它可以被编造，编造不构成欺骗。
而其余六张的像素，要么来自原片（有事实），要么来自文字（有事实）。**谁敢编，谁就是造假。**

由此得到一条判据，它是整套系统的地基：

> **一条信息错了，能不能被「对照实物或平台规则」发现？**
> **能 → 必须确定性；不能 → 才可以交给模型。**

用它切开一张图里的三类信息：

| 信息 | 能不能对照 | 所以 |
|---|---|---|
| 商品长什么样 | 能（对照实物） | 必须确定性 → 实拍抠图 |
| 图上写了什么 | 能（对照规则与事实） | 必须确定性 → 字体文件绘制 |
| 处在什么环境 | 不能 | 才可以生成 → 调模型 |

**跳过这条判据会得到的错误结论**：以为模型生成的是"整张图"（提示词 + 原图 → 新图）。
正确结论是模型**只生成背景层**。二者在电商语义上差一个量级——前者导致"实物与图片不符"。

## 3. 真正的业务复杂性：不是"做什么"，是"不许发生什么"

这门业务的复杂度**不在动作里**（抠图、排版，美工干了二十年），
**在六条红线上**——错了就上不了架、或者出事：

| # | 红线 | 违反的后果 | 系统对策 |
|---|---|---|---|
| 1 | 七张必须是同一个商品 | 买家不敢信，转化崩 | 主体只有一份，且模型看不见它 |
| 2 | 数字与文字不能错 | 客诉，且构成虚假宣传 | 文字不进模型，用字体文件画 |
| 3 | 不能带水印 / 道具 / 竞品 logo | 下架 | 工具判不了 → **要求人签字** |
| 4 | 缺料不能凑图，只能少做 | **花掉信任，最贵** | 缺料的坑位不进执行计划 |
| 5 | 分辨率不能低于平台下限 | 平台直接拒 | 入口体检，不合格**整批停** |
| 6 | 不能该调一次模型却调了七次 | 成本失控 | 表里只有一行声明调用 |

**六条全是"不许"，没有一条是"要做"。**

这解释了一个常见误判：为什么人工做的时候"不觉得复杂"？
**因为人工做的时候这六条"当然不会发生"——一个人从头做到尾，他自己会看。**
复杂度是存在的，只是被人的注意力默默吸收了。

## 4. 人工做 vs 系统做：差别到底在哪

动作清单完全一样（§2）。差别在三处：

| | 人工 | 系统 |
|---|---|---|
| 一致性靠什么保证 | 一个人记住、一个人盯 | **结构上不可能不一致** |
| 出错的样子 | 忘、赶、换人、状态差 | 没写下来就断 |
| 交付物 | 七张图 | 七张图 **+ 一份能回溯的账** |
| 谁来担责任 | 没人（默认不会错） | 明确到人（签字） |

第三条最容易被忽略：**"这版是谁批的、为什么批"在人工流程里根本不存在**，
因为它只发生在一个人的脑子里。系统化之后，这个问题会立刻被问出来——
所以 `run.jsonl` 不是"日志"，是**业务凭证**。

**"主体只有一份"这条不变量，本质上是把"我记得"变成了"结构上没有别的可能"。**
这就是这门业务的全部技术含量的所在处。

## 5. 业务对象：三个

| 对象 | 定义 | 关键性质 |
|---|---|---|
| **案卷（Run）** | 一个商品的一次上架素材生产 | 编号 = UPC。**业务的原子单位，不是"一张图"** |
| **坑位（Slot）** | 案卷里的七个位置，各有固定职责 | **是模板，不是内容** |
| **决定（Decision）** | 人对单个坑位的一次判断 | 只有两种：采纳 / 重做（重做**必带原因**） |

**为什么"业务单位是七张而不是一张"值得单独说**：七张在电商语义里是一组，
组内必须同源。所有架构约束（主体只有一份）都是从这条业务事实推导出来的，不是技术偏好。

## 6. 状态机：两条线

### 案卷线（由七坑位聚合而来）

```
已投递 → 运行中 → 待审 → 审核中 → 齐备可导出 → 已交付
```

**转移条件**：七坑位全部采纳 ⇒ `齐备可导出`；任一张回到待审 ⇒ 退回 `审核中`。

### 坑位线（每个坑位独立）

```
待生成 → 待审 → 已采纳
           ↑        │
           └─重做───┘   （仅该坑位回到待审）
```

**两条业务规则必须写死**：

1. **重做只影响单个坑位，不重置整个案卷。** 运营改一张图，不该被迫重审另外六张。
2. **重做必须归因到具体一层**，四选一：文字 / 位置 / 抠图 / 背景。
   归因不是流程要求，它是**采纳率数据的唯一来源**——没有它，模板永远不改进。

四档的代价差异是结构性的，不是承诺：

| 归因 | 重算什么 | 耗时 | 花钱 |
|---|---|---|---|
| 文字 | 只重画文字 | 约 0.1 s | 否 |
| 位置 | 只挪主体 | 约 1 s | 否 |
| 抠图 | 重抠主体 | 秒级 | 否 |
| 背景 | 重新生成背景 | 约 63 s | **是** |

**"位置不对 = 免费"是一句结构事实**：位置层的重做复用上一轮的生成底，
不重新调模型。它靠上下文构造决定，不靠任何人记得。

## 7. 谁在用，他必须懂什么

### 使用者的画像

- **懂亚马逊图片规范**（这是他的专业，教不了也不该教）
- **不懂技术**（不写 JSON、不碰命令行、不懂"层"这个词）
- **要连续操作**（一天多个商品，鼠标太慢）

### 系统替他扛的（这些他不必懂）

抠图（模型、内存、降级）· 几何（位置、占比、留白一处算好）· 同源（七张共用一个主体）·
成本（表里只有一行声明调用）· 版本与采纳（哪一版是要交付的）

### 系统当前漏给他的（这些他被迫懂）

| 漏出去的 | 属于 |
|---|---|
| 素材的目录与字段名 | **实现债**（可修：投递前下发素材清单） |
| 签字各项的技术叫法 | **实现债**（可修：换成业务语言 + 给判断辅助） |
| "层"这个抽象概念 | **实现债**（可修：让他说"哪里不对"，再由系统映射到层） |
| 改文案要离开界面编辑 JSON | **实现债**（可修：文案入口进界面） |
| 七张分别要表达什么 | **业务必然**（只能靠培训） |
| 缺哪料就不做哪张 | **业务必然**（培训 + 界面提示） |

**这张表的用法**：左列该修，右列该培训。**把两列混在一起，就是"人不知道该理解什么"的根源。**

### 一条因果，值得单独记住

> **往用户身上漏的每一处复杂性，系统都会长出一层界面去承接它。**

| 漏出去的 | 为它长出来的 | 真正该做的 |
|---|---|---|
| 素材标准（收到才说"会被放大"） | 齐套展示的前两步 | **投递前把要求说清楚** |
| 归因责任 | 四档选择器 | 让用户说"哪里丑"，再映射到层 |
| 签字责任 | 六项确认表单 | 给签字辅助，别只给勾选框 |
| 内存约束（6—9 GB） | 单实例串行锁 | 换更小的模型 |

**右列全是"往前挪"，左列全是"加界面"。往前挪更便宜。**

### 一个必须承认的能力缺口：设计

第 2、3 张图（卖点图 / 规格图）的排面是"白底 + 主体 + 几行字"，
**它解决的是"不出错"，不是"好看"。**

这是理性取舍的结果，不是疏忽：

- 让模型画字 → **好看，但会写错字**
- 用字体文件画 → **绝不错字，但没有设计感**

**判据：错字是事故，难看不是事故。** 所以选了后者。

但要明确记录缺口：**设计这件事，系统只解决了"一致"，没解决"好看"。**
而且真要补设计，"七张必须共用一套视觉语言"会立刻变成新的硬约束——**又绕回一致性**。

## 8. 界面 → 业务的映射

界面不是七个并列功能，是**一条主干 + 两类挂件**。

```
主干（运营日常全在这）
  ① 收件 / 齐套判定   只读：这次做哪几张、跳过哪几张
  ② 生成              只做"减"：默认推荐全集，关掉不想做的
  ③ 审核台            唯一动手处：一屏七张 + 采纳 / 重做 / 导出
  ④ 控制面            只读：坑位表、渲染器声明、重做档位

挂件 A · 控制面（改规则时才去）
挂件 B · 证据（排查时展开）
```

**判据**：既不属于主干、又不属于两类挂件的元素，**它就不该存在**。
用来挡住"顺手加个仪表盘""顺手加个历史列表"。

### 关键对应关系

| 界面上的东西 | 对应哪条业务逻辑 |
|---|---|
| 一屏七张不分页 | 业务单位是"七张一组"；组内同源**只有并排看才判断得出来** |
| 四档重做（文字 / 位置 / 抠图 / 背景） | 对应架构的层，也对应四档代价 |
| 重做必选原因 | §6 的规则 2，也是采纳率数据的唯一来源 |
| 生成前先展示齐套判定 | 输入缺失在**入口**暴露，不等出口报错 |
| 三张以上都要换背景时提示"问题在计划上" | 背景由同一份计划生成，单张重做只是重复同样的失败 |

## 9. 业务闭环：两条回路

开环的业务必然漂移，所以有两条回路：

| 回路 | 从哪到哪 | 作用 |
|---|---|---|
| **内环** | 决定 → 处理 | 单张重做，只重跑出事的那一层。保住**单件可用** |
| **外环** | 采纳率 → 控制面 | 按坑位 / 取景 / 提示词版本统计，反哺模板。让业务**在变好** |

**外环是唯一能证明"这个工具在持续解决问题"的东西。**
没有它，工具只是把人工从七步压到两步，然后水平就封顶了。
（当前状态：**外环未实现**——归因数据已经在产出，但没人收。）

## 10. 明确不做

| 不做 | 业务理由 |
|---|---|
| 上传到亚马逊后台 | 需要账号权限与审核反馈，且**导出即业务的终点** |
| 在线图片编辑 | 一旦开始做，它会退化成 PS，永无止境 |
| 审批流 | 一个人就是审，没有第二方 |
| 项目管理 / 历史列表 | **目录本身就是历史**，加一层是重复 |
| 仪表盘 / 图表 | 第一版日志够用，等有 20 个商品的数据再说 |

## 11. 两条回路之外，还缺一个环：确认它该存在

前面十条全部在回答"怎么做对"。**没有一条回答"该不该做"。**

这门业务的前提是一句用户原话：**"七轮循环很痛"**。
这句话从来没有被量化过。要量的是三个数：

1. 一款新商品，七张图从选图到上架，实际花多少人时？
2. 其中多少是纯重复劳动？
3. 现在怎么做、花不花钱（外包？美工？）

**判据（唯一一条能证伪整个项目的判据）**：

| 三个数的结果 | 结论 |
|---|---|
| 约两小时 | 这套系统省的工时抵不过它的维护成本 → **它是过度工程** |
| 约两天 + 外包 800 元 | 值得继续 |

**重复次数 × 单次错误的代价** —— 这是它值不值得存在的分界线。
一天做 1—2 个商品，人工就够了。

## 12. 最小骨架 vs 生长项

> 判据：**一个环节第一版是否必须有，取决于它是不是某条不变量或红线的执行点。** 不是，则推迟。

### 骨架（缺一项链路就不成立）

| # | 环节 | 为什么是骨架 |
|---|---|---|
| 1 | 坑位规范表 | 控制面本身，是交付物。没有它，每次运行都在即兴 |
| 2 | 抠主体（一次、落盘） | 红线 1「七张同一个商品」的物质基础 |
| 3 | 背景生成（仅第 4 张） | 唯一需要模型介入的地方 |
| 4 | 主体贴入 + 叠字 | 确定性层，接缝与文字正确性的落点 |
| 5 | 分级校验 | 红线 2 / 5 的执行点 |
| 6 | 落盘 + 日志（含主体指纹） | 可回溯，且「主体同一」可断言 |
| 7 | 审核台 | 唯一无法自动化的人工动作 |

### 生长项（真实需要出现时再做）

合规视觉检测 · 第 4 张的局部重绘 · 批量与并发调度 · 多用户与权限 ·
仪表盘与历史列表 · 跨站点本地化 · **采纳率回流闭环（§9 外环）**

### 已排除（不是推迟，是结构上不成立）

| 方案 | 为什么不成立 |
|---|---|
| 让模型直接出整张图（含字） | 主体确定性 ⇒ 背景看不见主体 ⇒ 画不出引线标注；且中文必错字 |
| 圈选重绘修文字 | 该技术是**擦除器不是修正器**：它只是再随机生成一次，不保证字形正确 |

## 13. 待确认（业务级，未解决）

| 级别 | 事项 | 影响 |
|---|---|---|
| ⭐⭐⭐ | **一天做几个商品？** | **决定这东西该不该存在**（§11） |
| ⭐⭐⭐ | 运营是否接受"目录投递"，还是必须有上传界面 | 决定入口形态 |
| ⭐⭐ | 卖点文案由谁提供、什么格式 | 决定输入门槛（见下） |
| ⭐⭐ | 用户能不能把"这张不好看"说成四档里的一个 | 若不能，四档粒度就该拆掉 |
| ⭐ | 采纳率的验收标准：多少算"这个工具可用" | 决定外环何时算闭环 |

### 一个被忽略的业务变化（风险）

工具化改变的不是操作步骤，是**运营的角色**：

| | 现状 | 工具化后 |
|---|---|---|
| 产出什么 | 提示词 | **卖点文案 + 审核判断** |
| 核心技能 | 会调 prompt | 会提炼卖点、会判图 |
| 节奏 | 一张一张来 | 一次一组 |

两条风险：

1. **输入质量可能下降。** 规则要求文案来自人、不由模型编。如果运营没有写文案的能力，
   工具再对，输入也是废的。
2. **审核能力的门槛被隐藏了。** 现状下"挑哪张"就是运营在做，工具化后这件事**一点没减少**，
   只是从"挑七张候选"变成"审七张成品"。
   **别把"自动化生成"误当成"自动化判断"。**
