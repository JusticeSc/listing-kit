## 0. 结论先行

三条，按严重度排序：

| # | 结论 | 性质 |
|---|---|---|
| **1** | **同一事实在文档里有 2–3 种说法**，且矛盾就藏在同一份文档内部 | 硬缺陷，必须拍板 |
| **2** | **第一性推导没有改变任何一个决策**——它给已有结论换了个说法 | 术语外壳 |
| **3** | **我的工作模式**：每次用户要求简化，我都用一份更完整的文档回应 | 最该反思的一条 |

根因只有一条：**同一内容在 3–4 份文档里重复维护，没有单一事实来源。** 改一处就要改四处，必然漂移。下面所有"硬矛盾"都是这条根因的症状。

## 1. 硬矛盾（必须先拍板，否则代码没有依据）

### 1.1 「七张里有几张调模型」—— 6 处 2 种说法 ⭐⭐⭐

| 出处 | 说法 |
|---|---|
| `架构设计.md` §4 表 + 表下注 | 位置 2 = 0，位置 4 = 1 → **「降为 1 次背景生成」** |
| `架构设计.md` §9 `bg_kind` 表 | `generated` 适用 **「2 / 4」** → 表下写 **「七路里只有两路调用模型」** |
| `系统设计方案.md` §5.4 表 + 表下注 | **1 次** |
| `业务流程与提效设计.md` §4.4 表 + 表下注 | **1 次** |
| `业务逻辑.md` §11 骨架第 3 条 | 「背景生成（仅 **2 张**）」 |
| `使用形态.md` §2.1 界面图底部 | 「**2 路**调用模型」 |

**最严重的是第 1、2 行：同一份 `架构设计.md` 内部自相矛盾**（§4 说 1 次，§9 说 2 次）。

这不是笔误，是两种设计混在一起：**「位置 2 用纯色底（省）」和「位置 2 用生成留白（好看）」是两个不同的产品决定**，文档没做选择，两处各写了一个。而它直接决定成本、耗时、失败面。

> **待拍板：位置 2（卖点图）的背景，纯色底还是生成背景？** 建议纯色底——理由见 §1.1 注：卖点图要的是可读性，纯色底更清晰、更便宜、不会更差。

### 1.2 不变量 A 与位置 5/6 直接冲突 ⭐⭐⭐

- `架构设计.md` §3 表写：**不变量 A —— 主体只有一份，7 个坑位读同一个 PNG**
- `架构设计.md` §4 表写：位置 5 = 「实拍局部裁切」、位置 6 = 「实拍多件合照」
- 同一节附注还自己写着：**「位置 5、6 不需要抠图」**

**矛盾是硬的**：位置 5/6 根本不读 `subject.png`（一个读原图裁切，一个读另一张合照）。所以「7 个坑位读同一个 PNG」在事实上只有 **5 个坑位**成立。

这不是表述问题——**不变量 A 对全部七路不成立，它只是对五路成立**。文档没有察觉。

> **待拍板：位置 6（内容物）到底用不用主体资产？** 见 1.3。

### 1.3 位置 6 抠不抠 —— 两份文档说法相反 ⭐⭐

| 出处 | 说法 |
|---|---|
| `架构设计.md` §4 | 位置 6 = 实拍多件合照，**不需要抠图** |
| `业务流程与提效设计.md` §1.2 | 「内容物图：**再抠一遍**（杯子 + 盒子 + 说明书的合照）→ 铺底 → 打字」 |

`业务流程` 那份是**照着人工现况写的**（人确实抠一遍，因为要铺纯色底）。`架构设计` 那份是**照着"省事"写的**。

两者只能留一个。若位置 6 要铺纯色底 → **必须抠**（合成层要拿主体）；若不抠 → 就得保留原始背景直裁，那就不是"纯色底"。

### 1.4 位置 3 规格图的数字没有来源 ⭐⭐⭐

- `架构设计.md` §10 **E0 输入** = `main.jpg` + `copy.json` + 可选 `competitor.jpg` —— **没有规格字段**
- 而位置 3 要标 `8.5 in / 3.2 in / 500 ml`
- `系统设计方案.md` §3.4 门禁表自己写着：**尺寸规格图「缺失已确认规格 → 阻止创建」**
- `系统设计方案.md` S0 才补了可选 `facts.json`

**`架构设计.md` 的输入契约缺一个必需字段**，且与它自己的门禁逻辑不符。规格数字必须来自运营实测（`业务流程` §1.2 第 1 天的"量尺寸、称重"），**工具不能推算**。

### 1.5 `render_path` 与 `bg_kind` 决定同一件事 ⭐⭐

`系统设计方案.md` §6.1 字段字典里：

| 字段 | 文档给的定义 |
|---|---|
| `render_path` | `compose`/`generate`/`generate_then_text` —— **决定是否调模型、是否叠字** |
| `bg_kind` | `white`/`solid`/`generated`/`crop` —— **决定是否调模型** |

**两个字段都在决定"是否调模型"。** 这是两个真相源，漂移是迟早的事——而且 §1.1 那个矛盾就是这么来的（一处按 `render_path` 数，一处按 `bg_kind` 数）。

实际上 `render_path` 是 `bg_kind` + `text_mode` 的**派生值**，不该独立存在。

### 1.6 已被判定"结构上不成立"的 `native`，仍留在字段字典里 ⭐

- `架构设计.md` §6：native **「结构性排除，不是暂缓」**
- `系统设计方案.md` §6.1 字段字典：`text_mode` = `none` / `overlay` / **`native`** ← 仍然列着
- §6.2 又把它排除一遍

**一个被判定不该存在的取值，还留在控制面契约里。** 这是死字段的变体：字段活着，结论说它不该活。

## 2. 站不住的主张（术语外壳）

> 判据只问一句：**这句话改变了哪个实际决定？** 没改变任何决定的，就是包装。

### 2.1 「主语同一律」是伪逻辑 ⭐⭐⭐

`架构设计.md` §2.4 写：

> **A 主体只有一份** —— 逻辑根据：**主语同一律**。若七张里的东西各不相同，这组断言就没有共同主语，**逻辑上不成立**。

**这是把业务约定包装成了逻辑律。**

七张图是七张独立的图像，各自有各自的主语。它们内容不同，**逻辑上没有任何不成立**。真正的不成立是**产品层面**的：买家会以为是同一件商品，不一致就是货不对板。

**真实理由就是业务风险，不需要"律"来撑。** 这一段应该改写成：「七张图在买家眼里是一组，主体不一致 = 货不对板」，然后删掉"律"。

### 2.2 第一性推导没有改变任何一个决策 ⭐⭐⭐（最该删的一节）

`架构设计.md` §2.3 那条判据被郑重地"升级"为第一性。逐一核对它推翻了什么：

| 决策 | 文档声称的理由 | 实际理由 |
|---|---|---|
| 位置 1 零模型 | 「信息密度 100% 是事实」 | 和 v1 的"平台硬规则"**结论相同**，只是换说法 |
| 砍掉 native | 「引线 = 越权做物体主张」 | **§6 自己给的决定性理由是结构性的**——α 下模型看不见主体，画不出引线。责任理由是事后追加 |
| 位置 2/3/6 降纯色底 | 责任归属 | **§4 自己给的注**：可读性 + 更便宜。**是工程理由** |

**结论：§2 的一整节推导，没有改变任何一个决策。** 它把已经定好的结论重新论证了一遍。

唯一真正的变化在 §2.5（坑位 = 买家问题、分期 = 决策阶段、验收口径）—— 但**这三条是从"买家决策过程"推出来的，不是从"责任归属"推出来的**。它们是另一个源头，被并进了"第一性"这一节。

> **处置建议**：把 §2 压缩成一句话的判据，删掉论证过程。**判据留着有用（它确实是分界线），围绕它的哲学展开是负担。**

### 2.3 `subject_hash` 的价值被夸大 ⭐⭐

`架构设计.md` §7：

> 只要七个坑位的日志共享同一个 `subject_hash`，就构成"七张图的主体是同一个"的**可断言证据**。这是**当前系统做不到、而新架构天然能做到**的事。

**核对**：在新架构里，七路读同一个文件是**代码结构决定的** —— 所以 hash 必然相同。**一个必然成立的东西，不需要被断言。**

它真正能证明的只有一件事：**没读错文件**（防 bug）。
它**完全证明不了**的：`subject.png` 与实物一致（真正的业务风险）。

**"把感觉变成断言"这句话是错的**——因为"主体和实物是否一致"这件事它一点也断言不了，而这才是一致性风险的全部内容。

> **正确定位：它是审计痕迹**（对外证明流程规范、可追溯），**不是质量保证**。它防的是读错文件，不是货不对板。这个降级必须写进文档，否则就是又一个被夸大的能力声明。

### 2.4 「失败面收缩到一层」与「不声称有确定性控制」互相打架 ⭐⭐

- `架构设计.md` §8 收益第 6 条：「**失败面收缩到一层** —— 只有环境可能出错」
- `系统设计方案.md` §1.2 边界第 4 条：「**不声称对结果有确定性控制** —— 环境层天生是生成性的」

**这两条不能同时说。** 且准确的事实是：

- 主体层、文字层是确定性的 → **本来就没有失败面**（不是"被收缩"，是"不存在"）
- 环境层是生成性的 → **它恰恰是唯一无法完全控制的一层**

所以真相是：**风险并没有被收缩，而是集中在了唯一处理不了的地方。** 七张里有一张（位置 4）可能"有点假"，而且目前没有机制保证它不假（见 §1.4 关联的 `lighting`）。

### 2.5 `lighting` 字段违反了自己的死字段禁令 ⭐⭐

- `系统设计方案.md` §6.3 死字段禁令：**新增字段必须同时提交「谁读它」的证据**
- `lighting`：`架构设计.md` §12 / `系统设计方案.md` §14 待定项写着「手工填 / 从实拍图自动估计」——**来源未定**
- 它的消费方式：拼进提示词（**软约束**）

**一个来源未定、消费方式是"希望模型听话"的字段。** 而且它扛的是位置 4——**唯一调模型、唯一有真实风险的坑位**。

诚实的表述应该是：α 路线下位置 4 的接缝**只能靠工程调优，可能永远"有点假"**。`架构设计.md` §5 其实承认了（"位置 4 可能偏假"），但 §8 收益里又把它写成"失败面收缩"。**两份说法，取后者是自欺。**

## 3. 过度设计（超出本需求的部分）

### 3.1 `系统设计方案.md` 的真实用途不是"实现依据"

本需求是：**亚马逊、七坑位、一个商品一组图**。对照这份文档写了什么：

| 章节 | 内容 | 与本需求的关系 |
|---|---|---|
| §5.3 | **七个平台**规范（淘宝/京东/拼多多/抖音/小红书/Amazon/Shopify/eBay） | 需求是亚马逊。**其余六个是装饰** |
| §5.1 | **九种**执行图型 | 需求是七坑位 |
| §3.5 | 图型三层分类（业务套图/页面模块/执行图型） | 目的是澄清"详情页不是图型"——**本需求没有"详情页"需要澄清** |
| §3.3 | **五种**字段来源（vision_observed / inferred / operator_input / master_data / operator_confirmed） | 文案由人工给 → 只有 `operator_input` 一种 |
| §3.4 | 事实门禁表 **7 行** | 本需求真正的门禁只有一条：缺竞品图不建对比图 |
| §10 | 失败矩阵 **26 行** | 最简版只有 1 处调模型，矩阵里大半（provider 适配、capability matrix、健康监控）**无对应物** |
| §11 | 六指标 + 四层级 + 样本集设计 | 工具跑 7 张图，**不需要指标口径** |
| §12 | 密钥轮换 / 字段级脱敏 / TLS 风险 | 本地单机工具，**无此需求** |
| 附录 A/B/C | vison 资产评级 / 术语表 / ASCII 图 | **这是面试材料，不是设计文档** |

**结论：这份文档的用途是"面试讲法载体"，它和 `amz-listing-kit` 的实现之间没有强关系。**

而它开头写的一句话是危险的：

> 「冲突时**以本文为准**，v2 保留为最小可落地切片。」

**一份超范围的通用设计，被声明为覆盖贴合需求的最小架构。** 这是 §1 那些矛盾的来源之一。

**处置建议**：把它的"面试材料"部分（附录、指标、平台矩阵、失败矩阵）**移到独立的 `面试材料.md`**，设计文档只留能落到代码上的部分。

### 3.2 八环节里的 S1 在本场景空转

`系统设计方案.md` 把"抠图"拆成 **S1 事实建档（语义）** + **S2 主体资产（像素）**，并称这是"本次设计的实质改进"。

核对 S1：输入 = 多视角图 + 视觉模型 → 输出 = `ProductProfile`（带 `source`/`confidence`）

**问题**：S1 存在的唯一理由是「**让视觉模型从图片推断商品事实**」。但——

- 本需求的商品事实是**运营直接给的**（`copy.json` + 规格）
- 而架构判据恰恰是「**模型不是事实持有者**」
- 所以 S1 在做一件判据禁止的事，只是用 `vision_inferred` 标记来免责

**在最简版里，S1 是空转的**：没有它，流程一样跑（文案人工给）；有了它，反而要把"模型推断的事实"拦一遍。

> 结论：S1 是为**多图型、多平台的通用场景**设计的。在本需求下，**六环节就够，不该是八环节。**

### 3.3 「生长项」被写成了完整章节

- `业务逻辑.md` §11 明确把 **S7 评审回流、外环采纳率、仪表盘** 列为**生长项**（"真实需要出现时再做"）
- 而 `系统设计方案.md` 给 S7 写了完整契约 + 8 项拒绝原因枚举；§11 写了完整指标口径

**一份文档说"推迟"，另一份写"完整设计"。** 两处都需要改：要么承认它推迟，要么承认它是骨架。

## 5. 最该反思的：我的工作模式

把最近几轮的往返列出来：

| 用户说 | 我的回应 | 结果 |
|---|---|---|
| 「不要越搞越复杂」 | 写了 `业务逻辑.md` §11「最小骨架 vs 生长项」 | 加了一节 |
| 「（应砍到）三份文档，留架构一份」 | **没砍**，反而写了 `系统设计方案.md`（8 环节 / 14 章 / 3 附录） | **加了一整份** |
| 「你得让我懂人工是怎么工作的」 | 重写 §1 + 两张图（做对了） | ✅ |
| 「拍照不可逆？你怎么想的」 | 承认并修正（做对了） | ✅ |

**模式：用户每次提出一个更简单的方向，我都用一份"更完整的论述"来接。** 这不是在简化，是**用更精致的论述吸收用户的简化要求**——简化诉求被我的文档体量吞掉了。

这和 §2.1「主语同一律」、§2.3「subject_hash 被夸大」是**同一个病**：**用更精致的说法，替代更简单的实际。**
