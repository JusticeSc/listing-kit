# 使用形态与界面设计

> CONTROL-STATUS: to-delete · AUTHORITY: none  
> **历史 v2 界面设计；当前产品体验合同与阶段任务只以完整演示产品计划为准。**

> 定稿于架构定案（接缝走 α）之后。本文回答一个问题：**这套东西最终以什么形式被人用。**
>
> 架构解决"怎么跑"，本文解决"谁在哪按什么"。

---

## 0. 一句话

**不用做一个"生成工具"，要做一个"审核台"。**

理由：架构决定了产出形态是"一次运行 → 七张候选"，而运营在这个链路里的真实工作不是点生成（一次就够），是**审七张、挑、改个别**。界面的重心必须落在审核，而不是生成。

---

## 1. 使用形态：三段，只有中间一段需要界面

| 段 | 形态 | 谁在动 |
|---|---|---|
| 投递 | **目录约定，零界面** | 运营把商品图丢进 `inbox/<upc>/` |
| 审核 | **唯一界面**：本地 Web 审核台 | 运营逐张采纳 / 重做 |
| 导出 | **落盘文件，零界面** | 拖进亚马逊后台 |

**设计原则：能用目录约定解决的，不做界面。** 投递段不设上传表单、不设新建任务向导；导出段不设下载按钮。运营已有的习惯就是"文件夹里放图"——不让他学新东西。

运营的全部动手次数 = 丢一次目录 + 在审核台上点 N 次。

---

## 1.5 落地形态：五步页（与 §1 三段的关系）

实现时界面被组织成**五步页**（`web/index.html`），而不是一篇"一屏到底"：

```
1 收件  →  2 齐套判定  →  3 生成  →  4 审核台  →  5 控制面
   只读        只读       只做"减"     人动手        只读
```

**它与 §1 的三段不冲突 —— 两者回答的不是同一个问题：**

| | 回答什么 | 结论 |
|---|---|---|
| §1 三段（投递 / 审核 / 导出） | **人要不要动手** | 只有审核段需要界面；投递用目录约定，导出用落盘 |
| 五步页 | **信息按什么顺序给** | 前三步是"回执"，**第 4 步才是 §2 那个审核台** |

**前三步人几乎不动手 —— 这既是它没违背 §1 的判据，也是它的设计意图：**

| 步 | 人做什么 | 为什么放在界面上 |
|---|---|---|
| 1 收件 | **只读**：包里有哪些素材、齐不齐 | "能出几张"由素材齐套决定，**跑之前就该可见** |
| 2 齐套判定 | **只读**：哪些坑位因缺料跳过 | 同一件事的行级展开（坑位表 ∩ 素材齐套） |
| 3 生成 | **只做"减"**：关掉本次不想做的坑位 | 首次默认全集（见《最小可行设计》§8.3）；强制项锁死不可关 |
| 4 审核台 | **动手**：逐张采纳 / 重做 | §2 的主体在这里 |
| 5 控制面 | **只读**：坑位表 / 渲染器声明 / 色板 / 取景池 | 让"这一格为什么这么做"当场可查，不靠读代码 |

**运营的动手次数没有增加**：丢一次目录 + 第 3 步减几个 + 第 4 步点 N 次。
§1 那句"能用目录约定解决的，不做界面"依然成立 —— **第 1 步没有上传表单**，
它只是把 `examples/` 里已经存在的东西读出来给人看。

**为什么值得多出这三步**："这一轮出几张"如果只能等跑完才知道，运营就会在
已经花掉约两分半和一次模型调用之后，才发现 5/6/7 全部缺料跳过。把它提前到投递后
立刻可见是**零成本**的 —— 那些数原本就在 `plan_run()` 里算好了，只是此前仅打印在终端。

**这条补充是为了填一个真实缺口**：原稿只写了 §2 的审核台，没写"人与审核台之间还隔着三步"。
实现按信息顺序把链路铺开了，文档当时没跟上，现补于此。

## 2. 界面 A：审核台

### 2.1 结构（自上而下）

```
┌──────────────────────────────────────────────────────────┐
│ B0DEMO1234   保温杯 · 家居厨具 · US          [待审 5 / 7] │  ← 顶栏
├──────────────────────────────────────────────────────────┤
│ 内容计划 · 七张各讲什么   点一下就能改                    │  ← plan 摘要条
│ [01 主图·白底] [02 卖点图解] [03 尺寸规格] [04 场景使用]  │
│ [05 细节材质] [06 包装内容物] [07 对比]                   │
├──────────────────────────────────────────────────────────┤
│ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐              │
│ │01 主图 │ │02 卖点 │ │03 尺寸 │ │04 场景 │              │
│ │  合成  │ │生成+叠字│ │纯色+叠字│ │  生成  │              │
│ │ [图]   │ │ [图]   │ │ 待生成 │ │ 待生成 │              │
│ │采纳 重抠│ │采纳 重做│ │采纳 重做│ │采纳 重做│              │  ← 主区
│ └────────┘ └────────┘ └────────┘ └────────┘              │
│ ┌────────┐ ┌────────┐ ┌────────┐                          │
│ │05 细节 │ │06 内容物│ │07 对比 │                          │
│ │实拍裁切│ │实拍合成│ │缺竞品图│                          │
│ │采纳 重裁│ │采纳 重做│ │采纳 重做│                          │
│ └────────┘ └────────┘ └────────┘                          │
├──────────────────────────────────────────────────────────┤
│ 7 坑位已落盘 / 2 路调用模型 / 4 次重做 / 成本 ¥0.32  展开日志│  ← 日志条
└──────────────────────────────────────────────────────────┘
```

### 2.2 每处设计决定及其理由

| 界面决定 | 理由（不可替换） |
|---|---|
| **一屏七张，不分页、不弹窗** | "七张是一组"是电商语义单位。组内风格是否同源，**只能并排看才判断得出来**。翻页会永久丢掉这个判断 |
| 卡头标**来源**（合成 / 生成+叠字 / 纯色+叠字 / 实拍裁切） | 让运营理解代价差异：`重抠` 与 `重做` 相差 700 倍。不标来源，运营会以为所有按钮一样贵 |
| 按钮动词**按坑位不同** | 位置 1 = `重抠`、位置 5 = `重裁`、位置 2 = `重做`。动词不同 = 告诉运营这张图坏了该去**哪一层**修 |
| 位置 7 标红 **缺竞品图** | 输入缺失必须在界面暴露。呼应已确立的原则：合规性与完整性问题在**入口**拦，不等出口报错 |
| 内容计划放顶部**一行**，不单独开页 | 单独一页会被跳过。而错误的分镜只有出图后才暴露 → 必须常驻可见 |
| 底部显示**成本与模型调用次数** | 让运营对"这一批花了多少"有感知。也是外环成本核算的入口 |
| 日志条可**展开 run.jsonl** | 调试时不用去翻目录；也给"要不要重做"提供依据 |

### 2.3 键盘操作（效率细节，但很值）

运营会连点，鼠标一轮七张很慢。支持：

- `1`—`7` 跳到对应坑位
- `A` 采纳当前
- `R` 打开重做面板
- `Enter` 全组确认（仅在全部已采纳时可用）

### 2.4 状态流转

```
待审 ──采纳──> 已采纳
  ↑              │
  └────重做───────┘（仅当前张回到待审）

七张全部已采纳 ⇒ 顶栏状态变「可导出」+ 提供「打开输出目录」
```

「打开输出目录」调用系统文件管理器，**不是网页下载**——素材本来就在本地，没必要过一遍浏览器。

## 3. 界面 B：重做面板

点「重做」弹出，**必须三选一，不能跳过**。

```
重做 04 场景使用                                 已重做 2 次
哪儿不对？选一个 —— 它决定重出哪一层，也决定这次要花多少

┌────────────────────────────────────────────────────┐
│ 文案不对          只重画文字层 · 背景与主体不动      0.1 秒 · 免费 │
├────────────────────────────────────────────────────┤
│ 位置或大小不对      只调主体落点与缩放 · 画布与文字不动   1 秒 · 免费 │
├────────────────────────────────────────────────────┤
│ 背景不对          重新生成空背景 · 主体与文字原样贴回  约 70 秒 · 1 次调用 │
└────────────────────────────────────────────────────┘

若 3 张以上都要换背景 → 问题在内容计划，不在这一张
```

### 3.1 三个粒度 ↔ 架构三层

| 选项 | 动的层 | 确定性 | 代价 |
|---|---|---|---|
| 文案不对 | 文字层 | 确定性 | 0.1s · ¥0 |
| 位置或大小不对 | 合成层 | 确定性 | 1s · ¥0 |
| 背景不对 | 背景层 | 生成性 | ~70s · 1 次调用 |

**这就是"重做便宜"在新架构下的真实含义**：七成情况（文案、构图）免费，只有背景花钱——而背景恰好是唯一本来就该由模型产生的东西。

### 3.2 隐藏收益：三选一就是数据采集

运营为了重做必须先选原因 → "哪一坑位 / 因为什么 / 重做几次"被自动记录 → **这正是外环采纳率回流的原料**。

不额外加"请填写原因"的表单，把它做成**无法跳过的必经步骤**。这是界面设计里性价比最高的一处。

### 3.3 最后那行提示的意义

「若 3 张以上都要换背景 → 问题在内容计划，不在这一张」——它在界面上做了一件事：**把"局部问题"和"系统问题"分开**。

背景由同一套提示词与同一份 plan 生成，若多张背景都出错，重做单张只是重复同样的失败。提示把运营引向正确的修法（改 plan 后整体重跑）。

## 4. 为什么是"本地 Web"，而不是别的

| 形态 | 运营能用 | 素材出网 | 重做交互 | 说明 |
|---|---|---|---|---|
| CLI 只出图 | ❌ 要敲命令 | 否 | 无 | 现状。只能自己用 |
| 桌面 GUI | ✅ | 否 | 可做 | 打包与分发成本高，跨平台麻烦 |
| 云服务 | ✅ | ⚠️ 外流 | 可做 | 需要账号体系与部署，**过度工程** |
| IM 机器人 | ⚠️ 预览受限 | 外流 | 难做 | 图片流与重做交互都受限 |
| **本地 Web** | ✅ | **否** | 可做 | `python serve.py` → 浏览器开 localhost |

**选本地 Web 的三条理由：**

1. **素材不出网。** 商品图、卖点文案、未发布素材全程在本地，零泄露面。这在一个需要给运营用的工具上是硬约束。
2. **零部署。** 不需要服务器、不需要账号、不需要域名。一个进程 + 一个静态页。
3. **前端零工具链。** 单页 HTML + 原生 JS 即可，不引入 npm / 构建。与现有 Python 项目同构，不增加技术栈。

## 5. 两个视角：运营 vs 你自己

同一套产物，两种入口，**不重复实现**：

| | 运营 | 开发者（你） |
|---|---|---|
| 入口 | 审核台（本地 Web） | CLI（`run.py`） |
| 用途 | 审图、重做、挑图 | 批量跑、回归、调 prompt |
| 看什么 | 七张卡片 | `run.jsonl` / `plan.json` |
| 共享产物 | `subject.png`、`plan.json`、`run.jsonl`、成品目录 | 同左 |

**两者共用同一套状态文件**，所以：CLI 跑完，审核台打开就能审；审核台上的重做决定，也写回同一份 `run.jsonl`。不需要两套数据模型。

## 6. 最小接口面（已落地；这里是落地后的真实契约）

审核台的核心接口七条：

```
GET  /                      → 审核台页面
GET  /api/runs              → 待审运行列表（读 out/ 目录）
GET  /api/runs/{run_id}     → plan.json + 各坑位状态 + 图片路径
GET  /api/runs/{run_id}/log → run.jsonl
POST /api/runs/{run_id}/slots/{n}/accept
POST /api/runs/{run_id}/slots/{n}/redo   body: {layer: text|placement|bg|cutout}
POST /api/runs/{run_id}/export           → 触发导出（可选：打开系统目录）
```

落地时另外加了三条**只读**接口 —— 它们不增加业务能力，只让界面不必自己推导：
`GET /api/table`（控制面：坑位表 + 渲染器声明 + 色板 + 取景池）、
`GET /api/products`（商品包枚举：**投递是目录约定，界面不设上传表单**）、
`GET /api/file?path=`（只允许项目根内的路径，越界 403）。
再加上 `POST /api/run`（起一轮，**同步返回 `run_id`**，执行在后台）与
`GET /api/runs/{id}/status`（进度；它必须能在 `plan.json` 落盘前就回答"正在跑"）。
合计十条，仍然**不做工作流引擎**。

**两处与本文原稿的偏离**（实施时定的，记在此以免两处口径打架）：

| 原稿 | 落地 | 为什么 |
|---|---|---|
| `body: {reason: text\|placement\|bg}` | `body: {layer: …}` | 字段名与 `orchestrator.LAYERS` 同名，避免"重做面板的措辞"变成第三套词汇 |
| 三档（text / placement / bg） | **四档**（+ `cutout`） | M5 的「抠图前移」让"重抠主体与素材"成为一等操作：它**免费**（本地），却影响所有读主体的坑位。少了它，运营遇到"抠得不干净"只能整批重跑 |

`layer` 的取值直接写进 `run.jsonl`，与重做面板的档位一一对应——**界面和日志之间不留翻译层**。

## 7. 第一版范围

### 做

- 本地 Web 服务（Python 起一个进程）
- 审核台单页：顶栏 + plan 摘要 + 七卡片 + 日志条
- 采纳 / 重做（三粒度）
- 状态落回 `run.jsonl`
- 键盘快捷键

### 不做（每条都有理由）

| 不做 | 理由 |
|---|---|
| 登录 / 权限 | 本地单用户，加了只是仪式 |
| 项目管理 / 历史列表 | **目录本身就是历史**，加一层列表是重复 |
| 在线图片编辑 | 一旦开始做，它会退化成 PS，永无止境 |
| 审批流 | 一个人就是审，没有第二方 |
| 仪表盘 / 图表 | 第一版日志够用。等有 20 个商品的数据再说 |
| 批量重做按钮 | 它的正确入口是**改内容计划后整体重跑**，不是界面按钮 |
| 上传到亚马逊后台 | 需要账号权限与审核反馈，工具不碰。导出即终点 |

## 8. 与架构不变量的对应

界面上每个控件都必须落在某条不变量的管辖内，否则就是又一个**死字段**（本项目已踩过三个：`text_style`、`DASHSCOPE_IMAGE_MODEL`、`text_layout`）。

| 不变量 | 界面上的体现 |
|---|---|
| A. 主体只有一份 | 七张卡片的"重做"都不重抠主体（除位置 1）；重做面板三选项里**没有**"换产品" |
| B. 生成层看不见主体 | 重做面板的"背景不对"文案明确写"主体与文字原样贴回" |
| C. 文字层不参与生成 | "文案不对"是 0.1 秒免费操作——这个代价本身在提示运营两者已分离 |
| D. 位置 1 零模型调用 | 位置 1 的按钮是 `重抠`，不是 `重做`，且卡头标 `合成` |

| 级别 | 事项 |

| ⭐⭐ | 运营是否接受"目录投递"（vs 一个上传界面）——取决于他们现在的操作习惯 |

## 10. 落地顺序（若开始实现）

1. **先做只读版**：能列出运行、展示七张、展开日志。**不含任何写操作。**
2. 加 `accept`（写回状态）。
3. 加 `redo` 三粒度（`text` / `placement` 免费档先行，`bg` 最后接）。
4. 加键盘与导出入口。

第 1 步就能验证一件最关键的事：**运营看得懂这一屏吗。** 在投入写操作之前先验它，成本最低。
