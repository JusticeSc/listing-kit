## 3. 提示词引擎（新的核心能力，不是附属工具）

用户点出的归结点：**调模型的输入只有参考图 + 提示词**。所以引擎是这套设计的心脏。

### 3.1 组装顺序（照库 A/C 的"逐字复用 + 本格变"结构）

```
① 保真段      ← 库 B PRODUCT_REF_LOCK / 库 A fission-pattern 段1      【逐字、整批复用】
               ★ **必须有"显式否定句"，不能是一句嘱咐** —— 实测见 §3.3；
                 ~~"逐特征枚举"~~ 是当时的过度归因（A→B 混了三个变量），见 §3.8
               ★★ **每条断言的出处按"量/定性/定量"三分** —— 实测见 §3.4 + §3.6 ④：
                  · 量（尺寸/比例/容量/材质名）→ **商品资料**（可复算）
                  · 外观定性（有无某部件、大体形状）→ 参考图 / VLM（重复读稳定）
                  · 外观定量（占比/长宽比/颜色范围）→ **谁也不给 ⇒ 写成"不得改变"**
                  **判据不是"读得准"，是"图像里有依据"** —— 从文案外推的属性会被模型执行
               ★★★ ~~它是被"编译"出来的~~ **→ 见 §3.8 改判：默认是"类目固定文本 + 否定句渲染"，
                  属确定性组装；离线 LLM 编译降为失败时才走的加强链**（§3.5 记其能力上限）。
                  ⇒ "LLM 润色"与"可复算"不冲突 —— 冲突的只是"在线让模型现场写"。
② 风格锁      ← 库 C Campaign Style Lock 10 字段                     【逐字、整批复用】
③ 本格专属    ← 镜位 / 构图 / 文字 / 卖点 / 受众 / 场景               【每格变】
④ 约束条款    ← 库 A brand.yaml 的 forbid 段（负面清单写具体项）      【逐字】
⑤ 平台段      ← 库 B image-types.md 的 6 平台各自 prompt（字体/色号/字号写死）【按平台切】
⑥ 模板/变体   ← 库 C 25 模板 × variants.overrides × category_tips × anti_ai_tips【按配方切】
```

**判据**：①②④ 是"锁"（整批逐字相同），③ 是"变"（每格不同）。**这个划分本身就是"同源"的实现方式**
——库 A `fission-pattern` §3 把它写成配方，库 C 把它写成 Style Lock 的"不得改写"。

### 3.2 铁律清单（照库 C「Prompt 铁律」逐条对）

- hex 色不用形容词（写 `#F5F0E8`，不写"米白色"）
- 产品占比写百分比（不写"大一点"）
- 显式声明留白，不靠模型猜
- 否定清单写具体项（"no brand logo, no text on product"），不写"不要乱七八糟的东西"
- 平台预留区写精确坐标
- **中文文字要显式给出，并进入人工 200% 核对清单**（库 C 明写笔画风险）
- **判不了的项标 `manual`，不写假检测器**（出处 `A/shared/scripts/check_listing.py:251-253`：
  「需模型判定的项 —— 不假装能测：文字 / 水印 / 拼图 → 像素层判不了，交给 detect-task 或人工过一眼」）
  —— 与本项目"假保护"教训（`no_watermark` / `text_render_ok`）同源，是三库最硬的一条分工原则

### 3.3 「锁」的实测结论（2026-09-22 · **已从"未验证前提"升为"已验证"**）

探针 `evals/probes/lock_probe.py`。**它是实验代码，不进 `src/`** —— `image_inputs_in_signature()`
必须继续返回 `[]`（不变量「生成层看不见主体」的唯一证据，且被 `golden/slot04.json` 冻着）。
单变量对照：同一参考图 `examples/input/cup_source.jpg` · 同一场景段 · 同一负面词 ·
同模型 `qwen-image-2.0-pro` · `n=3` · `prompt_extend=false`。**只改锁段写法。**

| 臂 | 锁段写法 | 长度 | 三张里的商品 | 两两 dHash（/256，**上界**） |
|---|---|---|---|---|
| A `advice` | 笼统嘱咐"一律不得改动、不得美化" | 84 字 | **3 张里 2 张长出了源图没有的把手**，壶口与壶身比例也变了 | 133 · 106 · 69 |
| B `enumerated` | 逐特征枚举（钢身/下三分之一深色套/带棱盖/高径比≈3:1）+ **显式否定已知失败模式**（`NO handle, NO spout, NO straw, NO second cap…`） | 820 字 | **3 张彼此形态一致，且与源图一致**；无把手、无壶口 | 91 · 31 · 82 |

**结论（上面两行的差就是结论，不是我的信心）：**

1. **锁能锁住，但"嘱咐"锁不住。** 笼统一句给模型留了发挥空间，它会**自造结构**（把手是最容易冒出来的）；
   把特征逐条枚举、并把已知失败模式显式否掉，同一模型同一参数就守住了。
2. ⇒ §3.1 ①保真段的实现要求**不是"写一句话"，而是"从商品资料里抽特征清单再渲染成锁段"**。
   这正是库 B `build_prompt()` 738 行在做的事，也是"提示词增强"落到实处的形态。
3. ⇒ **84 字那版与 820 字那版都能通过当时的任何性质断言**，差别只在图上。
   **没有这个对照，我会把 84 字那版写进设计并宣称"同源成立"** —— 这是本实验真正的价值。
4. 机器数字只当**上界**：dHash 把场景差异也算进去了（B 的 31 = 自己几乎不变）。
   "模型有没有改商品"是主观项，照 E0 规矩由人看对照图签字（`report.json.attest_required`）。

> **⚠ 对本表的一处自我更正（2026-09-22 深夜，见 §3.8）**：A → B 只换了锁段，但**那一次改动里
> 混了三个变量**（嘱咐→枚举 · 通用→本品具体 · 无否定→显式否定）⇒ **上表是"改了多个东西"的对照，
> 不是单变量对照**。结论 1 的措辞应以 §3.8 为准：被证明必要的是**显式否定句**（类目级），
> **本品具体特征未被证明必要**；结论 2 里"从商品资料抽特征清单"因此**不是默认路径**，
> 而是**漂移发生时才注入的加强项**。

**仍未验证**：`prompt_extend` 开着时模型会**改写提示词**（`src/imagegen.py` 模块注释已记），
锁段可能被它一起改写 —— 本实验刻意关掉了它。**→ 已补测，见 §3.5：开/关各 3 张看不出差别，
但"未观测到差异"不等于"差异为零"（API 不回传改写后的提示词）。**

### 3.4 「锁段由谁写」的实测结论（2026-09-22 · 四臂）

§3.3 的臂 B 是**人看过图手写的** —— 有效，但**不可扩展**：换一件商品就要人重看一遍图手写一遍。
所以追问：这段能不能由模型写出来？

探针 `evals/probes/prompt_enhance_probe.py` · 元提示词 `prompt_enhance/meta_lock_prompt.md`（v0.1）
· 失败模式表 `prompt_enhance/failure_modes.json`（v0.2）。两臂**单变量 = 给 LLM 的输入**：

- `text` —— 只给文本资料（title / bullets / specs）
- `vision` —— 文本资料 **+ VLM 对参考图的属性描述**（`qwen-vl-max`，13.0s，1456 字）

四臂共用**同一参考图 · 同一场景段 · 同一负面词 · 同模型 · 同 `n=3` · 同 `prompt_extend=false`**，
**只有锁段来源不同**。

| 臂 | 锁段来源 | 长度 | 机械判据 | 图上的结果 |
|---|---|---|---|---|
| A | 人写·嘱咐 | 84 | 红（太短 / 无枚举 / 覆盖 0 条失败模式） | 3 张里 2 张长出把手 |
| B | 人写·枚举 | 820 | 绿 | 3 张一致，无把手 |
| C1 | **模型写·只给文本** | 1184 | **绿** | **3 张全部丢了棕色矮套**。锁段原文写的是 `anti-slip matte spray coating applied to the entire outer surface`（来自卖点"杯身防滑喷涂"）⇒ 整杯被喷成一体灰；盖也被写成 `push-button`（来自卖点"一键弹盖单手开"），源图是旋盖 |
| C2 | **模型写·文本 + VLM 读图** | 1446 | 绿 | **3 张都保住两段式结构**（拉丝钢上段 + 深棕下段），无把手 / 无壶口 / 无按钮；与臂 B 同档 |

**四条结论：**

1. **元提示词 v0.1 成立。** C2 一次通过判据，图上与"人看过图手写的 B"同档 ⇒
   锁段不必人手写，**"提示词增强"有了具体载体**（元提示词 + 失败模式表两张离线资产）。
   代价：多一次 VLM 读图（约 13s）。~~这条直接改掉 §3.1 ① 的实现路径 ——
   保真段不是人写文案，是"读图 → 写锁段 → 校验 → 冻结复用"。~~
   **→ §3.8 再改判**：读图与"本品具体特征"**都不是默认路径的必需项**（臂 E 零读图即守住）。
   这条路径降级为**失败发生时才走的加强链**；默认路径是类目固定文本 + 失败模式表渲染否定句。
2. **★ 正向断言会被执行，即使它是错的。** C1 把两条**营销语**当成了外观事实并写进锁段，
   模型照着执行 ⇒ 棕色矮套消失、盖变成按钮盖。
   ⇒ **锁段的每一条正向特征都是一条指令；没看过的图不许写进锁段。**
   顺带否掉一个我原本以为的保险：**`unknowns` 拦不住这件事** —— C1 自己列了 7 条 unknowns，
   其中就有"coating 的颜色与范围"，但它仍把不确定的写成了断言。**`unknowns` 是诊断，不是闸门。**
3. **否定句的作用是"强化图像"，不是"覆盖图像"。** 臂 B 的否定句与图像一致（图里确实没把手）⇒
   3 张全守住；C2 的锁段写了 `no cap present`（与图像冲突）⇒ **没被执行**（图里盖还在）。
   ⇒ 否定句只能写在图像支持的方向；拿它否认图里明明有的东西，无效且白占篇幅。
4. **判据自己踩了两次假红，都已修**（这条比结论本身更贵）：
   - v0.1 检查字面标题 `HARD CONSTRAINTS`，而 C1 的锁段**语义完全达标**（6 条失败模式逐条否掉），
     只是没写那个标题 ⇒ 差一点把"模型没做到"写进结论。**标题是形状，否认是性质；测形状会把合格品判死。**
   - 改成按失败模式覆盖判之后，**又把正向对照判红**：`FM-03 比例`用"否定语境"判，
     而臂 B 写的是正向断言 `height-to-diameter ratio about 3:1` ⇒ 合格品被判死。
     ⇒ 失败模式分两类，判据必须跟着分（`failure_modes.json.check`）：
     **「凭空加出」类查否定语境，「改掉已有的」类查正向定量断言。**
   - 两次都靠 `--revalidate`（**零调用**重算旧产物 + 正反两组对照）抓出来。
     **判据改了不重算，就分不清红的是产出还是判据。**

对照图 `evals/probes/lock_out/compare_4arms.jpg`（SOURCE 固定左列 + 四臂各 3 张，留签字栏）。

### 3.5 通用编译器臂（D）与 `prompt_extend`（2026-09-22 23:2x）

两件互不相干的事，一个是"能力"，一个是"生产默认值"，但都只有一条结论。

#### D · 通用 Prompt Compiler + 本域 context（`meta_compiler_v1.md`）

**协议**：输入 = **臂 A 那版已知失败的 84 字粗提示词**（从 `lock_probe.ARMS["advice"]` 直接取，
单一出处，不会与实验失同步）。编译器的 L1 是**逐字未改的通用编译器**；L2 是本域 context
（事实三级分级 / 覆盖 L1 第 3、9 条 / 输出附加 `## 溯源`）。产出走 `--prompt-file` 整段替换。

| 量 | 值 |
|---|---|
| VLM 读图 | `qwen-vl-max` · 12.5s · 1669 字 |
| 编译 | `qwen-plus-latest` · 21.5s · 产出 1475 字（臂 B 人手写 820 字） |
| 生图 | `qwen-image-2.0-pro` · 23.8s · 3 张 |
| 机械判据 | **绿**（含新增的"最终提示词必须纯英文"一条） |
| `unknowns` | **5 条，全部合理**：品类（杯/壶/瓶未明示）/ 杯口内唇微结构 / 盖子开合方式 / 底部附件 / 图案工艺 |

**★ 这条臂最值钱的观察**：它把 `unknowns` 里的不确定项**转成了否定句**，而不是编成正向断言 ——

### 3.6 度量与产出的校准（2026-09-22 深夜 · 全部离线或低成本）

"能验的都提前验"落地成七项。**其中三项推翻了我自己此前引用过的证据。**

#### ① dHash **不是**「商品有没有被改」的度量（撤回引用）

我此前用 `pairwise_hamming`（臂 A `133·106·69` vs 臂 B `91·31·82`）当"臂 A 更乱"的佐证。
校准后（`evals/probes/dhash_calib.py`，零调用）**该论证无效**：

| 实验 | 结果 |
|---|---|
| A · 4×4 分块逐块填灰 | 敏感度 7–18/256，**无热点** ⇒ 反映全局纹理，不指向任一物体 |
| B · 仅把背景换成浅色 | **76/256** —— 已落在真实生成图 `vs_source` 区间的下缘 |
| B · 主体区域填灰 | 60/256（主体面积 31%；每面积 196 vs 背景 110） |
| C · 18 张真实产物 | 人眼已知**被改**的臂 (89,127) 与**守住**的臂 (79,120) **区间重叠** |
| C · 单变量铁证 | `enumerated`（守住）与 `c_text`（被改）**锁段完全不同**，dHash 却是 `[89,120,98]` vs `[89,121,98]`（差 ≤1）—— 因为两臂**共用同一个场景段** |

⇒ 这两个数由**背景与构图**主导，不得作为商品保真的证据。
⇒ 而且**没有便宜的替代**：客观测商品保真必须先把主体从背景分离（抠图），
而"对每张生成图抠一次" = 每张约 6 GB / 55 s（见环境硬约束）⇒ **代价不可接受**。
⇒ 所以"商品有没有被改"只能人判 —— **这不是偷懒，是核算过替代方案之后的结论**，
   同时也给 E0 的签字制补上了成本依据。

> **方法论**：这是"未校准的量被当证据"，与 v1 的假校验（`no_watermark`）同类；
> 区别是它**不报错、只给数字**，所以更难发现。

#### ② 离线编译**不可复现** ⇒ 冻结不是优化，是 J1 的**必要条件**

同一元提示词、同一输入、连跑 3 次（`prompt_enhance_probe --arm text`）：

| 次 | 锁段长度 | 与另两次的 token Jaccard |
|---|---|---|
| rep1 | 1209 字 | 0.625 / 0.654 |
| rep2 | 971 字 | —— |
| rep3 | 1113 字 | —— |

**约 1/3 的词不同，`unknowns` 条数与内容也不同（9 / 9 / 8）。**
⇒ 若不冻结，每次运行"系统写给模型的话"都在变 ⇒ **J1 直接不成立**。
⇒ ADR §3 的"LLM 离线编译 + 产出冻结"**从设计推断升为实测支撑**：冻结是 J1 的前提。
⇒ 附带推论：冻结**之前**必须有人确认 —— **人审的一个粒度是"锁段"，不是只有"成品图"**。

#### ③ VLM 读数：**定性可靠、定量不可靠**（且系统性偏低）

同一张参考图、同一提问连读 3 次（`vlm_stability_probe.py`；**跨模型对照不可行 —— 3 个候选里 2 个 403**，
这条由脚本自己产出证据，不靠我口述）：

| 字段 | 3 次结果 | |
|---|---|---|
| `has_handle` / `has_spout` / `has_second_cap` / `has_printed_text_or_logo` | `false` ×3 | **稳定** |
| `product_type` | `thermos` / `thermos flask` | 不稳（无害） |
| **`height_to_width_ratio`** | **2.15:1 / 2.50:1** | **不稳，且真值 3.14:1**（资料 22cm / 7cm） |
| **分节结构** | 3 段 / 2 段 / 2 段（矮套起点 0.75 / 0.73） | **不稳** |

⇒ 推论：`unknowns` 与布尔特征可交 VLM；**比例 / 占比 / 尺寸类断言一律不许来自 VLM**。

#### ④ 修正 §3.4 的一条：**人写也会读错**

臂 B（**我手写**的 820 字）写的是 `screw-on lid assembly in **dark charcoal**`，
而源图顶部是**银色杯口 + 黑色螺纹环** —— 手写锁段同样有读图偏差。

⇒ 所以"外观断言只能来自参考图描述"**说得太粗**。正确的分层是：

| 断言类型 | 唯一合法出处 | 为什么 |
|---|---|---|
| **量**：尺寸 / 比例 / 容量 / 材质名 | **商品资料** | 可复算，资料里写着 |
| **外观定性**：有无某部件、大体形状 | 参考图 / VLM | 实测重复读稳定（③） |
| **外观定量**：占比 / 长宽比 / 颜色范围 | **谁也不给 ⇒ 写成"不得改变"的约束** | 人读、模型读都会偏（① ③ ④） |

**关键区分**：臂 B 的 `dark charcoal` 偏了但**无害**（图像权重高于文字）；
C1 的 `coating applied to the entire outer surface` 有害 —— 差别不在"准不准"，
而在**有没有图像依据**：前者图里确有深色部件，后者是从卖点外推出来的属性。
⇒ 判据是：**断言必须在图像里有依据，而不是"必须读得准"。**

### 3.7 「离线编译 + 冻结」到底冻什么、运行时到底组装什么

> 起因：用户问「是不是**提前准备好提示词模板、使用时选模板填变量**就行」。
> **一半对。** 对的是：在线路径确实就是「取文本 + 填变量 + 拼接」，零模型调用。
> 漏掉的是：六段里有三段（①②④，即"锁"）**不是模板**，它们是被**编译**出来的完整文本。

**先看库 B 长什么样**（这就是用户描述的那个形状）：

| 位置 | 事实 |
|---|---|
| `generate.py:376-380` | `build_prompt()` 的**参数表就是变量清单**：`desc` / `selling_points` / `lang` / `garment_position` / `print_design_lock` / `has_product_ref` / `input_image_type` |
| `generate.py:408-413` | `PRODUCT_REF_LOCK` 是**函数内的一段固定串**，**不随商品变**（"Keep EXACT same: silhouette, print pattern…"） |
| `generate.py:500` | `ref_tail = f" {PRODUCT_REF_LOCK}" if has_product_ref else ""` —— 条件拼装 |
| `generate.py:1835` | 运行期自检靠 `"PRODUCT_REF_LOCK" in prompt` —— **子串存在性**当证据（形状检查，不是性质检查） |

**本项目为什么要多这一层**（**此段结论已被 §3.8 部分推翻，保留原文以留痕**）：
库 B 的锁段是**全局固定串**，而 §3.3 的实测结论是"**嘱咐式锁段锁不住**"（3 张里 2 张自造把手）。
当时的推断是：要锁住，锁段必须**逐特征枚举**；而"该枚举哪些特征、该否掉哪些失败模式"**随商品变**
⇒ 不可能靠填变量得到 ⇒ 必须先被**编译**一次。

> **§3.8 的改判**：真正必要的是**显式否定句**（类目级），**不是**本品具体特征。
> 所以"锁"这一层仍然**不是模板**（它是一段**整批逐字复用的冻文本**，与模板+变量在"谁在读、
> 怎么改"上不同），但它**不需要每商品编译** —— 类目固定文本 + 失败模式表渲染的否定句即可，
> 属**确定性组装**。阅读本节时以后者为准。

于是同一份资产里有**三种产出方式**，别混：

| 段 | 谁产出 | 何时产出 | 冻的是什么 | 运行时"填变量"？ |
|---|---|---|---|---|
| ① 保真段 | **类目固定文本 + 否定句**（失败模式表渲染）→ **人确认**；漂移时才注入本品具体值 | **离线 · 每上新类目一次**（§3.8 改判；原推断为"每件商品一次"） | 冻字符串（+ `lock_sha256`） | ✗ 逐字读 |
| ② 风格锁 | 人写一次 | 离线 · 每类目一次 | 冻字符串 | ✗ 整批复用 |
| ④ 约束条款 | 人写一次（+ 失败模式表回灌） | 离线 · 每类目一次 | 冻字符串 | ✗ |
| ③ 本格专属 | 坑位表 / 类目表 / 镜位表 | 运行时 | —— | ✓ 真实变量 |
| ⑤ 平台段 | `platform-specs` 表 | 运行时（按平台切） | —— | ✓ 查表 |
| ⑥ 模板/变体 | 库 C 25 模板 × overrides | 运行时（按配方切） | —— | ✓ **这一层确实是"选模板"** |

**一句话**：**①②④ 是"锁"（同源靠它们），③⑤⑥ 是"变"（每格/每平台靠它们）。**
用户描述的"选模板填变量"覆盖的是 ③⑤⑥；①②④ 是**冻结资产**。

> **粒度已改判为按类目**（本节写完 20 分钟后被 §3.8 的臂 E 推翻）：原先推断"锁段必须含
> 本品具体特征 ⇒ 按商品冻结 ⇒ 每件新商品一次编译 + 一次人工确认"。
> **臂 E 实测不需要本品具体值** —— 见 §3.8。下表"每件商品一次"一行以此为准。

> **缺口（本轮自查发现）**：§3.6 ② 写了一条纪律「冻结前必须有人确认『锁段』这一层」，
> 但**审核台五步页（收件→齐套→生成→审核台→控制面）里没有这个确认位** ——
> 按项目纪律「每个声明必须有消费它的代码位置」，这条纪律**目前是死的声明**。
> 落点已定（二类清单）：**不新增页，并入第 2 步「齐套判定」**。

### 3.8 臂 E：锁段**不需要**本品具体特征（2026-09-22 深夜 · 1 次调用）

**先自查出一个混淆变量**：臂 A → 臂 B 只换了锁段，但那**一次改动里混了三个变量** ——
(a) 嘱咐 → 枚举 · (b) 通用 → 本品具体 · (c) 无否定 → 显式否定。
所以 §3.3 写的「必须逐特征枚举」是**过度归因**：真正被证明必要的可能只有 (c)。

**臂 E**（`prompt_enhance/class_generic_lock.txt`）：**类目级通用枚举 + 显式否定，零本品具体值** ——
不写 `3:1`、不写"下三分之一棕色套"，**不需要读图、不需要商品资料**。

| 臂 | 锁段含本品具体值？ | 需读图？ | 凭空长出部件 | 两段式色块边界 | 出处 |
|---|---|---|---|---|---|
| A 嘱咐 84 字 | ✗ | ✗ | **2/3 长出把手** | 漂（#1 变矮胖） | §3.3 |
| B 本品枚举 820 字 | ✓ | ✓ | 无 | 棕色段比源图**短** | §3.3 |
| **E 类目通用** | **✗** | **✗** | **无** | **比 B 更接近源图** | `compare_ABE.jpg` · `zoom_B_vs_E.jpg` |

**判读**（放大到约 2× 后判 —— **不从缩略图下结论**，这条是本项目记过账的教训）：
- 挡住"凭空多出部件"的是**否定句**，而否定句**本来就是类目级的**（杯子类目 → handle / spout / second cap）。
- **本品具体数值没有被证明必要** —— 臂 E 连读数都没有，色块边界反而更接近源图。
- 表面纹理变光滑是 B / E **共有**（§3.5 已记），与锁段写法无关。

**改判（本条推翻 §3.7 的一处推断）**：

1. **锁段默认按类目冻结**（`assets/locks/<category>.json`），不是按商品 ⇒
   代价从"**每件新商品**一次编译 + 确认"降为"**每上新类目**一次"。
2. **"本品具体特征"降级为失败驱动的可选加强**：只在某格出现漂移时才注入 ——
   与库 A `run_loop.mjs` 的**修正句回灌**同构（只在失败时加，不预先加）。
3. **离线 LLM 编译从"必须"降为"失败时才调用的工具"**：默认路径是
   **类目固定文本 + 失败模式表渲染出的否定句** —— 确定性、可 diff、零模型调用，
   与库 B 把 `PRODUCT_REF_LOCK` 写成**常量**同形。这与 J1 同向（少一层每商品输入，更可复算）。

⚠ **边界**：本结论来自 **1 件商品 / 1 次调用 / `n=3`**。换商品、换类目**未验**（四类 #2 缺素材）；
带密集印刷图案的商品未验。⇒ 上面三条按"**默认 + 可推翻**"落地，**不写死成不变量**。

> **这一枪最有用的地方不是结论，是方法**：若我不把 A→B 里的三个变量拆开，
> 我会把"每件商品都要编译一次锁段"当成**已验证的必要代价**写进设计 ——
> 它成本高，还额外挂一道没人愿意做的人工确认。
> **"一次改了多个东西"永远不能算单变量对照。**

### 3.9 元提示词在这套运行设计里到底占什么位置（2026-09-23 00:1x）

> 起因：用户问「你设计如何运行的，那你要元提示词干嘛」。
> **质疑成立一半**：元提示词**不在运行路径上** —— 一次生成的全部模型调用只有生图与质检。
> 但它也不是废件：它的**规则**已被确定性资产吸收，剩下的是**一个还没接线的调用点**。

**一、运行路径（在线装配全程零模型调用）**

```
在线装配  ← build_prompt.py：纯组装、不联网、不需要 key（唯一能「先做完再谈钱」的一步）
  读 assets/locks/<category>.json          → ① 保真段 ② 风格锁 ④ 约束条款   逐字读
  查 slots.yaml / <类目>.yaml / 镜位表       → ③ 本格专属                     填变量
  查 platform-specs 表                     → ⑤ 平台段                       填变量
  查 库 C 25 模板 × overrides              → ⑥ 模板 / 变体                  选模板
        ↓ 拼接
  生图 1 次 × k 张 → 客观规则过滤 → VLM 质检 8 项 + 修正句
        ↓ 未达标：修正句回灌 → 下一轮（≤ maxRounds）· 无修正句即止损
  人选 1 张 → 采纳
```

**元提示词不在这张图的任何一格上。** 这是「模板 + 填变量」覆盖不到 ①②④ 的原因，
也是「离线编译 + 冻结」这套说法到目前为止唯一站得住的部分。

**二、它的规则其实已经被吸收（这才是「要不要它」的关键）**

拿臂 E 的锁段（`prompt_enhance/class_generic_lock.txt`，13 行）逐行比对：

| 行 | 内容 | 现状 |
|---|---|---|
| 1–6 | 类目级**维度**枚举（轮廓/比例/色块边界/盖结构/材质/只许改背景光角影） | **待定** —— 是否类目专属**未验**（至今只验过 1 个类目） |
| 7–12 | 逐条**显式否定** | **已可确定性渲染** —— 就是 `failure_modes.json` 里 `negation` 字段的拼接：**FM-01/02/03/05/06 五行逐字一致**，FM-04 是同一要求的改写（表里是 `Keep the lid assembly's layered structure…`，锁段里写成 `Do not add, remove, merge or recolour any section, ring or layer…`）⇒ 后者说明**渲染器需要支持同一模式的多种句式**，不能假设逐字照抄 |

⇒ 元提示词 v0.2 里那些**规矩**（不许编造外观、必须逐条显式否定、可逐条核对、不用形容词代替数字）
已经**升格成资产**：`failure_modes.json` 是唯一出处，「写提示词」与「校验提示词」两边都读它。
**留在元提示词里只剩一件事：起草 1–6 行。**（而 7–12 行这部分职责，从此与它无关。）

**三、三个候选位置 —— 必须选一个，不许三个都留**

| # | 位置 | 触发 | 产物 | 现状 |
|---|---|---|---|---|
| a | **新类目初始化起草器** | 每上新类目一次（人按下第 2 步的「重编译」） | 候选锁段 → 人签字 → 冻结 | **唯一已登记的消费点**（§6 消费方：第 2 步读数行里的重编译按钮） |
| b | **漂移加强链** | 某格出现锁段挡不住的漂移 | 加强段 → 人签字 → 覆盖该类目锁段 | 与「注入本品具体值」同级，**谁先谁后未定** |
| c | **R&D 探针**（不进产品路径） | 人主动跑 | 对照数据 | `meta_compiler_v1.md`（臂 D）纯属此类 |

**四、要改的不是删元提示词，是把 (a) 的触发条件写进表**

按项目纪律「每个声明必须有消费它的代码位置」：§6 **已给 (a) 登记了界面位**（第 2 步那个按钮，
与「冻结确认位」同一行 —— 这两件事其实是同一件事：确认 = 看过 + 签字，重编译 = 不满意就再起草一次），
但**触发条件没写** —— 运营不会对着一个新类目知道该不该按。
⇒ 缺口与 §3.7 那条同型，落点已定：**并在第 2 步一起写。**

**判据（决定 (b) 是否需要存在）**：第二个类目的商品跑一遍。
- 若 1–6 行**跨类目通用** ⇒ (a) 的默认消耗也归零 ⇒ 元提示词整体降级为 (c)、**从产品路径移出去**。
- 若 1–6 行**类是类目专属** ⇒ (a) 成立，每上新类目跑一次。

**两种情况都不留「声称是退路、实际没接线」的假保护** —— 那是硬教训 1 的同型错误。

**五、为什么不把它拿来做「提示词增强」（2026-09-23 00:2x）**

> 追问：*「为什么不拿来做提示词增强」*。这里说的「提示词增强」是 ADR 判据 **J3** 的那个概念
> （源头是用户最早那句提案：「其他的提示词优化增强相当于 SKILL」）。

| 若把元提示词用在 | 挡住它的判据 | 证据 |
|---|---|---|
| **每次运行前把拼好的 prompt 过一遍 LLM** | **J1**（同输入 → 同输出） | 同一元提示词、同一输入连跑 3 次：锁段 **1209 / 971 / 1113** 字 ⇒ `lock_sha256` 不可能跨格相同 ⇒ **同源这条不变量当场消失** |
| **让 LLM 来承担「提示词增强能力」这个角色** | **J3**（增强能力必须有**载体**） | J3 要的是**可 diff / 可回归 / 加类型只改一处** —— 不可复现 ⇒ 三条**全不满足**。库 B 的 `build_prompt()` 738 行之所以是载体，正因为它可 diff；元提示词是**一次性工具**，不是载体 |
| **润色 ③⑤⑥ 的措辞** | **臂 C1 实测** | LLM 把没看过图的东西写成断言，而**断言会被执行**（3 张全丢棕色矮套、盖变按钮盖）⇒ 在线增强 = 每格多一次「植入错误断言」的机会，且**这条断言不在 `plan.json` 里**（它是运行时生成的），审计链看不见它 |

**「提示词增强」的实际收益来自三样确定性资产，与 LLM 无关**：

| 增强哪一面 | 载体 | 为什么它有效 |
|---|---|---|
| **结构** | 六段模板（库 B 形状） | 把人容易漏的段落变成**必填格** |
| **知识** | 平台规格表 / 类目表 / 镜位表 | 知识以**可 diff 的查表**形式进 prompt，而不是靠模型记得 |
| **失败模式** | `failure_modes.json` → 否定句渲染 | 每轮实测到的失败追加一条，**下轮自动进锁段** ⇒ 复利资产 |

LLM 能加的那一层是**措辞** —— 而模型的失败**不是「词不够好」，是「改掉了商品」**。

**★ 判据收敛（这一条比上面十条都值钱）：LLM 的位置由「签字点」决定，不由「哪一段」决定。**

```
离线起草 → 人签字 → 冻结成资产 → 在线逐字读        ✅ 允许
在线拼好 → 直接送进生图模型                        ❌ 禁止
```

⇒ 所以「想扩大提示词增强的范围」的正确做法是**把更多段纳入「离线起草 + 人签字 + 冻结」**
（例如库 C 那 25 个模板同样可以由 LLM 起草一次、人签字后冻成资产），
**不是**在在线路径上加一次 LLM 调用。前者让资产变多，后者让不变量失效。

## 4. 验收语义反转：k 次 → 至少一张（照库 A `run_loop.mjs`）

### 4.1 闭环（逐行对应库 A）

```
for r in 1..maxRounds(默认3):
    生成 k 张候选
    ├ 关卡1 客观规则：纯白/占比/边长/比例/体积      ← A check_listing.py
    │                 不过的直接丢
    ├ 关卡2 VLM 质检：8 项 + 风险等级 + 修正句      ← A detect-task
    │                 8 项固定：商品崩坏/人脸不自然/手部异常/肢体结构错误/
    │                            文字乱码/光影矛盾/边缘融合痕迹/平台合规
    ├ riskOk = 风险等级 ≤ --accept（默认"低风险"，可调）   ← 阈值，不是"完美"
    ├ compOk = 合规判定 ≠ reject-risk
    └ riskOk ∧ compOk ──► accepted = true → 留下这一轮 → exit 0
             ✗ 未达标 ──► 修正句回灌 prompt → 下一轮
   到达 maxRounds 仍未达标 ──► 交人工（exit 1）
```

**两个必须照搬的细节：**
1. **修正句直接追加回 prompt**，不是重新组织；客观失败走**预写翻译表**（库 A `run_loop.mjs`：
   "纯白背景" → 一整句英文 `Pure seamless white background, RGB 255,255,255…`）——这就是本项目
   `fixers.CHECK_RUNG` 里"诊断齐、最后一跳丢"的那一格的正解。
2. **质检给不出可用修正句就立即停**（库 A 有这个判定），避免"每轮烧钱但 prompt 没变"的空转。

### 4.2 成本控制：两阶段，不是盲目 k 倍

- **阶段一（方向确认，1 张）**：先出 1 张 → 人看 → 满意 / 重生成(≤3) / 换配方 → 锁定
- **阶段二（批量出图，k 张/格）**：复用锁定的风格锁 + 参考图集，不再问方向

出处：库 B `SKILL.md` 4.5 两阶段模特锁定（45 内置模特库 / AI 生成后确认→锁定→出其余 6 种）；
库 A `batch.mjs` 的 `--max-credits` 成本熔断。

**k · n · 轮次是三个不同的量（2026-09-22 澄清 —— 我此前把它们写混过）**

| 量 | 是什么 | 出处 / 现状 |
|---|---|---|
| **n** | **一次调用里要几张候选**（生成协议参数，实测支持 1–6） | `lock_probe.py` 实测：`n=3` 一次调用 23.8s 拿回 3 张 |
| **k** | **一格要拿出的候选张数**（验收口径：k 张里至少一张达标） | 库 A `run_loop.mjs:98` `--accept` 阈值线 |
| **轮次** | **人审不满意 → 重做 的串行循环** | 库 A `run_loop.mjs:171-190`；本项目已由 M6 四档重做实现 |

⇒ **"至少一张"从来不靠"一次做成"，靠的是"人审 + 重做"。** 所以成本不是 `k × 单价`，
而是 `Σ_轮次 ⌈k_r / n⌉ × 单价`，且**只有人看着觉得不行才进下一轮**（机器只做客观关卡预筛，
`--accept` 是可调阈值线，默认低风险 —— 不追求一次完美）。

### 4.3 重试的分层 —— 「冻结」不是重试的对立面（2026-09-23 00:3x）

> 追问：*「你这么固定那重试你怎么设计的」*。先把前提摆正：

**模型输出从来没被固定过。** 官方口径（`docs/最小可行设计.md` §2 已记）：**同 seed 不保证下一次出同一张图**
⇒ `plan.json` 是「**可重放**」（近似结果），不是「**可复现**」（同一张图）。
旧设计里「重放 plan 第 4 条」这句话，在图像这一层**本来就是空的**。

所以冻结的作用**不是**让重试得到同一张（做不到），而是让**「重试时到底改了什么」可归因**：

```
锁段逐字不动（lock_sha256 不变）
  ⇒ 两张图的差异只能来自：seed / 尾部追加的修正句 / 模型自身随机性
  ⇒ 不可能来自「锁段被悄悄改了」
```

**★ 冻结不是重试的对立面，冻结是重试能被解释的前提。**

**四层重试（成本从低到高，只有 R3 动锁段）**：

| 层 | 触发 | 改什么 | 动锁段 | 成本 | 谁决定 |
|---|---|---|---|---|---|
| **R0 换张** | 同轮 k 张都接近但都不达标 | 只换 seed | ✗ | 1 次生图 | 系统 |
| **R1 修正句回灌** | VLM 给出可用的修正句 | **只在 prompt 尾部追加**，不重组 | ✗ | 1 次生图 | 系统（库 A 模式） |
| **R2 换配方** | 修正句拿不到 / 连两轮不过 | 换模板变体 / 镜位 / 背景取景提示 | ✗ | 0–1 次 | 人（界面三选一） |
| **R3 改锁段** | 失败表现是**商品被改**（不是背景/光/构图） | 注入本品具体值 / 走元提示词加强链 | **✓** | 1 次 LLM + 1 次生图 + **人工签字** | 人 |

**R0–R2 一律不动锁段** —— 这是重试的**作用域边界**：锁段一动，跨格 `lock_sha256` 比对当场失效。
⇒ 在重试这条路上，「改提示词」与「改锁段」必须是两件被分开记账的事。

**R3 有一处连带语义没写（本轮发现）**：锁段被改之后，
**该类目此前已产出的所有格子与新锁段不再同源**。流程上必须二选一：

- (a) **该批全部作废重跑** —— 贵，但语义干净；
- (b) **锁段带版本号**：已产出格子记 `lock_v1`、新格子记 `lock_v2`，**跨格比对按版本分组** ——
  省，但"七张同源"要改写为"七张同源（同版本内）"。

⇒ 这条现在**文档里没有**，与 §3.7 那条同型：有纪律、无落点。

**两条熔断（都有出处，不是我想的）**：
1. **质检给不出可用修正句 ⇒ 立即停**（库 A `run_loop.mjs`）—— 否则"每轮烧钱但 prompt 没变"。
2. `--accept` 是**可调阈值线**（默认低风险），不是"完美"—— 库 A 的口径是**不追求一次做成**。

**留档纪律直接来自"不可复现"这个事实**：既然同一张图拿不回来，**没留档 = 那张图永远消失**
⇒ 同轮 k 张全留、跨轮留被采纳的 + 每轮各一张（§6 已定）。
**留档是重试唯一能拿回历史产物的方式** —— 比"可重放"这个说法实际得多。

### 4.4 ★ 本轮新发现：删掉不变量 C 之后，最便宜的那层重试也没了

§2 那张表把 **C「文字层不参与画面生成」判为删除**（理由：三库都让模型画字），
§5 随之删掉 `text` 重做档。因果写对了，但**代价没有记账**：

| | 旧设计（文字用字体绘制） | v4（文字由模型画） |
|---|---|---|
| 改一个错字 | **0.1 s，免费**（只重画文字层） | **24–33 s + 计费**（重跑生成） |
| 中文笔画正确性 | **结构上不可能错** | 人工 **200% 逐字核对**（库 C 口径） |
| 修字手段 | 确定性重绘 | 只剩英文修正句回灌 —— 而中文是模型控制力最弱的一类 |

旧设计 `docs/最小可行设计.md` §8 那张「改什么 / 花什么」表里，
**"文案错 → 0.1 s 免费"这一行目前没有对应实现**；而 v4 §8 代价表只写了"人工 200% 核对"，
**没写"重做成本 ×250"**。

**建议（未验证，属三类可实验项）**：文字改成**两条路共用** ——
模型能画好的位置交给模型（保生成质量），**画不好的走"生成后字体叠加"**。
理由不是"旧设计更好"，而是叠加**零模型调用、可独立重做**，
恰好补上重试分层里**最便宜的那一层**（改字不改图）。
⚠ 与不变量 D（位置 1 零模型调用）同向，但与"生成优先"的取舍**未验**，需一张 A/B 对比。

### 9.1 为什么并列参考必然产出清单而不是设计

### 9.4 库 C = 配方来源（**取数据，不取骨架**）

> **更正（2026-09-22 21:2x）**：本节初稿给的理由——"其固定模板架构已被 B 论证废弃"——**不成立**。

**1. 确定性（决定性的那条）**
