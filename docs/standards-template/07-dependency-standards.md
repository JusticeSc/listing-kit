# 07 · 技术选型与依赖标准

> **目标**:优先复用成熟方案,禁止重复造轮子;依赖进得来、锁得住、退得出。
> **执行入口**:本文件的规则由 `06` 的 **②.5 技术选型门** 强制执行——规则告诉 AI“什么是对的”,选型门保证“它一定会经过”。

---

## 1. 复用阶梯(实现路径优先级)

遇到一个待实现的能力,按以下顺序逐层检查,**能用上层就不用下层**:

```text
① 复用现有代码 → ② 配置现有依赖 → ③ 标准库/框架能力
      → ④ 成熟第三方库 → ⑤ 外部服务 → ⑥ 最后才自研
Reuse → Configure → Integrate → Extend → Build
```

| 层 | 含义 | 示例 |
|---|---|---|
| ① 复用现有代码 | 仓库里已经有实现,直接用 | 项目里已有 `paginate()` 就不要再写一个 |
| ② 配置现有依赖 | 已在依赖树内的库,看它还有什么能力 | 已用 `httpx`,它的超时/重试传输层优先于新手写 |
| ③ 标准库/框架能力 | 语言标准库、框架自带功能 | `argparse`、`logging`、`zoneinfo`、FastAPI 自带校验 |
| ④ 成熟第三方库 | 通用基础设施的标准件 | `tenacity`(重试)、`pydantic`(校验) |
| ⑤ 外部服务 | SaaS / 云服务 | 不自建消息队列,先评估云厂商托管方案 |
| ⑥ 自研 | 只有第 5 节的情形才允许 | 真正的业务逻辑 |

AI 最常见的错误就是从需求**直接跳到第⑥层**。

## 2. 禁止自造清单

以下通用基础设施**默认复用,一律不许自造**:

- 日期时间与时区、UUID、JSON / YAML / CSV 解析
- HTTP 客户端、重试与退避、限流、缓存、定时调度
- 任务队列、事件总线、状态机、连接池
- 参数校验、序列化、配置管理、日志框架、CLI 解析
- 密码哈希与加密、JWT、鉴权、ORM / 数据库驱动封装

> 示例以 Python 生态为主(如 `tenacity`、`httpx`、`pydantic`、`APScheduler`);其他语言替换为等价生态标准件。

## 3. 选型四问(引入任何依赖前必答)

1. **标准库 / 已有依赖够不够?** 够 → 不引入。
2. **维护是否活跃?** 近 12 个月有提交、issue 有响应、有真实用户量;无人维护的库等于未来的自研负担。
3. **许可证是否兼容?** `MIT / BSD / Apache-2.0` 可直接用;`GPL / AGPL / 商业 / 未知` → **必须人类确认**。
4. **体积与安全代价?** 会拉多少传递依赖、是否有已知 CVE、是否需要原生编译、是否增加部署复杂度。

## 4. 引入流程

- 走 `06` 的 ②.5 选型门:填写 `templates/TECH_SELECTION.md` 选型报告 → ✋人类确认 → 实现 → 登记进 `00` 第 2 节依赖表 → 结论记入 `PROGRESS.md` 的 ADR。
- 单 PR 新增依赖**不超过 3 个**,多了拆 PR。
- 禁止“顺手升级”无关依赖;升级走单独的 `chore` PR。

## 5. 允许自写的判定

同时满足以下全部条件,才允许自己实现:

- 是**业务逻辑**而非通用设施。
- 现成方案经过第 3 节四问后确实不合适,理由已写进选型报告。
- 有单元测试覆盖。
- 放在项目业务模块内,**不许扔进 `utils/` 万能抽屉**。

记住经验法则:

> **业务逻辑可以自己写;基础设施能力默认先找成熟方案。**
> 反例也成立:30 行 TTL 缓存 vs 拉 20 个依赖的缓存框架——此时自研反而合理,理由同样要写进报告。

## 6. 版本与锁定

- 生产依赖必须**锁定版本**(`requirements.txt` 用 `==`;Node 用 lock 文件;Go/Rust/Java 用各自锁定机制)。
- 禁止浮动版本(如 `>=`)上线;“本地能跑、CI 挂掉”多半是版本没锁。
- 生产依赖与开发依赖分离(对齐 `05` 第 4 节)。
- 每学期(或每季度)跑一次已知漏洞扫描,结果记入 `PROGRESS.md`。

## 7. AI 常见反模式(禁止)

- 用正则解析 JSON / 手写日期格式化与时区换算。
- 手写重试循环 / 手写限流计数器 / 手写简易任务队列。
- 自己实现密码哈希、加密、JWT。
- 复制粘贴来源不明、无许可证说明的大段工具函数。
- 只为用其中几行代码引入重型库。
- 同时引入两个同类能力的库(如同时用 `requests` 和 `httpx`)。

## 8. 依赖排错(补 `05` 第 7 节)

| 现象 | 优先检查 |
|---|---|
| 装不上 | 镜像源、私有源配置、Python/Node 版本、是否需要原生编译工具链 |
| CI 能过本地不过(或反之) | 版本是否锁定、平台差异、lock 文件是否提交 |
| 镜像体积暴涨 | 开发依赖是否打进了生产镜像(对齐 `05` 第 4 节拆分) |
| 引入后行为异常 | 是否与现有依赖版本冲突(`pip check` / 等价命令) |
