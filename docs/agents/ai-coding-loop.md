## 总纲

**六环：选 → 说 → 切 → 验 → 因 → 学。**按任务选择必要环节；失败进入“因”，只回退受影响的环节，复用前提未变的实现与证据，不从头重复已完成工作。

**四项工作假设及其边界：**

1. **生成提速不免除验证责任**：需求、集成和验证仍可能成为瓶颈，但验证也能通过类型、工具和流程改进提效，不能由此推出“验证不可压缩”或要求每次全量检查。
2. **自动化可能削弱警觉**：不能靠主观顺畅感判断质量；检查应能暴露具体错误，但不能断言自动化必然降低人的能力。
3. **能力与任务、上下文及工具有关**：按当前模型和实际任务验证适用边界，不把架构、命名等类别永久列为AI禁区，也不把判断责任转交用户。
4. **边界与组合值得针对性验证**：根据实际风险检查异常、状态转换及跨模块组合；正常路径也可能有严重缺陷，不靠事故类比预先认定根因。

## 选：判断收益、风险与可验证性

同时考虑实现、理解、集成、验证和维护成本，以及错误后果与退路；验证便宜是有利条件，不是唯一准入标准。
交前明确：怎么算对、错了影响什么、改变是否可审查、失败如何恢复。
开发者主动承担架构、命名和跨模块分析，提出有依据的方案；仅将产品选择、缺失事实、权限或重大不可逆取舍交给用户。
做完标志：能说明为什么采用该方法、由什么证据验收，以及剩余风险。

## 说：明确可观察验收与边界

三件事：①写出用户可观察的目标和判错依据；适合自动化的写成实际存在的命令，界面、人因和品质用相应观察验证，不把用例数量当质量；
②写清非目标与权限边界，不顺手扩成重构或正式产品；
③自行查明仓库约定、业务规则与相邻实现，只对影响行动的不可获取信息提问。多文件工程改动先确定改动范围、受影响消费者、验证和失败退路。
做完标志：目标、非目标、依据和验证方式足以支撑下一步，不以补齐形式化文档为由延迟已有信息可支持的工作。

## 切：切到还读得动

改变切到能完整理解与审查的范围，不把固定行数当质量阈值；每片应是最小完整行为改变，必要消费者同组闭合，不交付空骨架或占位实现。
先保证可恢复；只有提交授权成立时，才按 `AGENTS.md` 的提交规则组织自包含commit。并行任务需有明确接口、文件所有权和集成责任，不要求逻辑上完全无关。
做完标志：每片结果、依赖、验证与退路清楚，不为缩小diff留下无法工作的中间产物。

## 验：分层检查，覆盖实际风险

1. **机械化**——按改动运行受影响的现有编译、类型、lint或静态检查；不是每次全量必跑，也不临时引入未采用的工具链。
2. **行为层**——通过实际消费者验证结果。AI可以写测试，但预期结果须来自需求、独立样例、业务不变量或可信基线，不能仅回声实现。需要时用受控故障或变异验证判错能力；只对确有风险的输入空间采用属性或模糊测试，不默认比有针对性的例子更有效。
3. **对抗与差异**——审查未测边界、异常吞噬和为刷绿削弱断言。测试删留按 `AGENTS.md` 的业务保护规则判断，不凭数量变化定罪或宣告改善；高风险时引入独立视角，但换人或换模型本身不保证判据独立。
4. **真实路径**——工程行为需实际smoke；界面验证真实表面。灰度或金丝雀仅在部署权限、环境和风险条件满足时使用，不能取代发布前验证，也不是每次任务的必经步骤。
做完标志：有与改变相符、能判错的实际证据，能说明验证范围与未证部分；工具成功仅证明其实际检查内容，不证明产品完整正确或未来不会失败。

## 因：保留失败，按假设定位

顺序：①保留原始失败，核对受测版本、输入、环境与检查本身，不能先假定是检查误报；
②有间歇性或竞态假设且重复安全时，设计有次数上限、观察项与停止条件的重复实验，保留全部结果；一次成功不抹去旧失败，少量重复也不能证明故障纯属偶然；
③按当前证据区分需求、实现、环境、检查或能力问题，一次改变一个可检验因素；不为凑固定分类反复重做；
④收费、有副作用或状态UNKNOWN的操作不默认重试，继续遵守相应授权与防重复规则；
⑤修后确认原失败条件下的目标行为恢复，分清根因修复与吞异常、删保护或跳测试带来的假绿。
做完标志：有可复核的原因与修后证据；若尚未定位，明确未决点和能区分假设的最小下一动作，不编造确定归因。

## 学：预测—核对—记录

对重复出现或高风险任务，可在行动前记录最有用的预期，完成后核对差距；只记录会改变后续决定的教训，落实到现有规则、实现或验证，不另建例行预测/评分平台。
统计指标仅在有真实记录、分母与适用范围时使用；不能凭印象报命中率、迭代数或节省比例。
做完标志：可复用的教训已落实为下一次的具体改变；无新教训时不强写总结，写总结本身不算产品问题已解决。

## 极简版

1. 选：权衡总成本、风险、退路与可验证性。
2. 说：明确目标、判错依据、非目标和权限。
3. 切：保持可审查、可恢复的最小完整改变。
4. 验：用独立判据分层验证实际结果。
5. 因：保留失败，按假设定位，重复实验有边界。
6. 学：把有证据的教训落实为可复用改变。

一句话：**主动承担工程判断，用实际证据验证结果；方法可以调整，事实、权限与验收底线不能为方便而放弃。**
方法若无法解释真实失败或改善决策，就修正方法，不强行把事实塞进六环。

## 受控自举：用本方法改进本方法

用户已要求持续完善并实现可自举AI Coding。本项目把它落实为授权内的工程改进，不是自动扩大权限、任意自改验收或宣称模型能力自我进化。具体本地记录见 `_working/ai-coding-bootstrap/work.md`；`_working/**` 被 gitignore 忽略，该记录只在本工作树可读，不随仓库发布，也不进 INDEX 登记。它不替代原Product V2的计划、state或原生Goal。

方法改进按以下闭环执行，不另建任务库、代理调度器或评分平台：

1. **问题与假设**：从实际失败提出可证伪的原因与预期改变。把判错依据与非目标先写清，不能实现后再修改标准制造通过。
2. **保留退路**：修改前保存受影响文件原字节及必要输入；已有历史与用户改动保留。无关原产品权限不因改进任务自动解除。
3. **最小工具改变**：优先修改当前实际消费者。上下文只承载原则与入口，能够由程序判断的精确模式、退出码或身份错误应在相应执行位置处理。
4. **同判据比较**：必要时用保留的原始实现与候选实现检验同一失败条件；再运行正常消费者路径，核实没有用禁掉全部操作换取拒绝错误。判据独立于实现，不以更换作者或模型代替独立性。
5. **采用或撤回**：根据正确性、覆盖范围和新增成本，明确本地保留、调整或撤回的理由。撤回只撤本轮差量；有后续修改先比对，不整文件覆盖用户工作或hard reset。保留失败证据，本地采用不等于获准提交、合并或发布。
6. **后续观察**：在下一次实际任务中观察同类失误是否减少。没有足够记录不报效率百分比；完成一次闭环不声称已经实现无监督自主改进。

本地与CI使用既有 `tools/select_v2_checks.py` 选择影响范围，命令仍唯一取自CI verify目录，精确模式取自验证登记：

```bash
uv run --locked python tools/select_v2_checks.py tools/select_v2_checks.py --emit-github
```

将路径替换为本次真实改变；`--emit-github`只预览，`--run`才执行。普通说明/不可执行过程证据只选管理检查；已批准验证器选自身与必要构建前置；已知UI视图选业务消费者（独占的共享DOM根按源码实际读取派生要求集，不写手名单）；混合变更取并集。公共合同、锁或未知影响保守扩大；走查没有批准离线模式/必要输入时明确报缺口，不能用全产品回归代替走查证明。

选择器先核对整份命令目录的精确入口、参数、批准与冲突，再启动首条命令；未登记或未批准模式必须拒绝，paid/remote/aggregate不进入普通执行，首个失败保留真实退出码。注册与选择不是用户授权来源，不能拦截绕过该入口的工具调用。未变前提的成功证据继续复用，最终必要两轮仍读取完整目录，不随每次小改重复。

CI的changes job使用真实base/head提交差量生成路由；坏基线失败，手动完整入口保留。PR/手动分类失败必须使required验证作业显式失败，不能条件skip伪装成功。verify消费同一结果；无运行/构建/发布闭包变化时明确记为不适用，不构建或部署相同内容，不冒称容器已验。实际实现/本地证据与远程是否生效须分别核对。
