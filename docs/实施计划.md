### 0.1 三个必须先说清的现状缺陷

**① `slots.yaml` 是旧设计，三处违反不变量**

| 位置 | 现在写的 | 问题 |
|---|---|---|
| 4 / 5 / 6 | `render_path: generate` | **位置 5 细节、位置 6 内容物是"事实"**（材质长什么样、盒子里有什么），生成它们 = 编造 → 违反 §4.1 判据 |
| 2 / 3 | `generate_then_text`（生成底 + 叠字） | 新定案是**纯色底**（`flat_overlay`）。留着就是"位置 2 用生成底"这个已废弃的产品决定 |
| 3 | `needs_scale_reference: true` | 要求"与手 / 硬币 / 手机并置" —— **那是道具**，而 `E0` 明令原图不得含道具。**同一份配置自相矛盾** |
| 全部 | `status: done / todo` | 被当成"本次做哪几个"的开关 —— 而新设计里**张数 = 坑位表 ∩ 素材齐套**。`status` 是死字段 |

**② 分派是 `if/else`，不是注册表**

`pipeline.py` L48 `if path_key == "compose"`、L78 `if path_key == "generate_then_text"`。
→ **等价于 `if slot == 1`。** "加一个坑位 = 加一行"目前**不成立**，加坑位要改这段代码。

**③ 字体合规缺口（这条最容易被漏，且后果是下架）**

`kit_config.resolve_font()` 默认探测 **`msyhbd.ttc`（微软雅黑）**。
**微软雅黑的商用权利属方正，用于商品图属未授权商用** —— 这和"原图自带水印"是同一类问题：
**工具修不了，且不合规的成品图直接不可用。**

按"合规问题在入口拦"的既定原则，它必须进 `assets{}` 校验，**M2 就要换掉**。

**④ `status: done/todo` 是死字段**：声明了"做哪几个"，但真实依据是素材齐套。删除。

## 1 改造的总判据：把枚举换成两个正交字段

这是整个 M1 的**唯一一件事**，其余都是它的展开。

```
旧：render_path = compose | generate | generate_then_text   ← 组合爆炸
                  「像素怎么来」和「有没有字」被缝在一个枚举里

新：renderer  ×  text                                        ← 加法
    compose_white  ×  none
    flat_overlay   ×  overlay
    gen_bg_paste   ×  none
```

**为什么必须拆**：旧枚举里每出现一种新组合，就要加一个枚举值（`generate_then_text_no_text`…）。
拆开后，**加一种组装方式 = 加一个 renderer 文件；要不要文字 = 表里一个字段**。
→ 这才是"加一个坑位 = 加一行数据"能成立的前提。

**配套三条**（来自 `最小可行设计.md` §9.1，此处只列施工含义）：

| 判据 | 施工含义 |
|---|---|
| 扩展是加法 | `orchestrator.py` 里**不允许出现 `slot["id"] ==`** |
| 一个字段一个解释者 | `renderer` 只被 `registry` 解释；`text` 只被 `flat_overlay`/`textlayer` 解释 |
| 拒绝派生配置 | **没有"输出几张"这类设置项**；张数是算出来的 |

**新表结构（位置 1 / 2 示例，作为施工基准）**：

```yaml
version: 2
site: US
category: home_kitchen
catalog: config/catalog/home_kitchen.yaml

slots:
  - id: 1
    role: main
    purpose: 主图 / 白底展示
    renderer: compose_white
    text: none
    mandatory: true          # 平台强制，不可关
    needs: [front]           # 缺 front → 全局拒绝
    background: pure_white
    product_fill_pct: 85
    validate_level: strict
    validate_rules: [white_bg_purity, product_fill, has_text_block,
                     aspect_ratio, long_side_px, filename_has_upc]

  - id: 2
    role: secondary
    purpose: 卖点图解 / 信息图
    renderer: flat_overlay
    text: overlay
    mandatory: false
    needs: [front, bullets]
    text_slots: {title: 1, callouts: 4}
    validate_level: medium

  - id: 5
    role: secondary
    purpose: 细节材质
    renderer: closeup_crop     # ← 不是 generate
    text: overlay
    mandatory: false
    needs: [closeup]
    validate_level: loose
```

### M2 ✅（改名叫「E0 体检」，因为齐套判定 M1 就做完了）

**先说一处计划与现实的偏离。** 计划里 M2 = 「齐套判定 + 字体合规」两项，但：

- **齐套判定 M1 已顺带做完**（M1 验收①绕不开"按 `needs` 算张数"）
- **字体替换按用户决定不做**

于是 M2 实际只剩一件事：**E0 体检**。这不是缩水 —— 它补的正是此前整条链路最大的一个洞：
**素材投进来时没人看一眼**。一张 320px 的原片、一个改了扩展名的文本文件，此前都会被
一路送到渲染器那里，然后产出"尺寸合规、实则不可上架"的成品图。

#### 设计核心：把"能自动判的"和"判不了的"分开

E0 的形状不是"加几个校验器"，而是**先承认机器判不了什么**：

|                | 有规则 | 无规则 |
|---|---|---|
| **有参照物** | ✅ 自动：可读性 / 尺寸 / 通道 | ⚠️ 半自动：边缘像素异常 |
| **无参照物** | ✅ 自动：是否已带 alpha | ❌ **只能人工**：水印 / 道具 / 主体完整 / 角度 / 字体授权 |

右下的红格就是 `src/intake.py` 里那份 `ATTEST_ITEMS`。工具**不假装验过它们**，
但真跑时要求 `product` 里有一份签字；签字落进 `plan.json` 与 `run.jsonl`，
于是"谁在什么时候确认过什么"可回溯 —— **这是人工项唯一能被事后审计的方式**。

> 这条纪律的直接来源是 v1 的教训：`validate_rules` 里写着 `no_watermark`，
> 而 `validators.py` 从来没有实现过它 —— **声称校验、实际静默跳过**。
> 现在遇到同类问题，答案是"要求签字"，不是"写个不可靠的检测器假装有保护"。

#### 三处自己查出来的缺陷（都不是"跑通了"能发现的）

**① 主体贴边 —— 真缺陷，已修**

`subject.png` 是**紧裁切**的（`rgba.crop(bbox)`），所以它的第 0 行就是产品的最高那一行。

实测贴图框 `y=0`：产品顶边就是画布第 0 行。

**它比"观感不好"严重**：贴边的商品图平台侧通常不接受，而位置 2/3 的校验规则
只有尺寸与文字存在性 —— **查不出贴边**。所以这道修正不能指望校验兜住，只能由几何保证：
`PAD_RATIO = 0.035` 从可用区里扣掉（因此垂直居中位置与修复前**完全一致**，

**并且新增断言 D。** 一条断言的价值看它抓到过什么：D 抓到的正是一个校验抓不到的缺陷。

- 更隐蔽的一处：同一张图上的**强调色有两个来源** —— 标注线箭头读 `catalog.palette.accent`，

| 归 `catalog/<类目>.yaml` | 归 `brand.json` |
|---|---|
| `palette.base` 底色 / `palette.text` 文字色 / `palette.accent` 强调色 | `fonts` 字体 / `text_bar_color` / `text_bar_opacity` |

```
模型看得到：  取景提示 + 构图约束 + 「不要出现任何产品…」+「不要出现任何文字…」
模型看不到：  主体（subject.png 根本不进请求）
主体从哪来：  代码在模型返回之后 paste 进画布
```

三句拼装全在 `build_bg_prompt()` 里，**没有一个字来自人工取景提示** —— 提示词是人写的，会漏；不变量必须是代码保证的。

| 子句 | 为什么必须由代码追加 |
|---|---|
| `SUBJECT_EXCLUSION_CLAUSE`（"画面为空场景背景，不要出现任何产品、商品、容器、杯、瓶、包装盒、logo 或其局部"） | 取景提示只描述"环境长什么样"，不会主动说"不要产品" |
| `NO_TEXT_CLAUSE`（"不要出现任何文字、字母、数字、汉字、水印、标志、logo、签名、价格标签、促销角标、边框"） | 实测：首轮 qwen-image-3.0 自作主张画了水滴 logo 与 `THERMO` 字样 |
| 负向词 = `SUBJECT_EXCLUSION_NEGATIVE`（英文类别词，模型对英文更敏感）+ `BASE_NEGATIVE` + `brand.forbidden_on_image` | 中文正向句与英文负向词**两边都堵** |

**验收结果**

| # | 断言 | 实测 |
|---|---|---|
| 1 | 位置 4 出图，主体与 `subject.png` 完全一致 | `subject_excluded_from_model: true` 落进 `run.jsonl`；主体 sha `250c7f78…`；贴图框 `[667, 432, 266, 736]` |
| 2 | 日志记录**实际拿到的尺寸** | `requested_size=1600*1600`，**原生 1600、无需放大**（qwen-image-3.0 上限 2048；wanx 族只有 1024，走 LANCZOS） |
| 3 | 负向词里"产品本体"词表生效 | 生成图里不出现杯子 —— 因为主体是贴上去的，**模型根本没有杯子的像素可用** |

**4.2 那个【待实测】项结案**：`1600*1600` 在 qwen-image-3.0 上是原生支持，`resolution_upscaled` 不触发。`_size_candidates()` 的降级链（`n → 1024*1024 → auto`）保留，是给 wanx 族与未来换模型用的，不是当前路径。

**4.3 接缝：接受它，并说清代价。** 主体是贴进去的，光影融不进背景 —— 这是**已知且被明确接受**的代价。对冲手段是**背景优先选简单环境**（桌面 / 墙面 / 单色），不引入超分、重绘、ControlNet。
「主体不进模型」换来的不是更好看，是**主体一致性从"要验"变成"结构上不可能错"**。

**一处确定性设计（容易被误当成实现细节）**

`pick_hint()` 的取景提示是**确定性挑选**（`kept[slot_id % len(kept)]`），不是随机：

```
随机   → 同一 (run, 坑位) 每次取到不同提示
         → layer=bg 的「重做」会换成另一个场景
         → 那不是重做，那是换了一张图，版本对比立刻失去意义
改数据 → catalog.bg_prompt_hints 换一条，再重做      ← 行为变化来自数据
```

并且 `forbidden_on_image` 在这里有**第二个消费点**：取景提示若命中禁令词 → **弃用该提示**（提示词是人写的，"促销标签"四个字等于主动邀请模型画那个东西）。一条不剩就抛错 —— 那说明类目配置与品牌禁令已经互相矛盾，照跑会产出一张不可能合规的图，**报错比出图正确**。

**生成底复用（`reuse_bg`）—— 它是「位置不对 = 免费」的实现**

| 重做粒度 | 背景该不该变 | 行为 |
|---|---|---|
| `placement` | 不该 | 复用 `raw/slot04_gen.jpg`，**不调模型** |
| `cutout` | 不该 | 复用，**不调模型** |
| `bg` | 该 | 重新生成 |

没有这条复用，位置 4 会为了把主体挪 20 像素去花一次模型调用 —— 那笔钱买不到任何东西，还会顺手换掉背景，让"只是位置不对"这个判断失去意义。

**验收口径修正（计划写错了，记录在此）**

计划原文：「每加一个 = 一个文件 + 表里一行；`orchestrator.py` 零改动（`git diff --stat src/orchestrator.py` 为空）」。

**这条不成立，而且是好事。** 实施过程中撞出一个顺序问题，它必须在编排层解决：

```
一次 run 的时间线（M5 之前）
  ├─ 抠主体（本地；进程刚起来，稳）
  ├─ [位置 1/2/3 出图]
  ├─ ★ 位置 4：云端生成 55—63s   ← 这一段之后，进程的内存状态变了
  ├─ 位置 5
  ├─ 位置 6：抠 contents    ← 此刻 ORT 偶发 bad allocation / numpy MemoryError
  └─ 位置 7：抠 competitor  ← 同上

症状：同一个抠图调用，进程刚起来时稳，跑完一次 55s 生成之后不稳。
      位置 6/7 恰好排在位置 4 后面 → 「整格失败」。
```

**解法：把所有抠图提到模型调用之前**（`cutouts.prepare` + `orchestrator.produce_cutouts`）：

```
一次 run 的时间线（现在）
  ├─ E0 体检
  ├─ 抠主体 + 抠 contents + 抠 competitor   ← 全挤在进程最清爽的时候
  ├─ [位置 1/2/3 出图]
  ├─ ★ 位置 4：云端生成
  └─ 位置 5/6/7
```

这一改同时兑现了三条**已有**规矩（不是新加的）：

1. **抠图失败就不该再去调模型** —— 这条本就写在主体那一步，只是当时只管了主体
2. **不烧冤枉钱** —— 素材抠失败 → 该格跳过（不是整批停），而且是在花钱**之前**就知道
3. **一轮只抠一次** —— 抠好的素材落在 `raw/cut_*.png`，`--redo 7 --layer placement`（只挪位置）直接读它。否则既多花 25s，又可能因为"这次抠图走了另一条路"而**换掉像素** ——「只改了位置」这句话就不成立了

**代价**：`orchestrator.py` 必须改（这是编排层的事）。所以 M5 验收改成**行为级**的：
`grep -En 'slot["id"] ==' src/orchestrator.py` **零输出** —— 加坑位仍然只需加数据行。

**抠图归属（分清，否则会长出第二个真相源）**

### M6 ✅（重做与交付 —— 这一步抓出全链路最贵的缺陷）

**四个重做粒度与架构三层一一对应，不是随手分的档**

```
LAYERS = ("text", "placement", "bg", "cutout")
```

| 粒度 | 语义 | 复用多少 | 花钱 |
|---|---|---|---|
| `text` | 文字层（确定性） | 拿上一轮文字底重新叠字 | ✗ |
| `placement` | 合成层（确定性） | 只动落点/缩放；**背景像素与文字内容都不变** | ✗ |
| `bg` | 背景层（生成性） | 重新生成空背景 | ★ 唯一花钱的一档 |
| `cutout` | 主体（本 run 唯一一份） | 本地重抠主体**与素材**，所有读它们的坑位一起重出一版 | ✗（本地） |

这个划分本身就是给运营的**代价提示**：七成情况（文案、构图）不花钱，只有背景花钱 —— 而背景恰好是唯一本来就该由模型产生的东西。

**版本不覆盖**

重做写 `slot02_feature_2.jpg`，不覆盖 `_1`。理由不是"怕丢文件"，是**覆盖会抹掉归因数据**：`_1` 记录着"运营当时看过它、然后决定重做"，而那正是"哪一版被采纳、为什么被采纳"的唯一证据。**归因数据就是资产。**

**★ 全链路最贵的缺陷：静默降级换像素**

`layer=cutout` 的重做报了一个只在这种路径上才会出现的错：素材重抠失败 → `synth` 里还留着"推理失败就降 floodfill"的旧逻辑 → 于是**同一格的两版图，主体是两条不同抠图路径的产物**，而日志只写了"重做成功"。

它的严重性在于**版本对比的前提被抽掉了**：v1 与 v2 的差异里混进了"换了一种抠图方式"这个变量，运营看到的"重做后变好了"其实是换了算法。

**已修**：`synth.remove_background` 推理失败 → 重试 `INFER_ATTEMPTS = 3` 次（**每次丢掉缓存的会话**再试 —— 那才是真重试，否则是在同一块坏内存上把同一个调用念第二遍）→ 仍失败抛 `CutoutError`，**绝不静默换 floodfill**。

**但"丢掉缓存的会话"还差一步（2026-09-21 复审抓出，同一个缺陷的第二层）**

`_drop_session(...)` 加 `session = None` 之后，旧会话**依然活着**。真正钉住它的既不是缓存、也不是局部变量，而是 `except` 块里那个异常对象自己：

```
exc.__traceback__  →  整条栈帧链  →  帧的局部变量 / 形参里就有 `session`
```

只要 `exc` 还在作用域内，这条链就一直替我们握着那块 arena。

判据与证据（受控实验，只改"清不清 traceback"**这一个变量**）：

| 变量 | 新建会话那一刻，旧会话还活着吗 |
|---|---|
| 不清 `exc.__traceback__`（原代码） | **True** ← 新旧两个 arena 并存，峰值翻倍 |
| 清掉 `exc.__traceback__` | **False** |

在"已经拿不到内存"的场景里，峰值翻倍就是必输：重试**必然继续失败**。而日志写着"连续失败 3 次"，看起来像运气不好 —— 那个失败其实是自己制造的。**"看起来偶发"是最容易被放过的失败形态。**

已修（`synth.remove_background`）：重试前先 `exc.__traceback__ = None`，再丢缓存、再置空局部名、再 `gc.collect()`，然后才新建会话。

并把它做成**可回归的断言**（`verify_m6.py` K 段）：用 `weakref` 观测「`_load_session()` 被调用那一刻，上一个会话是否已被回收」，要求恰好为 `False`。没有这条断言，这个修复下次就会被"看起来等价"的写法无声改回去。

> 这条纪律与 M2 的"不假装验过水印"是同一个东西的两面：
> **不确定的事要么报错、要么要求人签字，不许悄悄换成另一种东西。**

**验收结果**（`python tools/verify_m6.py` → `EXIT=0`）

| 项 | 实测 |
|---|---|
| `layer=text` 重做位置 2 | 0.06s、**0 次模型调用**、`subject_sha256` 不变 |
| `layer=placement` 重做位置 4 | 0.22s、**0 次模型调用**、`reused_bg` 生效 |
| `layer=cutout` 重做主体 | 主体重抠 21.6s、素材重抠 sha 一致、读主体的坑位各自新增一版 |
| 版本不覆盖 | 重做后 `_1` 仍在，新增 `_2`/`_3`；`slot04` 出现 v1–v5 |
| `--progress` | 进度行落 `run.jsonl`，等模型那 60s 是看得见的 |

**一处 CI 级修正**：`verify_m3..m6` 各自写了一份**严格**的 jsonl 读取器，而产品侧早有容错读法。历史遗留的**半行日志**（正是 README §7.8 记录的那次并发截断）会把四次验收一起炸掉。已统一为 `orchestrator.read_records(d, tolerant=True)` —— **验收脚本读日志的口径必须与产品一致**，否则它测的是脚本，不是产品。

**读模型：状态只有一个源**

```
run.jsonl（追加式日志）  ← 唯一事实来源
      │
      ├─ run_state(run_dir)       → 审核台要的每一样：七格的版本列表 / 采纳状态 /
      │                             可点档位 / 成本 / 跳过原因 / E0 与签字 / 主体与素材抠图
      ├─ mark_accept(run_dir, n)  → 追加一条 accept，**不改任何既有记录**
      └─ export_bundle(run_dir)   → 交付「被采纳的那一版」+ sha256 清单
```

**「已采纳」由日志顺序判定 —— 这一条改过一次定义**

| 定义 | 问题 |
|---|---|
| ~~采纳版号 == 最新版号~~ | ①「重做后自动回待审」与「比较后仍采纳旧版」相互冲突；② **比较后仍采纳 v1 无法登记**，而 v1 才是要交付的那一版 |
| **最后一条 accept 晚于最后一条 redo → 已采纳** | 两种情形同时正确：重做后旧采纳作废（redo 更晚）· 比较后仍采纳旧版（accept 更晚） |

`export_bundle()` 导出的因此是 **`accepted_version`，不是 `latest`** —— 交付的是"运营签字认可的那一版"，不是"目录里最新的那几版"。

### 复审（2026-09-21 傍晚）：两个真问题 + 一条内存事实

#### 1. 抠图重试没有真正回收旧会话（产品缺陷，已修）

详见「M6 ✅」一节的第二层说明。结论：持有旧会话的是 `exc.__traceback__` 这条
「异常 → traceback → 栈帧 → 局部/形参」的引用链；清掉它才算真重试。
现已修，并加了一条**机制级**回归断言（`weakref` 观测新建会话那一刻旧会话是否已回收）。

#### 2. 一次抠图要 6—9 GB 内存（实测，写进错误文案）

| 时点 | 物理可用 | 可提交可用 | 内存负载 |
|---|---|---|---|
| 抠图前 | 6851 MB | 17849 MB | 51% |
| 抠一次之后 | **889 MB** | **8553 MB** | 93% |

`birefnet-general-lite` 在 1024² 输入上跑一次，吃掉约 **6 GB 物理 / 9 GB 提交内存**。
这不是"有点占内存"，是**同机第二个进程必然拿不到内存**的量级。

#### 3. 两个进程各揣一个会话 → 后启动的那个必然失败（不是产品缺陷，但必须知道）

对照实验（同机、同输入、同代码，只改"父进程手里有没有会话"）：

| 父进程状态 | 服务子进程 |
|---|---|
| 干净（不起任何 run） | ✅ 30.7s 出图 |
| 揣着一个抠图会话 | ❌ 3 次推理全挂（ORT 在 decoder 的 Sum 节点报 `RUNTIME_EXCEPTION`） |
| 先放掉会话再起服务 | ✅ 22.4s 出图 |

产品侧在这个条件下的行为**全程正确**：重试 3 次 → 显式抛 `CutoutError` → **不静默降级**。
所以没有改产品逻辑，改的是两处"表述与前提"：

1. **错误文案补上量级**：原来只说"通常是内存不足"，现在写明"实测约需 6—9 GB 可提交内存"，
   并点出"同机会话各要一份，两个一起就把彼此挤死" —— 报错是运营唯一的线索，量级比形容词有用。
2. **验收脚本起服务前先放掉本进程的抠图会话**（`release_cutout_sessions()` + 注释写明实测数据）。
   原因不是"让测试变绿"，而是：**A 段在进程内跑过真抠图，那 6 GB 是验收自己留下的债**，
   真实用法里命令行跑完进程就退出了，不会有谁揣着 6 GB 会话再去起审核台。
   B 段该测的是**接口契约**，不该受 A 段的余温影响。

#### 4. 验收沙箱改成"每跑新开一个时间戳子目录"（环境逼出来的设计，别改回去）

本机的删除会被导去回收站，而且**对顶层目录会失败并 fail-closed**：`shutil.rmtree` 与
PowerShell `Remove-Item -Recurse` 都返回 `SHFileOperationW 0x2` → 抛错。而**删子目录是好的**。
原来的写法 `SANDBOX = ROOT / "out_verify_m7"` + 开头 `rmtree(SANDBOX)`，于是只要上一轮用了
`--keep`，下一轮就**死在清理那一步**，A/B 两段验收一起作废（这次真发生了）。

改成 `SANDBOX = SANDBOX_ROOT / <时间戳>` —— **不删旧目录**，让沙箱天然不需要被删。
旧目录留着不影响任何断言（断言引用的都是这一轮新生成的名字）。
收尾时清理失败也会**写进报告**（`· 沙箱没清掉（…）→ 留在 …`），不静默吞掉。

#### 5. 顺带修掉的两处"表述不实"

| 位置 | 原来 | 现在 |
|---|---|---|
| `web/index.html` 成本栏 | `model_calls_used == null` 一律显示"未记录（M7 之前的 run）" | 按 `state.finished` 分开：跑到结束=旧格式的 run · 没跑到结束=**这一轮没跑到结束**。归因错了比不显示更坏 |
| `tools/verify_m7.py` B8 | 上游没出图时，`str(None)` 被当成路径去请求 → 404，报成"路径守卫坏了" | 显式报"上游一轮没出图 → 没有产物图可读"，**原因要报准确的，不能张冠李戴** |
